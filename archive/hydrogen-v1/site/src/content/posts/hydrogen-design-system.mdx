配色这件事我一直做不好。每次开新项目都要在「主色用哪个蓝」上耗掉半天，
最后选出来的那个也说不出比隔壁那个好在哪。更糟的是三个月后回来加一个新分类，
完全想不起当初那五个颜色是按什么规律排的，只能凭感觉再挑一个，慢慢就漂了。

所以这次我换了个办法：不挑颜色，改成算颜色。

## 分类的颜色来自里德伯公式

主题定成 Hydrogen 之后，分类的自然映射就是氢原子的发射谱线。
电子从 n<sub>hi</sub> 能级落到 n<sub>lo</sub>，放出一个光子，波长由里德伯公式给出：

```
1/λ = R_H · (1/n_lo² − 1/n_hi²)
```

巴尔末系（n<sub>lo</sub>=2）刚好整段落在可见光里，前四条就是四个分类：

| 分类 | 谱线 | 跃迁 | 空气波长 | 颜色 |
|---|---|---|---|---|
| 工程日志 | Hα | n=3 → 2 | 656.29 nm | 红 |
| 系统设计 | Hβ | n=4 → 2 | 486.14 nm | 青 |
| 认知与模型 | Hγ | n=5 → 2 | 434.05 nm | 蓝紫 |
| 随笔 | Hδ | n=6 → 2 | 410.18 nm | 紫 |

波长转 sRGB 用 Dan Bruton 那个经典的分段算法，含可见光两端的视觉响应衰减和 gamma 0.8。
整条链是：主量子数 → 波长 → RGB。没有一步是我拍的。

## 差 0.35nm 的那次翻车

第一版我用的是里德伯常数 R<sub>∞</sub> = 1.0973732×10⁷ m⁻¹，算出 Hα 是 656.11nm。
但教科书上印的是 656.28nm。差了 0.17nm，看着像舍入误差，我差点就放过去了。

不是舍入误差。R<sub>∞</sub> 假设原子核无限重，实际上质子只有电子的 1836 倍重，
两者绕共同质心运动，要做约化质量修正：

```
R_H = R_∞ / (1 + m_e/m_p)
```

改用 R<sub>H</sub> 之后 Hα 算出 656.46nm。还是对不上 656.28 —— 因为里德伯公式给的是
**真空**波长，而光谱表印的是**空气**中的波长。空气折射率约 1.000276，
过一遍 Edlén 色散公式，656.46 / 1.000276 = 656.29nm。

对上了，误差 0.01nm。五条谱线全部对上。

> [!NOTE]
> 这一段的价值不在于精度本身。既然整个设计前提是「颜色由物理推导」，
> 那推导链上任何一环偷懒，这个前提就变成了装饰。0.35nm 在屏幕上看不出来，
> 但「我算的和光谱表能对上」和「差不多就行」是两种不同的东西。

## 真色和文字色是两个角色

Hα 的真色是纯红 `#ff0000`。作为一条 1px 的发射线，这是准确的 —— 真实谱线在感光元件上
就是那么一道饱和的亮线。但拿它写正文会刺眼，在浅色背景上对比度还不够。

所以我把它拆成两个角色：

- **谱线真色**只用在小面积发光元素上：发射线、色点、色卡。
- **文字色**从真色派生：保持色相，收敛饱和度到 0.86 以下，然后抬明度，
  直到对目标背景的对比度达到 6:1。

6:1 而不是 AA 下限 4.5:1，因为 4.5 对红色解出来是个火红 `#ee1717`，
虽然合规但视觉上很吵；6.0 解出来是 `#f35959`，柔和的鲑红。这是在合规基础上留的余量。

暗色和浅色主题各派生一套，两边都跑对比度校验，不达标就让构建失败。

## 生成，而不是抄写

Tailwind v4 的 `@theme` 只接受静态值，但我的颜色是算出来的。
如果我手动把算出的 hex 抄进 CSS，那份 CSS 立刻就变成第二真源，
下次改谱线定义时必然忘记同步。

所以走生成：一个脚本从 `physics.ts` 和 `spectrum.ts` 读定义，
算完写进 `spectrum.generated.css`，生成物入版本库。
CI 里跑 `npm run verify:palette` 重算一遍并比对，不一致就失败 ——
不管是有人手改了生成物，还是改了定义忘了重新生成，都能拦住。

Node 22.18 之后原生支持 TypeScript type stripping，所以脚本能直接
`import` 同一份 `.ts` SSOT，不需要先编译，也不需要为了脚本再复制一份 JS 逻辑。
唯一的代价是 `src/lib` 内部互引要写显式 `.ts` 扩展名，因为原生 ESM 不做扩展名补全。

## 它替我挡掉了什么

一开始我以为这只是个自洽的小把戏。用下来发现它真正的作用是**替我做决定**：

**第五个分类配什么颜色。**巴尔末系往系限（364.6nm）挤，Hε 之后几条谱线的颜色
几乎分辨不出来，硬塞第五条会让两个分类在界面上看起来是同一个色。
所以第五个分类改用帕申系的 Paα（1875nm，红外），界面上明确标「伪彩色」，
颜色由把整个帕申系线性映射到可见橙端算出来。这是天文图像处理的标准做法，
而不是我挑了个橙色然后编个理由。

**置顶文章该放几篇。**文章按玻尔模型分层，每层容量是 2n²，来自泡利不相容原理。
K 壳两个位置，所以整站永远最多两篇「基态」文章。想加第三篇，
必须先把一篇降到 L 壳。构建时校验，超了直接失败。

这条约束的好处是它不是我定的，所以我也没法为了方便就改掉。
以前「精选文章」会慢慢膨胀到七八篇然后失去意义，现在它膨胀不了。

**分层和分类是不是两套重复的分类法。**一开始我担心这个 —— 又要选分类又要选能级，
是不是给自己找麻烦。后来发现它们在物理上本来就是同一件事：
电子从 n=3 落到 n=2 放出 656nm 的光子，这既是一次能级跃迁，也正好是 Hα 那条谱线。
分层描述「这篇有多核心」，分类描述「它落在哪个主题」，两者共享同一批能级，
不是并行的两套标签。

## 什么时候不该这么做

这套办法成立有个前提：约束的方向恰好和你想要的编辑纪律一致。

2n² 限制置顶文章数量，这是我本来就想要的。如果物理约束逼我做的事情
和产品需求相反 —— 比如某个真实常数要求我把导航项限制到 3 个，
而我确实需要 7 个 —— 那就不该硬套，那时候诚实的做法是承认这里是设计选择。

我在两个地方做了明确的妥协，都写在界面上了：红外谱线用伪彩色（标注了），
文字色不是真色（说明了派生规则）。剩下的地方，数字都是能拿去核对的。
