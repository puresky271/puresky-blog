我之前所有博客的「精选文章」都烂在同一个地方：一开始放三篇，
后来觉得这篇也不错，那篇也值得，半年后列表里有九篇，
读者面对九篇「精选」和面对全部文章没有区别。

## 为什么会膨胀

因为「要不要加这篇」这个决定的成本是不对称的。

加一篇的成本是零：改个 frontmatter 就行，而且当下我确实觉得它够好。
不加的成本是我要承认它不如已有的那几篇 —— 这个判断更难做，而且做完会有点不舒服。

所以每次遇到边界情况，理性的选择都是加进去。膨胀不是意志力问题，是激励结构问题。

## 换成一个我改不了的规则

这个博客的文章按玻尔模型分四层。关键是每层容量不是我定的，是 2n²：

| 层 | n | 容量 | 束缚能 |
|---|---|---|---|
| K | 1 | 2 | −13.61 eV |
| L | 2 | 8 | −3.40 eV |
| M | 3 | 18 | −1.51 eV |
| N | 4 | 32 | −0.85 eV |

2n² 来自泡利不相容原理。K 壳只能放两个电子，所以 n=1 层只能放两篇文章。

然后我把它写进了构建校验：

```ts
export function assertShellCapacity(counts: ReadonlyMap<number, number>): void {
  const violations: string[] = [];
  for (const shell of SHELLS) {
    const occupied = counts.get(shell.n) ?? 0;
    if (occupied > shell.capacity) {
      violations.push(
        `n=${shell.n}（${shell.letter} 壳）容量 ${shell.capacity}，实际 ${occupied} 篇`
      );
    }
  }
  if (violations.length > 0) {
    throw new Error(`壳层超容，违反 2n²：\n  ${violations.join('\n  ')}`);
  }
}
```

超了就抛错，`astro build` 直接失败。不是警告，是失败。

## 现在那个决定变成什么样

想给 K 壳加第三篇，我必须先把现有两篇里的一篇降到 L 壳。
也就是说，「这篇值得放进最核心」这个判断被迫和「那篇不如它」同时做出来。

这个改动很小，但它把决定的形状换了：从「要不要加一个」变成「换掉哪一个」。
后者是个真的比较，前者不是。

有几次我确实想加第三篇，然后打开另外两篇看了看，发现比不过，就放回 L 壳了。
这个「打开看看」的动作，在没有容量限制的时候我一次都没做过。

> [!TIP]
> 这个办法能用的前提是约束方向和你想要的纪律一致。
> 2n² 恰好限制了我本来就想限制的东西，所以它是助力。
> 如果某个物理常数要求我把导航项砍到三个而我确实需要七个，
> 那就不该硬套 —— 那时候诚实的做法是承认这是设计选择，而不是假装它有物理依据。

## 界面上把空位画出来

能级页画的是一张真的玻尔图：每层一圈轨道，轨道上实心点是已发表文章，
空心点是剩余位置。K 壳画两个点，满了就是两个实心。

把空位画出来是有意的。如果只显示「2 篇」，读者不知道这是全部还是我懒得多写。
显示「2/2，已满」，那条约束就一直在场 —— 对读者是信息，对我是提醒。
