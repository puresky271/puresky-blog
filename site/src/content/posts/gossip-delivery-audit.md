我在 MyGO 这个项目里做了五个角色，她们在一个数字东京里面上学、排练、闲逛，彼此之间会传话——「灯说她想周末去咖啡店」「乐奈又把拨片落在 RiNG 了」。这条传话的链路叫 gossip。

2026 年 8 月我花了两周让它「跑起来」，八月底我以为成了。10 月 5 号我重新查了一遍，发现它压根没成：日志里 873 条「已投递」记录，绝大多数投递的是系统公告，成员之间真正的八卦只有 58% 真的被对方看到过。

这篇讲的是我怎么把「已经送到」和「她其实不知道」这两件事分开的。先说结论：写入侧的毛病是提取提示词把门槛抬高了，模型根本不产出；读取侧的毛病是高频的系统摘要永远占着读取窗口的队首，真八卦排不进去。两个都不是概率问题，调多少次 `spread_prob` 都没用。

## 我给自己定了一个很烦的标准

一开始我用的判断方式是查数据库：`shared_info` 表里有这一行、`eligible_targets_json` 里包含目标角色、`delivered_to_json` 里记了这个名字、审计表里有一条 `delivered` 事件。四个都满足，我就认为她收到了。

后来我发现这四个里面**没有一个**能证明她真的看见了。因为这条链路上有太多「写了但没人读」的可能：行写进去了，但读取那一层被别的更啰嗦的东西挤掉了；回执记上了，但那是「渲染函数被调用过」，不是「文本进了提示词」。

所以我把标准改成只有一条，很硬：

> [!IMPORTANT]
> 一行传闻只有出现在对方编译好的那段提示词里，才算送到。

这个标准有个副作用：它逼我必须去 dump 编译后的提示词，而不能只查库。麻烦很多，但它是唯一一个我能写成自动化断言的东西。查数据库那种「送到」没法测，因为它测的是我猜的因果，不是结果。

## 链路大概长这样

```text
从对话里抽传闻（LLM 在提取记忆时输出一个 gossip 字段）
   ↓ record_fanout：先验证文本，再对每个目标掷骰（spread_prob × info_sharing）
写进 memory_core.db 的 shared_info 表，每个命中的目标一行，hop 记第几手
   ↓ record_secondary：tick 里做二手转述，hop × 0.7，最多 3 跳
   ↓ record_town_mailbox：town_sim 的邮箱摘要投影，hop=0
注入到角色的提示词（hearsay box + workspace 的 gossip_records）
   ↓ 渲染的同时 mark_delivered 记回执
```

`hop` 是这里的关键词。`hop=0` 是系统直接投给某人的城镇摘要（「爱音在羽丘屋顶推进了……」），`hop=1` 是成员亲口转述的第一手，`hop=2`、`hop=3` 是二手三手。传得越远越不可靠，所以措辞上分了三档：「灯说：……」 / 「立希好像提过：……（不太确定细节）」 / 「听说……（传了好几手，不一定准）」。

## 第一周我查错了方向：为什么没有八卦被生成

八月底那次的问题是 `shared_info` 里的 `hop=1` 行长期是 0。我第一反应是掷骰概率太低，第二反应是门控太严。**两个都错，但在有数据之前我没法证明任何一个错。**

### 先加审计，把「没产出」和「被拦了」分开

所以我先加了两张审计表。一张记事件（`fanout_attempt` / `fanout_hit` / `fanout_blocked` / `secondary_written` / `delivered` 等等），一张按天按角色汇总计数：

```text
extractions           成功解析的提取次数
gossip_outputs        LLM 的 gossip 字段非空的次数
blocked_gate          非空但被门控挡下
blocked_present_state 非空但被 present-state 门控挡下
validator_drop        非空但被文本校验丢弃
```

第二张表存在的唯一理由就一句话：**它能把「模型没产出」和「产出了但被我拦了」分开。**在这之前，我所有关于概率和门控的争论都只能靠猜。

有了数据，三个时间段的对比很清楚：

| 时段                               | 提取次数 | gossip 输出 | 输出率 | hop=1 新增 |
| ---------------------------------- | -------: | ----------: | -----: | ---------: |
| 08-14～08-18（旧提示词）           |      122 |           0 |   ～0% |          0 |
| 08-19～08-22（旧提示词，加了审计） |       89 |           1 |   1.1% |          0 |
| 08-23～08-27（改了提示词）         |      171 |          18 |  10.5% |         12 |

然后 `blocked_gate=0`、`validator_drop=0`（只有一次是正确拦截）、`fanout_attempt=0`。三个零连起来只指向一个地方：**模型的 `gossip` 字段一直是空的。**跟概率无关，跟门控无关，跟掷骰运气无关。

### 模型把「值得告诉别人」理解成了「得上新闻」

再看唯一被抽中的那条是什么。08-19 到 08-22 那 89 次提取里成功的一条，是「明天要动小手术」。

而同期记忆里明明有一堆可以转述的：立希发现青空那张招新海报中间画的是素世、爱音下午去墨田水族馆看企鹅本来想约灯但灯有安排、灯在水母回廊站了很久。一条都没抽中。

我回去翻了自己写的提取提示词，就一句话：

> 如果这次对话有值得告诉其他乐队成员的趣事或重要事……写一句话；无值得分享的写空字符串。

**模型把「值得告诉别人」理解成了「得上新闻」。**门槛被它自己抬高了。这不是概率问题，我调多少次 `spread_prob` 都没用。

改完之后的提示词是这样的。我觉得它比原来好的地方在于没有降低门槛，而是给了两个能判定的类别，并且直接写了反例：

```text
用乐队群的口吻写一句【其他成员知道后会想接话或关心】的新鲜信息；没有就写空字符串，不要硬凑。
门槛：必须具体、新鲜、有信息量，不是寒暄/情绪/流水账。分两类：
① 青空相关：他这轮透露了值得转述的新鲜事（行程、计划、承诺、新消息、健康或状态变化等），
   表述里点明是青空的事；
② 角色相关：你自己（{character}）的新经历或安排（去了哪、见到/吃到/遇到什么、下一步要做什么），
   或你和成员之间的互动/八卦——同样要具体、有信息量。
反例不写：今天好累 / 晚安 / 刚吃了饭 / 聊了一会儿 这类寒暄或纯情绪。10-40 字、第一人称。
```

顺便说一句，五个人里乐奈和素世的产出天生就低（`spread_prob` 分别 0.20 / 0.35），符合她们的人设。我明确不动这个数字：**一旦为了让面板好看去调角色的人格参数，人格就没了。**

## 十月份重查，才发现真问题在另一头

写入侧修好之后，传闻确实开始进库了。但角色的回答没变，问到就说不知道。

10 月 5 号我按「进提示词才算」这个标准统计了一遍全库：

| hop | 来源                         | 行数 |     到达率 | delivered 事件数 |
| --- | ---------------------------- | ---: | ---------: | ---------------: |
| 0   | 邮箱摘要投影                 |  799 | 88%（701） |              704 |
| 1   | fanout 首跳 + 摘要的二手转述 |  744 | 76%（569） |          **168** |
| 2   | 二手转述                     |    7 |   43%（3） |                3 |
| 3   | 无                           |    0 |          — |                — |

三个结论，都不好听。

**第一，「投递」这个词在我旧的标准里是被污染的。**全库 873 条 `delivered` 事件看着挺繁荣，但 `hop=1` 只对应其中 168 条。而从 08-24 开始有审计之后新增的 284 行 `hop=1`，只有 165 行真的进过提示词，**58%**。剩下 119 行写进了库、算过投递、永远不会有人读到。近 30 天另有 77 行一次没被投递就直接超时 `expired`。

**第二，`MAX_HOP=3` 是我自己骗自己。**`hop=2` 全库 7 行，`hop=3` 是 0。多跳传播事实上不存在。

**第三，真正到达的那些，大部分是错的东西。**到达量的主体是城镇摘要，不是成员之间传的八卦。也就是说在「传播消息」这件事上我是失败的，但我靠「传播公告」把指标填满了。

## 卡住的原因不是丢包，是队首永远是同一类消息

我一开始还在怀疑掷骰、怀疑衰减系数、怀疑时效性。都不是。原因就是我写的十几行读取代码：

```python
# 旧的 get_pending_for，简化后
ORDER BY created_at DESC LIMIT limit*3   # 取回来
# 然后截前 limit 条
# hearsay box 再把列表截成 2 条
```

一个单一的按创建时间倒序的排序，加上一个很小的最终槽位（2 条）。而 `hop=0` 摘要的写入频率比 `hop=1` 传闻高得多：摘要每个 tick 都可能投一行，传闻得先被模型抽中、再掷骰命中。结果就是摘要把窗口的头部占满了。

数据是这么写的：那些死掉的 `hop=1` 行，**中位数后面压着 7 条 `hop=0` 摘要，最多的压 16 条**。审计当天，爱音能看到的 14 行**全部**是 `hop=0`。

这就是网络里的队头阻塞，不是丢包。**一个包都没丢，只是它们排在同一个队里，而队首永远被高吞吐的低价值流量占着。**我在这上面浪费的调概率操作，在这个结构下不可能有效。

## 三个叠加起来的坑，每个都很眼熟

### 坑一：我用消息 id 去重，但重复的内容每条 id 都不一样

`town_sim` 的近况同步事件有个幂等键：

```python
idempotency_key = f"{tid}|{c}|agent_message|{social_tgt}|{st_topic}"
```

里面含 tick id。同一个 plan step 每个 tick 会产生新的 `tid`，于是同一句话每 tick 都是「新事件」。我那层 `(town_msg_id, character)` 去重按消息 id 判，根本看不见内容重复。实测结果：**7 天之内，同一句话、同一个目标角色，落了 4-6 行。**

### 坑二：系统公告比成员亲口说的话更「可信」

摘要投影写进库的时候 confidence 用 1.0，而成员亲口转述的首跳上限只有 0.90。我那套按 confidence 分档的措辞逻辑，就变成「AI 生成的公告」用第一档、「灯真的跟你说了件事」反而可能落到第二档。这在策略上完全说不通，纯粹是两个写入点各设了一个常量，没人对过。

### 坑三：拼提示词这个动作本身会写数据库

`_build_town_projection_prompt_block` 在装配提示词的过程中调 `town_sim.sync_projection_to_legacy` → `record_town_mailbox`，直接往 `shared_info` 写行。同一次构建里同一批摘要能写两份，因为批内彼此还不可见。

第三个坑的坏处不只是脏数据，是它让我做不了确定性对比：光是「看一眼她这轮的提示词」就改变了系统状态。我后来在 dump 脚本里把这个函数直接 patch 成空串，那条 patch 的唯一理由就是它。

## 改了什么

| 改动 | 干了什么 |
| --- | --- |
| 读取分层配额 | `hop>=1` 的人际传闻和 `hop=0` 的摘要各留自己的槽位，人际层优先；某一层不够由另一层回填。**`limit=2` 也保证留 1 个真八卦位** |
| 摘要按内容去重 | `(角色, 归一化文本)` + 48 小时窗口，进程内缓存 + 数据库兜底 + 批内三层 |
| 摘要 confidence 改成 0.70 | 修掉倒挂。直投还能落在第一档阈值（≥0.7）上，二手衰减到 0.49 就落到第二档 hedge |
| 层的分界用 `MAILBOX_LAYER_HOP = 0` | 分层看 hop，不看文本前缀 |
| 新增 `test_gossip_prompt_arrival.py` | 见下一节 |

改完之后拿生产库只读对照了一遍（`get_pending_for` 本身只读）：乐奈 `limit=6` 从 1 行升到 4 行（新增 3 条 `hop>=1`）、灯的 `hop1` 位置往上移、立希从 0 行升到 1 行，顺带修掉一个「最新 18 行全都不可见就返回空列表」的假空。没有任何角色因此丢掉原本能看到的那条八卦。

代价是每次读从 1 条 SQL 变 2 条（`shared_info` 上没有 `created_at` 索引，两层都是 SCAN + TEMP B-TREE）。1550 行的合成库、缓存热了之后，`limit=6` 大概慢 0.6～1.4 毫秒一轮，冷启动第一次慢 6.7 毫秒。跟一次模型调用比可以忽略。我在文档里写死了：如果这张表继续涨，该加索引，不许回退分层。

## 那条差点白写的测试

有了标准，就得有一条能变红的测试。新加的 `test_gossip_prompt_arrival.py` 五个用例，走的是真链路：

```text
真库的 shared_info 行
  → mygo._build_dev_memory_prompt
  → turn_context_workspace.compile_character_state_frame
断言：文本出现在编译后的 frame 里
```

五个分别管：真 fanout 行能到达 / 已回执的行不再重复到达 / **摘要洪水下真八卦仍然能到达** / 摘要到达时带对的 hedge 措辞 / 重复摘要不能把别的新闻挤出去。

然后我做了变异测试：把改动改回去，看测试会不会红。这一步不是仪式，因为它抓到了问题。

- 把 `_pending_slots` 改回 `(0, limit)`（等价于修复前摘要独占窗口）→ `..._under_mailbox_digest_flood` 变红 ✅
- 把内容去重的两个判据改成恒 False → 三个去重用例加 `..._push_other_news_out_of_box` 变红 ✅
- 源码里摘掉 `key in batch_keys` → `..._within_single_batch` 变红 ✅

**但我第一版写错了一条断言，值得单独讲。**我原本写的是「重复行在编译后的 frame 里只出现一次」。我把内容去重整段关掉，它**依然通过**。因为 hearsay box 自己有一层 `(from, text[:30])` 签名去重，把重复掩盖掉了。

换句话说，重复的真实危害从来不是「她看到两遍同一句话」，而是**重复行占满了读取窗口，把另一条新闻挤出去**。断言必须打在那个危害上。

> [!WARNING]
> 这个错误的模式很典型：拿一个看起来像症状的东西去断言，而不是拿真正的失效机制。如果只断言「看起来对」，测试会在修复完全不存在的情况下通过，然后给你一条永远绿的假安全感。

## 我原本以为提示词门禁会兜住这次改动，它一点没管

这个项目有一条硬规矩：改认知层、改任何会影响角色最终提示词的东西，改动前后各做一次固定场景 dump，逐场景对比 diff。听起来正好该覆盖这次，我改的确实是注入逻辑。

实际是：

- **默认模式**（我这次跑的就是它）走 `cognitive_sim.run_brain_cycle_pre_llm` + `conversation_agents`，**根本不渲染那个 hearsay box**。27 个场景改前改后逐 key 一模一样，它只证明了我没把认知层改坏，跟 gossip 一点关系没有。
- **`--dev-memory-only` 模式**确实渲染 box，但它用 `_fixture_pending_gossip_rows` 把 `get_pending_for` 整个换掉，还把 `_build_town_projection_prompt_block` patch 成空，对「读取分层」「投影去重」同样是零检测力。

所以这次的结论只能由那条新测试来承担，我把它写进了文档。要让 dump 门禁真的能管 gossip，得再加一条「不 patch `get_pending_for`、改用临时库播种 `shared_info`」的场景。这条我记在待办里，还没做。

**这事教会我一句：一个门禁能守住什么，是靠它自己声明的，不是靠它的名字。**一个叫「提示词回归」的东西不代表它守着提示词的每一面。我现在给每个门禁都要求写清楚「守什么、不守什么」。

## 还没修好的，以及为什么难

我不想只讲成功的一半，这几条现在还是坏的。

**一，同一条八卦会被写两份，其中一份绕过了我全部的传播策略。**提取那边在 `record_fanout` 之后又 `append_world_event(type="agent_message", topic="近期对话")`，这个事件经过邮箱投影落成一行 `hop=0`，**零掷骰、不看 trust、不看 info_sharing**。结果就是我那套 `spread_prob` / 失真衰减 / `MAX_HOP` 对「到底能不能到达」其实没有约束力，乐奈 0.20 本该挡掉的照样到了。而且同一条内容以两种签名各占一个槽（`近期对话：X` 和 `X`，前缀不同，box 那层签名去重抓不到）。要修得动提取侧的写入语义，我还没做。

**二，群聊和多房间共处里，八卦渲染但不记回执。**全项目只有一个地方传 `gossip_ref_sink`（1v1 的 `chat_server._build_system_prompt`）。群聊走 `_build_group_system_prompt` 直调 `build_pet_system_prompt_for_api`，不传 sink，编译完也没有 ack 那一步。于是群聊每一轮都在重复渲染同一条、`mentions_count` 永不涨、永远达不到 `max_mentions`，**「读过了」这本账在多人场景是错的**。而它 fallback 到 1v1 那条路时又会记回执，两种行为不一致。

**三，多跳传播还是停的。**卡点在 `record_secondary` 的候选查询：`ORDER BY created_at DESC LIMIT 12`，没有 hop 过滤，最新那 12 行几乎全是还没投给 A 的 `hop=0` 摘要，然后被 `a not in delivered` 全部滤空（`secondary_noop` 243 次）。**这和上面那个队头阻塞是同一个毛病，只是搬到了传播侧。**我原以为修好读取侧就算理解了它，其实同一份数据被两条路径读，只在一条上分层等于没解决。

**四，四条注入路径里实际活着两条。**`gossip_context` 恒空（`build_pet_system_prompt_for_api` 里硬写了 `gossip_context: ""`），legacy 私聊后缀要 `_context_workspace_enabled=False` 才走得到。文档里写的是「注入点四处」，真正有用的是 hearsay box + `gossip_records`，加一个 QQ preview。

**五，八卦不能触发主动说话。**`_compute_impulse`（里面有 pending gossip 加分）在主工作树**没有任何生产调用点**，只有 `test_daily_digest_quality.py` 调它。另外三个 worktree 里还有调用者，说明那次接线没回到主线：代码在，没人按开关。

## 我现在按天盯的几个数

这四个比率才是这条链路的体温：

```text
hop>=1 的 delivered >= 1 条/活跃日        （现在 1-11）
hop>=1 delivered / hop>=1 created >= 70% （分层之前是 58%）
hop=0  delivered / 总 delivered <= 70%   （现在 81%，公告不该一直压过真八卦）
mailbox_attempt.detail.content_dedup_skipped > 0
   长期为 0 但 shared_info 还是出现同文本多行 = 去重失效了
```

最后那个我觉得最有用：**它把「去重到底有没有在干活」变成了一眼能看出来的信号，而不是需要读代码才能确认的实现细节。**

跑一遍验证：

```bash
py -X utf8 -m pytest test_gossip_runtime.py test_gossip_prompt_arrival.py -q
```

八套测试合跑的回归：569 passed + 114 subtests，1 failed，17 分 47 秒。那一个红的跟这次改动无关：测试把 builder 换成了 MagicMock，实现里打日志要取 `__name__`，HEAD 上就红，是「改了实现没改测试」的旧账。

## 我想记住的四句话

1. 先把「什么叫成功」写成一句能测的话，再去建监控。我前面两周测的是自己猜的因果。
2. 一定要把「模型没产出」和「产出了被我拦了」分成两个计数器。一张日汇总表省下的争论时间比它值钱。
3. 低价值高流量的东西会饿死高价值低流量的东西，这不是概率问题，是排队问题。解法是分层留槽，而且关键那一层要有下限。
4. 每条测试都要用变异验一次能不能变红。没做这一步，你不知道它是检测器还是装饰。
