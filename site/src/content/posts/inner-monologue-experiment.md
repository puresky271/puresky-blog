先说结局：我花了 255 次生成，把爱音的沉浸式推理遵循率从 1/5 拉到 49/50。结果当天晚上就发现，那个让我最得意的开关会把 2.6% 的轮次变成空回复。同一个晚上，我把那两行提示词删掉了。

下面是完整过程。

## 我在纠结什么

我这个项目里角色用的是有显式推理通道的模型，返回值里有个 `reasoning_content`。我对这个通道有个不太实用的期待：**我希望她是「以角色第一人称在心里想」，而不是「以编辑的身份在打草稿」。**

两种形态长得很不一样。沉浸的那种是括号里的内心独白；编辑器式的那种是一堆字数统计、草稿枚举、模板自检，我管它叫元规划。之所以在意这个，是因为独白式推理往往伴随更自然的情感表达，而元规划出来的回复结构稳但僵。

而且这里有个很尴尬的前提：**生产的回复链根本不读 `reasoning_content`。**它是从 `message.content` 取正文、把里面的 `<think>` 标签块剥掉。也就是说我想影响的那个东西，用户一个字都看不见。我做的是一件纯粹通过改变「她怎么想」来改变「她怎么说」的事。

## 社区已经有一份答案，但它面向的场景跟我的差了十万八千里

victorchen96 那个 `deepseek_v4_rolepaly_instruct`（两千多 star）是这个领域被参考得最多的方案。它给了三条结论：

1. 控制标记要追加到**首条用户消息末尾**，不要放系统提示，因为那是模型的训练时注入位置；
2. 触发是**概率性**的，作者自己说「目前无法做到 100% 触发」；
3. 有一个没经过专门训练的技巧：强制思考块以指定字符串开头，「改变推理起始 token 来把模型切进另一个 pattern」。作者管这个叫**纯抽奖**。

问题是这套讨论都是短对话场景。我的单次请求里装着：角色人格卡、历史对话回顾、当前状态权威帧、对话对象状态、记忆召回工作区、认知工作区、这一轮的执行包。实测系统提示约 **51000 字符**。

在这个规模下，原来那个「放系统提示」的做法已经明显失效：模型的推理大量退化成字数统计和草稿枚举。GitHub 上有人报过同样的现象：「如果人设比较长并且塞了很多记忆，似乎就只有第一条 user 生效」。

我想知道的是：**失效到什么程度，哪个因素贡献多少，以及最好的组合是什么。**所以我做了 255 次生成。

## 实验是怎么搭的

我不想要一个玩具环境，所以基础输入直接用**生产实际构建出来的那组消息数组**，包括约 51000 字符的系统提示（含角色沉浸那块）、当前状态权威帧、记忆召回工作区、用户消息和带本轮长度预算的执行包。

固定场景：爱音，用户输入「我爱你」，模拟时间 2026-09-14 12:30 JST。午休时段，她正在天台跟另一个角色一起吃午饭。选这个场景是因为它同时有情感表达、社交在场感、和其他角色共处，对「是否会进入角色内心独白」这件事比较有代表性。

生成参数跟生产一致：deepseek-flash，温度 0.92，`max_tokens` 1620（角色基础预算 120 + 推理预算 1500），thinking 开，`reasoning_effort=high`。

### 三个自变量

- **注入位置**（三档）：`system-only`（只放系统提示末尾，我原来的生产配置）/ `system+user`（系统提示保留，同时在当前轮用户消息末尾追加一份镜像块）/ `user-only`（从系统提示里拿掉，只在用户消息末尾注入）
- **指令措辞**（两档）：**通道绑定**（原版：「在你的思考过程（`<think>`标签内）中，请遵守以下规则……」）/ **通道中性**（改写版：「在你的内部思考过程中（无论其以何种形式呈现），请遵守以下规则……」）
- **思考起始契约**（两档）：无 / 有（要求推理必须以指定标记 `（心想：` 严格开头，且这个标记不得出现在回复正文里）

通道这一维是我自己加的假设。模型实际用的是原生 `reasoning_content`，而我的指令在指着一个 `<think>` 标签：**指令指向的通道和模型真正用的通道不是一个东西**，我认为这本身就是一个独立的失效原因。

### 七个组

| 组      | 变量组合                             | 轮次 | 目的                       |
| ------- | ------------------------------------ | ---- | -------------------------- |
| E1      | 通道绑定 × 三种注入位置              | 5×3  | 建基线，验「注入位置」假设 |
| E2 / E3 | 通道中性 × system+user / × user-only | 5+5  | 验「通道措辞」假设         |
| E4      | 通道中性 × system+user               | 20   | 稳定性                     |
| E5      | 四种触发策略对比                     | 10×4 | 挑最好的机制               |
| E6      | 最优策略，无补丁                     | 40   | 大样本 + 暴露副作用        |
| E7      | 最优策略，加正文禁区补丁             | 40   | 验证缓解                   |

所有组共用同一份基础消息数组、同样参数，**组间交错执行**，为了不让后面那几组赶上服务端时间漂移。

## 有个方法学错误我先犯了，然后改掉了

早期我把「推理字段的统计结果」当成「用户体验的指标」。这是错的，因为前面说过 `reasoning_content` 在生产里被完整丢弃。

> [!IMPORTANT]
> 分开统计之后我才看清：推理形态和用户可见质量是两个独立维度，必须两条列分开记。

最终指标（全部按生产实际的取值路径统计，不是按模型返回的所有字段）：

| 指标           | 怎么算                                   |
| -------------- | ---------------------------------------- |
| 推理遵循率     | 推理文本里括号式独白段占比 ≥ 50%         |
| 起始契约遵循率 | 推理以 `（心想：` 开头（只对契约组适用） |
| 推理长度       | `reasoning_content` 字符数               |
| 输出开销       | `completion_tokens`                      |
| 正文泄漏       | 最终展示的文本里含括号独白               |
| 空回复率       | 最终展示的文本为空                       |

后面你会看到，「分开记」这件事救了我不止一次。

## 结果

### 注入位置（E1）

在通道绑定的措辞下：

| 注入位置                    |  遵循率 | 推理长度 | 输出开销 |
| --------------------------- | ------: | -------: | -------: |
| system-only（我原来的配置） | **1/5** |      768 |      493 |
| system+user                 |     3/5 |      606 |      399 |
| user-only                   |     4/5 |      313 |      228 |

系统提示单独注入只有 20% 的遵循率，**而且它的推理最长、开销最大**：模型在没有被有效引导的时候，转而去做冗长的自我规划。把指令搬到当前轮的用户消息末尾，遵循率和成本同时改善。

到这里我以为结论就是「搬到 user 就行」。

### 措辞（E2、E3）：一个反直觉的交互

| 配置               |  遵循率 | 正文泄漏 | 推理长度 | 开销 |
| ------------------ | ------: | -------: | -------: | ---: |
| system+user + 中性 | **5/5** |        0 |      306 |  213 |
| user-only + 中性   |     3/5 |        2 |      589 |  392 |

**把系统提示里那份删掉，反而退化了。**通道中性化在「保留系统侧那一份」的时候是最好的（5/5、零泄漏、开销降到基线的 43%），在 user-only 下变成 3/5，还出现两例正文泄漏。

我现在的解释是：系统侧那个块提供的注意力锚点，对稳定性有独立的贡献。它不需要被「读得很准」，它只需要在那儿。**双点注入 > 单点注入，哪怕单点那个是「训练时正确位置」。**这直接跟社区方案的建议相反。

### 稳定性（E4）：5/5 是假的

把最好的配置扩到 20 轮：

- 遵循率 **17/20（85%）**
- 正文泄漏 0，空回复 0
- 平均推理长度 392 字符，开销 277 tokens

85% 说明它是**一个高概率倾向，不是一条稳定契约**。

而且这里出现了「分开记」的第一次救命：那 3 例没遵循的样本，推理膨胀到 1468 字符（里面有 13 次草稿迭代），看起来惨不忍睹。**但它们的可见回复质量全部正常**，长度合规、零泄漏。

如果我把推理字段的统计当成用户体验指标，我会为了修这 3 例去做完全没有必要的优化。

### 触发机制对比（E5）：四种策略各 10 轮

| 策略          | 描述                               | 契约遵循率 | 正文泄漏 | 推理长度 | 开销 |
| ------------- | ---------------------------------- | ---------: | -------: | -------: | ---: |
| D1 起始契约   | 双点注入 + 要求以 `（心想：` 开头  |  **10/10** |        2 |      255 |  202 |
| D2 示例引导   | 双点注入 + 给 3 行独白示例         |       7/10 |        1 |      725 |  479 |
| D3 全叠加     | 规则 + 示例 + 契约                 |      10/10 |    **8** |      158 |  166 |
| D4 社区原教旨 | 删掉系统块，纯文本指令挂 user 末尾 |       9/10 |        2 |      476 |  331 |

四条结论：

**一，起始契约真的有效。**D1 和 D3 都是 10/10，验证了社区关于「改推理起始形态能切模式」的观察。而且我要澄清一件事：那个社区方案里提到的特殊 token 标记，**在我这 255 次生成里一次都没有出现过**。它是模型端的特殊 token，纯文本指令复现不了。真正起作用的不是那个 token，是**「强制指定推理从哪里开始」这个约束本身**。

**二，叠加越多越糟。**D3 开销最低（166），但**泄漏率 8/10**。规则 + 示例 + 契约三重叠加，反而诱发模型在正文里「表演」它在思考。

**三，单契约最好。**D1 在遵循率持平的前提下泄漏更低（2/10），也不需要示例带来的额外提示长度。

**四，社区原教旨配置在我这里不是最优。**D4（只 user 注入）9/10、推理 476 字符，都比「双点 + 契约」差。

### 大样本（E6，40 轮）：副作用露头

- 契约遵循率 **39/40（97.5%）**
- 但暴露了 2 例正文泄漏 + 1 例空回复，**三者同源**

机制是这样的：起始契约有大约 7.5% 的概率让模型把**整条回复**写成纯括号独白，一句台词都没有。这段文本进我的清洗链，括号内容被全部剥掉，正文变空；然后触发我那条「宁可保留旁白也绝不发空消息」的安全网，**它把原始的推理文本原样放出去了。**用户会看到她的完整内心思考。

这个失效形态在 E1 到 E4（没有契约的四组）里**一次都没出现过**。它是我这个机制自己引入的。

顺便说，那条安全网是我的锅。它设计的初衷是防空消息，但它没有区分「清洗后空的」和「因为整条都是内部思考所以空的」。一个兜底机制在正确的意图下制造了最糟的泄漏，这是我最不想写进文章但必须写的一段。

### 缓解（E7，加一条正文禁区，40 轮）

我在契约里追加了：

> `（心想：`只出现在你的内部思考中，绝不要出现在回复正文里；回复正文必须是直接对……说的台词，不要以括号开头。

| 指标       | E6（无补丁） | E7（有补丁） |
| ---------- | -----------: | -----------: |
| 契约遵循率 |        39/40 |        39/40 |
| 正文泄漏   |            2 |        **1** |
| 空回复     |            1 |        **0** |
| 推理长度   |          327 |          398 |
| 开销       |          239 |          280 |

**空回复归零了，但我不能声称根除了。**补丁的代价是推理长度和开销都涨约 17%（禁令语句本身增加了推理负担）。而且 40 轮样本下，1 例和 2 例的差别完全在统计噪声里。

所以我没有停在这里等它自己变好，加了请求侧的两道防御：

- **纯独白检测 + 重试**：在正文清洗**之前**判断这一条是不是纯括号独白。判据是**把所有括号段剥掉之后一个字符都不剩，且至少存在一个括号段**。命中就重试一次生成；重试成功用新结果，失败进兜底。
- **空回复兜底**：清洗后正文为空的话，回填**角色专属**的最短安全占位文本。保证永远不发空消息，也永远不放行推理文本。

检测器是拿真实泄漏样本校准出来的，它明确排除了两种合法写法：独白里夹台词、台词里夹括号补白（后者是角色语料的正常写法，很容易误判）。

## 成本这块是我最初没打算讲、但其实最实在的

以原来的生产配置（system-only + 通道绑定）为基准：

| 配置                | 输出开销 | 相对基准 |
| ------------------- | -------: | -------: |
| system-only（基准） |      493 |        — |
| system+user + 中性  |      277 | **−44%** |
| D1 起始契约         |      239 | **−52%** |
| D1P 契约 + 补丁     |      280 |     −43% |

遵循率从 20% 到 98%，同时单轮输出 token 少了将近一半。这不是我特意优化的结果，它更像是**模型不用再自己打草稿了**：推理长度从 768 掉到 255，元规划省下来的就是钱。

## 然后同一晚我把契约删了

这部分是文章真正的结尾。

做完 255 次实验的当天晚些时候，我跑了一轮全链路排查，发现起始契约**还有一个更隐蔽的失效形态**：偶发地，整轮的 token 全部停在 reasoning 通道，`finish_reason=stop`，`content` 是空的。生产上出现率约 **2.6%**，同一个 prompt 重放里 3/116。

它比 E6 那个 7.5% 更难被发现：7.5% 那个至少还有文本，只是被剥空了；这个是从一开始就没有正文，于是我前面一步的兜底把它接成了空回复罐头句。**当天爱音两次对用户说了罐头句。**

我当天定了：把起始契约那两行从生产尾块删掉，三条规则和正文守卫保留。

删之前我不敢直接删，跑了四臂对照（表白轮 × 5）。结果是：**删掉之后，思考仍有 3/5 是自己以 `（心想：` 开头的**，正文零泄漏，记忆接地不受影响。剩下的空正文形态由质量链的请求侧重试承接（`[QC.empty-retry]`，关掉 thinking + 抬预算，工具轮跳过）。

所以那个 98% 现在应该这样读：**「契约开启的时候」是 49/50。当前生产形态下，思考的起手式是自发行为，不是被逼出来的。**

## 从这件事里我真正学到的三条

1. **小样本会骗你三次。**5 轮的时候我看到 5/5 完美遵循；20 轮降到 85%；40 轮才第一次暴露出「整条回复变成纯独白」这个此前完全看不见的失效形态。**每一轮扩样本都不是在提高精度，是在换一种盲区。**尾部行为只有样本量能够到它的时候才存在。
2. **「用约束换确定性」这笔交易在尾部会付双倍。**我把遵循率从 85% 提到 98%，代价是引入两个此前不存在的失效模式（7.5% 的思考泄漏、2.6% 的空正文）。而后者比前者更糟：它绕过了我全部的兜底假设，因为我原来的兜底假设是「至少 content 有东西」。
3. **可见质量和内部形态必须两条列分开记。**这条我犯了错才学会。E4 里那三例推理彻底跑偏、可见回复全绿的样本，如果我按「推理字段 = 体验」来排优先级，我会把整周花在无关的地方。

我并没有得到一个「更好的角色」。我得到的是一个更贵、更容易崩的中间版本，和一条现在还在生产的规矩：

> [!WARNING]
> 不要用提示词去逼模型的回答开头长什么样，尤其是当你没法为它的失效写一个兜底的时候。

## 几个我明说没解决的东西

- **单角色单场景。**我只测了爱音的「我爱你」，五个人语气差别很大，我没覆盖。
- **98% 的置信区间很宽。**50 轮样本，只有点估计，我没算区间，更没做显著性检验。D1 vs D4 那 10 轮对比更是纯粹的方向性观察。
- **强模型版本依赖。**社区报的那个失效本身就是模型版本更新带来的。我这套结论换个模型日期可能全变，这也是为什么我倾向于把它当「实验记录」而不是「最佳实践」来读。
- **我只验证了有效，没解释原理。**「强制指定推理起始形态能切换模式」这件事我复现了，但我给不出机制层面的解释。

> [!TIP]
> 如果你想在自己的项目上重做这套实验，需要准备的东西只有三样：一份从生产抓的真实 messages 数组（别手写）、一个能反复调用又不脏状态的入口，以及把 `reasoning_content` 和最终展示文本分成两列记录的日志格式。
