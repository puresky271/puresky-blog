记忆系统的召回打分有九个通道，其中 lexical 权重 0.30，是单个权重最高的一路。某次例行回归发现 canon 事实的召回率从 90% 掉到 80%，而那一周我没碰过检索代码。

查到最后不是算法问题：生产进程跑在另一个 Python 解释器上，那里没装 `jieba`，lexical 通道一直在静默地按字切。装上依赖只修好了这一次，真正要修的是那条不出声的 fallback，以及一个对单通道失效不敏感的评测。

## 症状

召回评测跑下来，掉的都是同一类：需要词面匹配的短事实。语义相近但用词不同的那些没受影响，说明 embedding 通道正常。掉的全是「问句和记忆里用的是同一批词，但顺序和虚词不一样」这种，典型的 lexical 通道失效特征。

lexical 的实现靠 `jieba` 做中文分词。加了一行日志才看到：

```text
jieba import failed, falling back to character-level split
```

这条 fallback 在设计时是对的：分词库挂了，不该让整个召回崩掉。问题是它太安静了。日志级别是 debug，而且退化到按字切之后，lexical 通道仍然会返回分数，只是那个分数不再有意义。系统「能跑」，所以没人发现。

## 真正的原因：两个解释器

本机有两个 Python 解释器。开发时我在 `.venv` 里跑测试，`jieba` 装在里面；生产进程用的是系统的 `py`（3.14），那里没装。

这个差异一直存在，只是之前无所谓：之前 lexical 通道的权重没这么高，掉一点召回被其他通道盖过去了。权重调到 0.30 之后它就露出来了。

> [!CAUTION]
> 这类 bug 的麻烦在于它不是「代码写错了」，而是「代码在两个环境里行为不同，而只有一个环境有测试覆盖」。修好 `jieba` 只解决今天这一次，下次换成另一个可选依赖还会再来一遍。

## 修法：让退化看得见

装上 `jieba` 只是第一步，真正要修的是那条静默 fallback。改了三处。

### 启动时显式检查关键依赖

不是 import 时 try/except 就算了，而是在进程启动阶段跑一次依赖自检，缺了就打 error 级日志，并在健康检查里标出来。可选依赖仍然可选，但「它缺了」这件事必须可见。

### 退化时给通道打标记

lexical 通道退化到按字切之后，在返回的打分结构里带一个 `degraded: true`。上层做加权时看到这个标记，就把该通道的权重折掉，而不是拿一个无意义的分数当正常分数用。

### 回归评测里加一条哨兵

专门测一个只有靠分词才能召回的事实。之前的评测看的是总体召回率，10% 的下降会被当成正常波动；现在这条哨兵挂了就是挂了，没有波动空间。

## 聚合指标看不见单通道失效

第三条其实是最有价值的那条，但它不是从这个 bug 直接推出来的。

总体召回率这种聚合指标有个通病：它对「某一路完全失效」不敏感。九个通道里挂掉一路，剩下八路会把总分托住，指标只掉一点，看起来像噪声。

> [!TIP]
> 要发现单通道失效，得有针对单通道的探针。现在每一路都有一条哨兵事实，构造成只有那一路能召回它。九条哨兵跑一遍，哪一路死了立刻知道，这比看总体召回率有用得多。
