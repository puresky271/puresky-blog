## 什么是GitHub CLI
GitHub CLI（`gh`）是 GitHub 官方出品的命令行工具，让你无需离开终端就能操作 GitHub，包括创建仓库、管理 issue、提交 PR、查看代码等。

[官方仓库入口](https://github.com/cli/cli)

GitHub CLI 的起点，是把 GitHub 上常见的协作流程带进终端。2020 年 2 月，GitHub 发布了 `gh` 的公开 Beta，最初重点放在 Issue 和 Pull Request 上，希望开发者少在终端与网页之间来回切换。[官方 Beta 公告](https://github.blog/news-insights/product-news/supercharge-your-command-line-experience-github-cli-is-now-in-beta/)

同年 9 月，GitHub CLI 1.0 正式结束 Beta；GitHub 当时称，测试期间用户已用它创建超过 25 万个 PR、完成超过 35 万次合并，并创建超过 2 万个 Issue。2021 年 8 月发布的 2.0 又加入扩展机制，开发者可以创建、安装和分享自定义 `gh` 命令。它的演进路线也由此清晰起来：先覆盖常见协作流程，再让团队和社区按自己的工作方式继续扩展。[1.0 发布公告](https://github.blog/2020-09-17-github-cli-1-0-is-now-available/) · [2.0 与扩展机制](https://github.blog/news-insights/product-news/github-cli-2-0-includes-extensions/)

与传统的 `git` 命令不同，`gh` 是针对 GitHub 平台本身的高层操作，它简化了很多重复的操作，大幅提升开发效率。

一个直观的例子是，假设你要新建一个在github上的公开仓库并且创建首次提交，在传统方式下，你的操作可能是：

```bash
# 创建本地仓库、推送代码
git init
git add .
git commit -m "init"
# 然后要去 GitHub 网页上手动创建远程仓库，复制地址
git remote add origin https://github.com/user/repo.git
git push -u origin main

```
GitHub CLI 方式：

```bash
# 一个命令直接创建远程仓库并推送
gh repo create my-repo --source=. --remote=origin --push

```
哦我的天啊，一行命令直接搞定了，你甚至不用去github上新建一个仓库，所有事都在命令行搞定。

---

常见问题

Q：GitHub CLI 和 Git 的区别是什么？

A：git 是版本控制工具，管理代码的版本历史。gh 是 GitHub 平台工具，管理仓库、issue、PR 等平台功能。两者互补，不冲突。

Q：gh 能替代 git 吗？

A：不能。git 是必需的，gh 是增强。你还是要用 `git add/commit/push`，gh 只是让平台操作更快。

Q：安全吗？密码会泄露吗？

A：完全安全。gh 用 `OAuth` 认证，密码永远不会输入到命令行，认证信息存在系统密钥链里（macOS 是 Keychain）。

Q：能在脚本里用 gh 吗？

A：可以。gh 支持` --json` 输出，方便在 CI/CD 里集成。

## 安装，登录和验证
macOS

```bash
brew install gh

```
Linux

```bash
# Ubuntu / Debian
sudo apt-get install gh

# Fedora / RHEL
sudo dnf install gh

# Arch Linux
sudo pacman -S github-cli

```
Windows

```bash
choco install gh
# 或者
scoop install gh

```
快速验证版本

```bash
gh --version
# 输出：gh version 2.x.x

```
---
安装完毕后，需要登录 GitHub 账户，gh 会用 OAuth 认证，完全不需要输入密码。
> [!tip]
> OAuth（Open Authorization，开放授权） 是一个关于授权（Authorization）的行业标准开放协议。
简单来说，它的核心作用是：**允许第三方应用在不获取用户账号密码的情况下，代表用户获得对其在另一服务上的某些资源的有限访问权限。**

```bash
gh auth login
```
按提示选择（下方答案仅作示例）：

```bash
? Where do you use GitHub?
> GitHub.com

? What is your preferred protocol for Git operations?
> HTTPS

? Authenticate Git with your GitHub credentials?
> Yes

? How would you like to authenticate GitHub CLI?
> Login with a web browser

```
最后一步会弹出浏览器，自动打开 GitHub 授权页面，点确认即可。登录成功后，后续所有 `gh `命令都会自动用你的身份。

```bash
gh auth status
# 输出你的用户名和权限信息

```

## 开发常用命令
这里我们就介绍一些最常用的命令

1. 创建新仓库

方式 A：直接创建远程仓库并推送本地代码
一个命令搞定：创建仓库、关联本地代码、推送到远程。

```bash
gh repo create customer-service-agent \
  --description "这是我的一个个人仓库" \
  --private \
  --source=. \
  --remote=origin \
  --push
```

方式 B：只创建空仓库（不推送代码）

```bash
gh repo create my-repo --private
```

2. 查看仓库信息

```bash
# 查看当前仓库详情
gh repo view

# 查看某个仓库
gh repo view owner/repo-name

# 查看仓库的 README（并在浏览器打开）
gh repo view owner/repo-name --web
```

 3.  管理 Issue

```bash
# 列出所有 open 的 issue
gh issue list

# 查看某个 issue 的详情
gh issue view 1

# 创建新 issue
gh issue create --title "修复登录 bug" --body "用户反馈..."

# 关闭 issue
gh issue close 1

# 添加标签
gh issue edit 1 --add-label "bug,urgent"
```

4.  提交和管理 PR

```bash
# 当前分支创建 PR（会自动打开编辑器让你写 PR 描述）
gh pr create --title "新增XX功能"

# 列出所有 PR
gh pr list

# 查看 PR 详情
gh pr view 5

# 在本地检出某个 PR 的代码
gh pr checkout 5

# 合并 PR
gh pr merge 5

# 关闭 PR
gh pr close 5
```

5. 代码审查

```bash
# 查看 PR 的改动
gh pr diff 5

# 添加评论
gh pr comment 5 --body "你的代码写的和豆包一样"

# 请求审查
gh pr review 5 --request-review @username
```

6.  查看工作流 / Actions 状态

```bash
# 列出所有 workflow runs
gh run list

# 查看某个 run 的详情
gh run view 12345

# 查看日志
gh run view 12345 --log
```

7.  克隆仓库

```bash
# 速度比 git clone 快，因为会自动用 SSH 或 HTTPS（取决于你的认证方式）
gh repo clone owner/repo-name

# 克隆到指定目录
gh repo clone owner/repo-name ~/my-projects/repo-name
```

8. 快速打开仓库网页

```bash
# 在浏览器打开当前仓库
gh repo view --web

# 打开 issue
gh issue view 1 --web

# 打开 PR
gh pr view 5 --web

```

[这里是GitHub CLI的官方的操作列表清单](https://cli.github.com/manual/gh)

## 让你的agent助手使用GitHub CLI
你大概见过ai使用GitHub CLI

想想看，如果你是一个使用ai辅助开发的人，你肯定有过要求ai替代你完成一些远端操作的经历，那么如果你没有安装好GitHub CLI，ai大概会说：

🤖：本机GitHub CLI不可用/未安装

此时agent就只能在传统的命令行界面里面笨笨的敲git命令了，但是一旦我们安装好GitHub CLI，你大概就会在agent的输出里面看到这样的前缀：

```shell
$ gh api
```
这就代表你的agent在使用本机的 `gh auth` 登录状态或 token，并通过 GitHub API 和 GitHub 服务通信
，命令结果回到了你的本地终端。

> [!WARNING]
> 请不要将GitHub CLI和你的ahent助手的Github插件混为一谈，它们可以配合使用，但不存在“GitHub 插件就是 GitHub CLI 的图形界面”这种关系。

下面我们就以codex为例，完整过一遍全流程

比如你对codex说：

> “帮我检查这个仓库的 PR #123，修复问题，跑测试，再把修复推上去。”

如果codex选择通过GitHub CLI，也就是 `gh`来完成，整个过程就是：**codex在终端调用 `gh` 获取 GitHub 信息，用本地文件工具修改代码，用测试命令验证，再用 `git` 和 `gh` 把结果同步到 GitHub。**

### 1. 先判断当前环境和仓库

codex需要知道当前在哪个仓库、工作区有没有未提交修改，以及 `gh` 是否可用：

```powershell
git status --short
git remote -v
gh --version
gh auth status
```

这些命令分别回答：

- 本地有没有正在进行的修改，避免覆盖我们其他的工作。
- 当前仓库对应哪个 GitHub 地址。
- GitHub CLI 是否安装。
- `gh` 当前登录了哪个账号，以及认证是否有效。

这里需要特别注意的是：**codex 登录、`gh` 登录和 Git 的推送认证是不同层次。**你登录了 codex，不代表本机的 `gh` 自动拥有 GitHub 权限；`gh` 登录成功，也不保证 `git push` 使用的 SSH 或 HTTPS 认证已经配置好。

如果 `gh` 没有登录，通常需要完成：

```powershell
gh auth login
```

**请不要向agent展示你的token，这种步骤我们自己完成**

### 2. 把你的请求转换成具体的 GitHub 查询

“检查 PR #123”对模型来说是自然语言，对 `gh` 来说需要明确的命令和参数：

```powershell
gh pr view 123 --repo owner/repo `
  --json number,title,body,state,baseRefName,headRefName,url
```

这里的 `--repo owner/repo` 指定仓库，避免在项目目录不明确时查错地方。

`--json` 很有用，因为json最擅长的事情就是返回结构化数据，这能方便codex准确区分标题、正文、目标分支和来源分支。例如：

```json
{
  "number": 123,
  "title": "Fix login redirect",
  "state": "OPEN",
  "baseRefName": "main",
  "headRefName": "fix/login-redirect"
}
```

此时底层发生的事情大致是：

```text
生成 gh 命令
    ↓
codex 的终端工具启动本机 gh 进程
    ↓
gh 使用已有认证向 GitHub 发出 API 请求
    ↓
GitHub 检查权限并返回数据
    ↓
gh 将数据输出到终端
    ↓
终端工具把输出交给codex
    ↓
codex根据结果决定下一步
```

codex并不是直接“看见你的 GitHub 账号”，它得到的是工具返回的具体结果。命令失败或权限不足时，codex也只能根据返回的错误判断原因。

### 3. 读取修改、讨论和 CI 状态

接着，codex通常会读取：

```powershell
gh pr diff 123 --repo owner/repo
gh pr view 123 --repo owner/repo --comments
gh pr checks 123 --repo owner/repo
```

它们提供三个不同角度：

| 命令 | 获取什么 | 为什么需要 |
|---|---|---|
| `gh pr diff` | PR 修改的代码 | 找出具体改动 |
| `gh pr view --comments` | PR 信息及讨论评论 | 理解需求和已有讨论 |
| `gh pr checks` | 关联的检查状态 | 判断测试或构建是否失败 |

如果 CI 失败，codex还可以进一步查看对应运行：

```powershell
gh run view RUN_ID --repo owner/repo --log-failed
```

使用gh命令，你可以直接让你的agent助手读取日志以当作诊断材料。例如它可能表明失败来自测试断言、缺少依赖或权限配置。当然，**`gh` 能取得完整数据，不代表模型每次都能完整收到：终端输出可能被截断。**

>[!tip]
> 将log展示给你的agent助手是一个很好的习惯，不管你通过何种方式。

### 4. 将 PR 代码放到可操作的本地目录

如果需要修改或跑测试，只有 GitHub 上的 diff 通常不够，需要本地 checkout。

在适合切换分支的干净工作区中，可以使用：

```powershell
gh pr checkout 123
```

**`gh` 不只调用 GitHub API，也能编排本地 Git 操作。**它会取得 PR 分支信息，并使用 Git 完成获取代码、切换分支等动作。

### 5. 分析问题、编辑文件、运行测试

这一阶段就是agent自己干的活了，和GitHub CLI一般没关系，我们跳过。

恭喜你，codex向你报告：**测试全过！**

### 6. 提交并推送修复

首先codex会先确认最终 diff，然后执行类似：

```powershell
git add path/to/changed-file
git commit -m "Fix login redirect handling"
git push
```

这一步主要是Git，不是 GitHub CLI，这就很像我们人工的开发流程了：先将你的改动提交到本地仓库，然后push到远端。

| 工具 | 主要操作对象 |
|---|---|
| `git` | 文件版本、提交、分支、远程代码同步 |
| `gh` | GitHub 上的 PR、Issue、Review、Actions、Release 等对象 |

已有 PR 的来源分支收到新提交后，GitHub 会更新这个 PR，一般不用再创建一个新的 PR。

### 7. 按请求发布 PR 或评论

如果任务是创建新 PR，codex可以用：

```powershell
gh pr create `
  --title "Fix login redirect handling" `
  --body-file work/pr-body.md `
  --base main
```

PR 描述会交代问题、修复后的行为，以及验证结果。

使用 `--body-file` 可以保存准确的多行正文，减少 PowerShell 转义问题。尤其是含有代码片段、引号和换行的文本，文件输入通常更稳妥。

**这些命令会改变 GitHub 上的状态。**本地写好评论文件还没有发布；执行 `gh pr comment` 才会把内容发出去。

### 8. 验证 GitHub 实际收到结果

推送或创建 PR 后，codex会检查远端结果：

```powershell
gh pr view 123 --json url,headRefOid
gh pr checks 123
```

必要时，把 GitHub 返回的分支提交 SHA 和本地提交对照：

```powershell
git rev-parse HEAD
```

codex需要区分三个状态：

- 本地测试通过。
- 提交已成功推送。
- GitHub CI 已运行完成并通过。

它们不能互相替代。比如推送成功后，CI 可能仍在排队，codex就应该如实报告“已推送，CI 尚未完成”。

最终codex会给我们 PR 链接、改动说明和验证结果，完事。

## GitHub CLI对你意味着什么
我在和很多新手开发者交流的时候，一个非常让我红温的点就是很多人只把git的一系列操作当成是IDE（如vscode）上的一系列的魔法按钮，而不愿意去深入了解git的底层原理，不愿意去不那么方便且好看的CLI界面里面敲上几行命令，甚至不知道`.git`是什么。

GUI尚且会让人如此懒惰，更别提能和agent助手结合的GitHub CLI了，回看我们上述展示的所有操作，一切的命令都是如此的美观，一切的过程在agent的`Re-Act`流程下都是那么的严丝合缝。ai最擅长的事情之一就是敲命令行，人来敲命令会因为各种各样的原因出错，但是GUI不会出错（前提是你正确操作），看过巨量相关的预训练语料的ai更不太可能会。

GitHub CLI是轮椅，比如codex更是轮椅，如果两个结合起来——我去，强强？？

但是很多时候事情不会那么简单，不是吗。事实证明在人类的历史上，**一切自动化的系统都是需要一个人的把控环节的**。我的观点是：

- 还要不要去记住那些繁琐的git命令——可能不太要了，但基本的依旧要记牢，不然你连描述需求都得用自然语言。
- 还要不要全程参与版本管理的流程——**要！**
> [!warning]
> **在一切关于git的操作中，你使用纯自然语言和AI交互都可能带来毁灭性的后果。**

  一个ai因为GitHub CLI越界的经典例子就是，**你只要求分析，ai却公开评论；你只要求修复，ai直接合并；一次推送触发生产部署。**

agent的这些操作是逐级叠加的：

```text
本地改文件 → 提交 → 推送 → 发布评论或 PR → 合并 → 发布版本
```

一次 `git push` 也可能触发部署、包发布或其他 Actions。创建标签、Release 或执行 workflow，可能直接影响生产系统。

更糟糕的是：**`gh` 不只有 `gh pr`。它还有通用 API 入口：`gh api` **。在凭据权限允许时，它可以操作很多仓库和组织设置。**但只允许调用 gh，并不等于只允许查看 PR。**如果没有参数级限制，这个可执行程序的权限范围很广。

可能的事故：
- 删除仓库或 Release。
- 修改仓库可见性，公开私有代码。
- 关闭分支保护或调整 Actions 权限。
- 增加协作者、修改访问权限。
- 利用管理员能力绕过部分合并要求。

## 写在最后

我上面的这些话吓到你了吗？好吧不好意思啦，我平时也是一个非常依赖GitHub CLI的懒人。

但我还是想说，GitHub CLI真正改变的，是人与 GitHub 交互的入口：许多原本需要在网页上逐步完成的操作，现在可以被压缩成可复用、可审查的命令。它和 agent 结合后，效率会进一步提高，但命令背后的权限和影响范围也不会因此缩小。**把 `gh` 当成一把更顺手的工具，同时保留对权限、参数和最终结果的确认，才能让自动化带来便利，而不是把一次误操作变成线上事故。**

现在，去**享受工具本身**吧，如果你觉得GitHub CLI确实是一个不赖的轮椅，也可以去给它的开发组一颗星星哦。
