你是一个负责的开发者，正在维护一个不大不小的项目，你大概会在发版前先在本地把测试跑一遍，再手工打一次包，传到服务器，然后 SSH 进去重新部署。但是人做重复的事一定会出错：忘了跑某个测试、漏传了一份文件、部署到一半网络断了，等等等等。

所以看起来，最好不要将这个环节全部交给你自己来做，对吗？什么是高效且稳定，重复一万次结果也一模一样的呢——代码。GitHub Actions是GitHub推出的持续集成`（CI/CD）`服务，于 2018 年 10 月推出。它允许开发者在 GitHub 仓库中直接自动化软件开发工作流程。不依赖你本地环境，只用一份` YAML` 文件定义流程，push 代码的瞬间任务就在 GitHub 的服务器上跑起来。

## GitHub Actions能帮你做什么
就像我们上文所提到的：你每次push代码之后，想自动跑一遍测试；每次打个tag，想自动生成一份release notes；每隔一段时间想把线上数据抓下来存到仓库里做分析。这些事情单独看都不难，难在“每次都记得做”。

而GitHub Actions解决的就是这个“记得”的问题。你定义好触发条件，剩下的交给它：往`main`分支推代码就跑测试，提PR就做静态检查，定时任务到点就执行，打tag就自动发版。

一旦你将这些放进GitHub Actions，你便将这些流程变成了你的仓库的一部分，任何人checkout代码，都能看到`.github/workflows/ `里躺着什么任务——你不再需要口头让别人或自己遵守什么规矩，代码里写的明明白白，让自动化流程帮你把关。

> [!IMPORTANT]
> 别觉得自己的个人项目就没必要上Actions，它不仅方便，生态完整，而且一个好的，全绿的Actions比任何纸面漂亮的README都要更有说服力。


## GitHub Actions的各种概念
- `Workflow` ：一份`.yml` 配置文件，放在`.github/workflows/` 目录下。它定义“什么时候开始干活”和“具体干什么活”。
- `Event` ：触发 Workflow 的事件。最常见的push 、 pull_request ，还有手动触发 workflow_dispatch 、定时触发 schedule 。
- `Job` ：Workflow 里的一个执行单元。一个 Workflow 可以有多个 Job，默认情况下它们在各自的 runner 上并行跑。
- `Step` ：Job 里的具体动作。一个 Step 可以是一条 shell 命令，也可以是一个 Action。
- `Runner` ：真正干活的机器。通常用 GitHub 托管的 ubuntu-latest ，也可以用 Windows、macOS，甚至你自己维护的自托管机器。
- `Action` ：别人封装好的“积木”。比如` actions/checkout@v7` 负责把代码拉下来， `actions/setup-node@v7` 负责装 Node.js。你不用自己写全套命令，直接 uses 就行。

## 从0写出你的第一个GitHub Actions
你需要将你的工作流文件放在仓库根目录下的`.github/workflows/`里，文件名随意，`.yml` 和`.yaml` 后缀都行。一个仓库可以放多个文件，GitHub 会全部识别。

> [!TIP]
> YAML 是一种直观的、主要面向人类可读的**数据序列化语言（Data Serialization Language）**。
它的全称最初是 Yet Another Markup Language（又一种标记语言），后来改为递归缩写 “YAML Ain't Markup Language”（YAML 不是标记语言），以此强调它专注于数据表示，而不是像 HTML/XML 那样用于文档标记。

（你还不会写YAML吗？那就去花一小些时间了解一下吧！）

### 简要介绍一些在编写CI/CD时需要遵守的YAML的语法规范：

#### 一、 核心基础语法规范

1. **严禁使用 Tab 键，只用空格**
   * YAML 严格禁止使用制表符（`\t`）。在编辑器中务必将 Tab 设为转换为 **2 个空格**。
   * 缩进必须对齐，**同一层级的子属性必须保持相同的空格数。**
2. **符号后必须跟空格**
   * **冒号 `:`**：键与值之间冒号后**必须有一个空格**（写成 `key:value` 是错的，应为 `key: value`）。
   * **连字符 `-`**：列表项（如各个 step 或 stages）的 `-` 后面**必须有空格**（如 `- run: npm test`）。
3. **大小写严格敏感**
   * 键名和值都是大小写敏感的。平台定义的关键字（如 `jobs`、`steps`、`script`）不能写错大小写。

#### 二、 CI/CD 场景极高频的特定语法

##### 1. 多行脚本（Run Shell）的书写：`|` 与 `>`
在 CI/CD 中，经常需要连续执行多行 Bash/PowerShell 命令，必须熟练使用这两个折叠符号：
* **`|`（保留换行）——最常用**：每一行都是独立的命令，换行会被忠实保留。
  ```yaml
  - name: Build and test
    # `|` 保留换行，下面每行都是一条 shell 命令
    run: |
      npm install
      npm run build
      npm test
  ```
* **`>`（折叠换行）**：多行内容会被合并成一行，中间用空格隔开。适合写超长的一行命令或描述。

#### 三、字符串必须加引号的“四大陷阱”
CI/CD 中经常出现“语法看着没错，但解析出来完全不对”的情况，通常是因为没有给字符串加引号：

* **陷阱 1：CI/CD 表达式与花括号 `{}`**
  在 GitHub Actions 中，表达式如 `${{ secrets.TOKEN }}` 以 `{` 开头，YAML 会误以为这是内联对象，导致解析错误。
  * ❌ 错误：`env_var: ${{ secrets.TOKEN }}` （若放在特定位置可能报错）
  *  正确：`env_var: "${{ secrets.TOKEN }}"`
* **陷阱 2：版本号被解析为浮点数**
  * ❌ 错误：`node-version: 18.10`（会被 YAML 解析成浮点数 `18.1`，直接丢失最后的 0）
  *  正确：`node-version: "18.10"`
* **陷阱 3：布尔值关键词（挪威问题）**
  `yes`, `no`, `true`, `false`, `on`, `off` 会被自动识别为布尔值。
  * 例如国家代码挪威 `NO` 会变成 `false`；GitHub Actions 的触发器关键字如果直接写 `on:`，在较旧的 YAML 规范中容易与布尔冲突，建议或必须按平台文档规范编写。
* **陷阱 4：包含特殊字符开头**
  如果字符串以 `@`、`*`、`&`、`!`、`?`、`%` 等特殊字符开头，**必须加单/双引号**。

#### 四、 怎么尽量少踩坑

1. **区分标量、对象与列表的结构：**
   * CI 平台通常对结构有极强校验。例如：
     ```yaml
     # jobs 下是字典/映射（Map）
     jobs:
       build:
         # steps 下是数组/列表（List），每个步骤必须以 - 开头
         steps:
            # uses 调用现成的 Action，把仓库代码检出到 runner
           - uses: actions/checkout@v4
            # run 在 runner 上执行 shell 命令
           - run: npm test
     ```
2. **利用 IDE 插件与 Schema 校验：**
   * 在 VS Code 中安装 **YAML (by Red Hat)** 插件。
   * 现代 CI/CD 文件顶部可以通过添加`JSON Schema` 声明来获得实时的自动补全和语法报错提示。
3. **提交前先做 Linter 验证：**
   * 使用 `yamllint` 检查格式；
   * 使用平台专用的验证工具（如 GitHub Actions 的 `actionlint`、GitLab 的 CI Lint 网页工具）。

### name：工作流名称
任何东西都得有名字，所以我们也在第一行给你的workflow来写一个`name`：

```yaml
# 工作流显示在 Actions 页面上的名称
name: CI

```
在仓库的 Actions 页面上，GitHub 会用 `name` 显示工作流名称。它是给这份配置起的名字；`run-name` 则可以另外设置某一次运行的名称。

### on：触发事件
`on` 字段决定工作流由什么事件触发。它相当于工作流的启动条件：只有匹配到这里配置的事件，GitHub 才会运行后续的 Job。

下面这个例子配置了三种常见的触发方式：

```yaml
on:
  # 向 main 分支推送提交时触发
  push:
    # 只匹配推送目标为 main 的事件
    branches:
      - main
  # 目标分支是 main 的 Pull Request 被创建或更新时触发
  pull_request:
    branches:
      - main
  # 在 GitHub Actions 页面手动启动
  workflow_dispatch:

```

这里的 `branches` 是分支过滤条件：`push.branches` 检查提交推送到哪个分支；`pull_request.branches` 检查 PR 要合并到哪个目标分支，不是 PR 来源分支。把它们都设为 `main`，就表示只有涉及 `main` 的推送或 PR 才会触发。

`workflow_dispatch` 用来启用手动触发。配置后，可以在仓库的 Actions 页面选择这个工作流并点击 “Run workflow”。它是可选项：需要从页面手动运行或重跑时再添加；省略它不会影响 `push` 和 `pull_request` 等其他触发器。

常用的过滤参数：

```yaml
on:
  push:
    # 路径过滤器：只有改动匹配下列路径时才触发
    paths:
      # 匹配 src 目录下的文件
      - 'src/**'
      # 匹配工作流配置目录中的文件
      - '.github/workflows/*'

```
`paths`表示只有改动指定路径时才跑，你也不希望在你的项目里面只是改了某一份文档/某一张图片就要重跑完整测试线吧？

定时任务：

```yaml
on:
  schedule:
    # 每天北京时间上午 10 点运行（UTC 02:00）
    # cron 字段依次是：分钟、小时、日期、月份、星期
    - cron: '0 2 * * *'

```

**请注意：`cron` 用的是 UTC 时间。 如果是北京时间，得在 UTC 基础上加 8 小时。**

> [!TIP]
> UTC 是 协调世界时（Coordinated Universal Time）的缩写。
它是当今全球最主要的时间标准，全世界各地的时钟和时间调节都以它为基准。


### env：环境变量

`env` 可以写在工作流、Job 或 Step 上，作用范围从大到小逐层缩小。下面的 `NODE_ENV` 对整个 Job 的步骤生效，Step 自己的 `LOG_LEVEL` 只对运行测试的这一步生效：

```yaml
jobs:
  test:
    # Job 运行期间都能读取这个环境变量
    runs-on: ubuntu-latest
    env:
      NODE_ENV: test
    steps:
      - name: 运行测试
        # 这个变量只传给当前 Step
        env:
          LOG_LEVEL: info
        run: npm test
```

需要使用密钥时，把值保存到仓库或组织的 Secrets，再用 `${{ secrets.NAME }}` 读取；**不要把令牌直接写进工作流文件。**

### 表达式与条件

`${{ ... }}` 用来读取 GitHub Actions 的上下文或计算表达式。常见上下文包括事件信息 `github`、矩阵参数 `matrix` 和密钥 `secrets`。`if` 可以限制某个 Step 或 Job 是否运行：

```yaml
# 这是 steps 列表中的一个 Step
- name: 只在 main 分支部署
  # 只有当前引用是 main 分支时才运行
  if: github.ref == 'refs/heads/main'
  run: npm run deploy
```

`if` 字段可以直接写表达式，不必再包一层 `${{ }}`。在其他需要插入表达式的字段中，通常使用 `${{ ... }}`；它和 Shell 中的 `$NAME` 或 PowerShell 的 `$env:NAME` 是两套不同的语法。

### needs：Job 依赖

没有依赖关系的 Job 默认可以并行运行。`needs` 指定一个 Job 必须等待哪些 Job 成功后再开始：

```yaml
jobs:
  # 先运行测试
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 22
      - run: npm ci
      - run: npm test

  build:
    # 必须等 test 成功后才运行
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 22
      - run: npm ci
      - run: npm run build
```

这里 `build` 会等待 `test` 成功后运行。若依赖多个 Job，可以写成列表，例如 `needs: [test, lint]`；依赖失败时，下游 Job 默认不会运行。

### strategy.matrix：矩阵运行

矩阵会把同一个 Job 按不同参数组合分别运行，常用于验证多个运行时或操作系统：

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        # Actions 会为这里的两个 Node.js 版本分别创建一次 Job
        node: [20, 22]
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          # 从 matrix 上下文读取当前这一轮的版本
          node-version: ${{ matrix.node }}
      - run: npm ci
      - run: npm test
```

GitHub Actions 会为 Node.js 20 和 22 各启动一次 `test` Job。`${{ matrix.node }}` 在每次运行中会取对应的版本值；矩阵中的每一项都成功后，这个 Job 才算成功。

## 两个完整的实际应用示例

### 第一个例子：React 项目的自动化测试、构建和部署

```yaml
# 工作流在 Actions 页面显示的名称
name: Frontend CI/CD

on:
  # 推送到 main 时运行
  push:
    branches: [main]
  # 目标分支为 main 的 PR 也运行检查
  pull_request:
    branches: [main]

# 默认只允许 GITHUB_TOKEN 读取仓库内容
permissions:
  contents: read

jobs:
  # 先执行检查、测试和构建
  build:
    # 使用 GitHub 托管的 Ubuntu runner
    runs-on: ubuntu-latest

    steps:
      # 将仓库检出到 runner
      - uses: actions/checkout@v7

      - name: 设置 Node.js
        uses: actions/setup-node@v7
        with:
          # 项目使用的 Node.js 主版本
          node-version: 22
          # 缓存 npm 下载的包
          cache: npm

      - name: 安装依赖
        # 按 lockfile 安装，适用于 CI 环境
        run: npm ci

      - name: 代码检查
        run: npm run lint

      - name: 运行测试
        run: npm test

      - name: 构建项目
        run: npm run build

      - name: 打包 Pages 产物
        # 上传给后面的 deploy Job 使用
        uses: actions/upload-pages-artifact@v4
        with:
          # 项目的静态站点构建输出目录
          path: ./dist

  # 只有构建成功后才会运行部署
  deploy:
    needs: build
    # PR 只检查和构建；仅 main 上的 push 会发布
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    # Pages 发布所需权限只授予部署 Job
    permissions:
      contents: read
      pages: write
      id-token: write
    # 将发布关联到 GitHub Pages 环境并记录页面地址
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: 部署到 GitHub Pages
        # id 供 environment.url 引用此 Step 的输出
        id: deployment
        uses: actions/deploy-pages@v4

```

1. **工作流名称与触发条件**：`name` 会显示在仓库的 Actions 页面。`push.branches` 表示推送到 `main` 时触发；`pull_request.branches` 表示目标分支为 `main` 的 PR 触发。PR 的来源分支可以是其他分支。
2. **默认权限**：顶层 `permissions` 让 `GITHUB_TOKEN` 默认只有 `contents: read`。构建和测试通常只需读取仓库代码，因此不需要写权限。
3. **`build` Job**：`runs-on` 指定由 GitHub 提供的 Ubuntu 虚拟机。每个 Step 按顺序运行：`checkout` 拉取代码，`setup-node` 安装 Node.js 22 并缓存 npm 下载的依赖，`npm ci` 根据锁文件安装依赖，然后运行项目中定义的检查、测试和构建脚本。
4. **构建产物**：`actions/upload-pages-artifact` 把 `./dist` 上传为 Pages 部署产物。这里假设项目的构建结果确实位于 `dist`；如果框架输出到 `build` 或其他目录，应相应修改 `path`。
5. **`deploy` Job 的依赖和条件**：`needs: build` 要求构建成功后才能部署。`if` 又把部署限制为推送到 `main` 的事件，因此 PR 会运行检查和构建，但不会发布网站。`github.event_name` 和 `github.ref` 来自 GitHub 的事件上下文。
6. **部署权限与环境**：Pages 部署需要 `pages: write` 和 `id-token: write`，所以这些权限只给 `deploy` Job。`environment` 将发布记录到 `github-pages` 环境；`url` 读取部署 Step 输出的页面地址。部署 Job 不需要重新 checkout 或重建，Deploy Pages Action 会取得前一个 Job 上传的产物。

使用这份配置前，还要在仓库的 Pages 设置中把发布来源设为 GitHub Actions，并确认 `npm run lint`、`npm test`、`npm run build` 与实际项目脚本及输出目录一致。

### 第二个例子：自动进行代码审查和安全扫描

```yaml
# 工作流在 Actions 页面显示的名称
name: Code Quality

# push 和 pull_request 两类事件都会触发
on: [push, pull_request]

jobs:
  # ESLint 检查及 PR 评论
  lint:
    runs-on: ubuntu-latest

    # PR 评论需要写权限；读取代码只需 read
    permissions:
      contents: read
      pull-requests: write

    steps:
      - uses: actions/checkout@v7

      - uses: actions/setup-node@v7
        with:
          node-version: 22
          cache: npm

      - name: 安装依赖
        run: npm ci

      - name: 运行 ESLint 并评论 PR
        uses: reviewdog/action-eslint@v1
        with:
          # 使用 GitHub 自动提供的工作流令牌
          github_token: ${{ secrets.GITHUB_TOKEN }}
          # 将诊断结果作为 PR review 评论提交
          reporter: github-pr-review

  # 与 lint 并行运行的文件系统安全扫描
  security:
    runs-on: ubuntu-latest

    # 上传 SARIF 报告需要 security-events 写权限
    permissions:
      contents: read
      security-events: write

    steps:
      - uses: actions/checkout@v7

      - name: 运行安全扫描
        uses: aquasecurity/trivy-action@0.36.0
        with:
          # 扫描仓库文件系统
          scan-type: fs
          scan-ref: .
          # 生成 GitHub Code Scanning 可接收的 SARIF 文件
          format: sarif
          output: trivy-results.sarif

      - name: 上传扫描结果
        uses: github/codeql-action/upload-sarif@v4
        with:
          # 上传上一步生成的报告
          sarif_file: trivy-results.sarif

```

1. **触发器**：`on: [push, pull_request]` 是流式写法，表示两类事件都触发；它没有限制分支，所以任何分支的推送和 PR 都会运行。若只想检查 `main`，可以改为前一个示例中的映射写法并添加 `branches`。
2. **两个 Job 默认并行**：`lint` 和 `security` 之间没有 `needs`，所以 Actions 可以同时启动它们。代码检查不必等安全扫描完成，扫描也不必等 ESLint 完成；这通常能缩短总等待时间。
3. **`lint` Job**：先 checkout 和安装 Node.js，再用 `npm ci` 安装项目依赖。`reviewdog/action-eslint` 假设仓库已经配置 ESLint，并通过 `github-pr-review` 把发现的问题写成 PR 评审评论。`github_token` 使用 GitHub 自动提供的 `GITHUB_TOKEN`，不需要把令牌硬编码进文件。
4. **`lint` 的权限**：`contents: read` 用于读取代码，`pull-requests: write` 允许 Reviewdog 写 PR 评论。来自 Fork 的 PR 通常拿不到写权限的令牌，因此 Reviewdog 可能无法发布评论；不要为此直接让不受信任的 PR 代码在 `pull_request_target` 工作流里运行。
5. **`security` Job**：Trivy 的 `scan-type: fs` 表示扫描文件系统，`scan-ref: .` 指向仓库根目录，`format: sarif` 选择 GitHub Code Scanning 可接收的报告格式，`output` 指定报告文件。紧接着的 `upload-sarif` Step 把该文件上传到仓库的安全扫描结果中。
6. **安全报告权限**：`security-events: write` 只给安全扫描 Job，用于上传 SARIF。仓库还需要启用 GitHub Code Scanning 才能在安全页面查看结果。

以上两个示例使用 Action 的主版本标签或发布版本标签，便于阅读和更新。对供应链安全要求较高的仓库，可以进一步把 Action 固定到完整的 commit SHA，并定期审查升级。

## 关于GitHub Actions的一些限制，以及怎么管理你的自动化

并发限制：

- 公共仓库：20 个并发任务
- 私有仓库：根据计费方案不同（5-180 个）

使用限制：

- 每个工作流最多运行 72 小时
- 每个 Job 最多 6 小时
- API 请求限制：1000 次/小时
- Artifact 存储：90 天自动删除

免费额度（私有仓库）：

- Linux：2000 分钟/月
- Windows：1000 分钟/月（2 倍计费）
- macOS：200 分钟/月（10 倍计费）

当然，能烧完免费额度当然代表你的仓库的活跃度相当的健康，但是免费额度再多也是有限的钱。不少人能在一个月之内把2000分钟干没，所以我们还是有必要学习一些必要的技巧

其一：`concurrency` ，设置 work 路由组后，同一时间只保留一个运行实例

```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

```
其二：`path`过滤，这真的很重要，前文已经给出写法，这里不再赘述

另外，我们说过，人做重复的事一定会出错，所以我们将其交给GitHub Actions，但是天底下就没有100%完美的系统，万一GitHub Actions出错，后果可能比人手动操作出错更严重，毕竟你可以在执行操作后立即看到执行结果的true or false，但GitHub Actions可能会出现**静默报错**的情况。

这是我们绝对不想看到的，所以我们需要在末尾加上一个`if: failure()` 的 step，一旦出错，将出错信息通过邮件发出去。这样线上有问题时，你不用每次主动去刷 Actions 页面。

常见的写法如下：
```yaml
      - name: 发失败通知
        if: failure()
        run: curl -X POST https://your-webhook-url -d '{"msg": "CI failed"}'

```

最后，GitHub Actions来帮你管理`CI/CD` 流水线，**但是GitHub Actions本身也需要被管理**，一团乱的 workflow只会起到负作用

- 按职责拆好workflow，可分为`CI`，`CD`，`Schedule`等分类
- 管好Action版本，尽量不要用下载量少到可疑的冷门Action

还是那个道理：**没有一劳永逸的完美银弹**，把自动化当成可靠的工具，但是永远要留出人工审阅把关的环节，这才是对于项目维护者而言的合格的心态和做法。
