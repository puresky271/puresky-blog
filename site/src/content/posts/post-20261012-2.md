过去，开发者在终端拉取/推送代码（`git push` / `git clone`）时，直接输入 GitHub 的账号和密码即可。但从2021 年 8 月起，GitHub 为提升安全性，彻底停用账号密码认证，改用个人访问令牌（PAT）替代密码。

[GITHUB_TOKEN官方文档](https://docs.github.com/zh/actions/concepts/security/github_token)

> [!TIP]
> 在英语中，“token”既有象征/凭证（Voucher/Badge/Coin）的意思，安全领域借用了这一层含义，把能代表你身份的加密数据称为 **Access Token（访问令牌）**。它也有最小符号单元（Symbol/Mark）的意思，自然语言处理借用了这一层含义，把文本切分出的最小计算单元称为 Token（词元）。还请不要搞混。

什么意思呢，就是说当你需要验证你对于某一个仓库的权限时，我们并不是像在常规app上/Linux上一样输入你的邮箱和密码，而是需要使用一串由 GitHub 生成的加密随机字符，用于证明“你是你”。

这是因为传统的用户名密码方式存在几个明显缺陷：

1. 每次都需要我们手动输入，不适合自动化（`CI/CD`）流程
1. 牵一发而动全身，一旦泄露的话攻击者可以获得账户完全控制权
1. 无法针对不同场景设置不同权限级别

 而访问令牌逐一解决了这些问题：

1. 可以设置为长期有效，适合自动化场景
1. 权限可精确控制，最小化安全风险
1. 可以随时撤销单个令牌而不影响其他认证方式

下面我们就简要介绍GitHub 个人访问令牌的获取和使用

## 三种令牌

不过“权限可精确控制”这句话落到具体某一种令牌上差距是很大的，GitHub 现在能签发的长期凭证有三类，我们可以靠前缀快速区分：

| 前缀 | 名称 | 权限模型 | 能限定仓库吗 |
| --- | --- | --- | --- |
| `ghp_` | 经典令牌（classic PAT） | scope，账号级 | 否 |
| `github_pat_` | 细粒度令牌（fine-grained PAT） | 按仓库 + 逐项权限 | 是 |
| `gho_` | OAuth 令牌 | scope，由应用在授权时申请 | 否 |

前两类是我们平常说的 PAT，你自己生成而且当密码使用。第三类不是你自己去生成的，而是你把账号授权给某个应用时由 GitHub 替你签发的。

三者的安全边界差别很大，下面会逐一介绍

> [!TIP]
> 在GitHub Token（以及网络安全授权） 的语境下，Scope 直译为**“作用域”，更通俗的理解就是“权限范围”**。

## 经典令牌（`ghp_`）

这就是我们常说的 PAT，是最早的一批。2021 年 8 月停用密码认证之后靠它顶上的就是这一种。

### 获取

打开 [Tokens (classic) 生成页](https://github.com/settings/tokens/new)，也可以从 Settings → Developer settings → Personal access tokens → Tokens (classic) 进去

1. **Note**：还是那句话，任何东西都需要一个名字
1. **Expiration**：可以选 7 天、30 天、60 天、90 天、自定义，或者 No expiration
1. **Select scopes**：勾权限范围。最常用的是 `repo`（读写私有仓库）、`workflow`（改动 GitHub Actions 工作流文件）、`read:org`（读组织成员关系）

**点 Generate token 之后令牌只显示这一次，关掉页面就再也拿不回来，只能重新生成。先复制走再关。**

> [!WARNING]
> 经典令牌的 scope 是账号级的，**不区分仓库**。勾了 `repo`，你名下有权限的所有仓库（包括以后新建的）就全都给了出去。它同时允许设成永不过期。**要是这两点叠在一起，攻击者就有可能一次性删除你的全部仓库，吓哭了。**

## 细粒度令牌（`github_pat_`）

这是GitHub 现在推荐的方式。它把“能碰到哪些仓库”和“能做什么”拆成两个独立维度，补上了经典令牌的短板。

### 获取

打开 [Fine-grained tokens 生成页](https://github.com/settings/personal-access-tokens/new)，也可以从 Settings → Developer settings → Personal access tokens → Fine-grained tokens 进去。

1. **Token name**：名字，名字很重要
1. **Expiration**：默认 30 天，最长一年，组织还能设更短的上限。自动化场景可以放长，**但别设成永不过期**
1. **Repository access**：三选一。Public Repositories (read-only) 只读所有公开仓库，All repositories 覆盖全部，Only select repositories 只勾需要的那几个
1. **Permissions**：分 Repository permissions 和 Account permissions 两栏，逐项展开设成 Read 还是 Read and write

> [!IMPORTANT]
> 细粒度令牌的权限是白名单语义，**没勾的权限就是没有**。经典令牌反过来，勾了哪个 scope 就作用于你名下的所有仓库。这就是上表里“能限定仓库吗”那一列的分野：前缀 `ghp_` 对 `github_pat_`。

**点 Generate token 之后令牌同样是只显示这一次。**

> [!NOTE]
> 在需要与旧系统兼容的场景下经典令牌是很有必要的。因为细粒度令牌不是所有接口都支持，部分 REST 和 GraphQL 端点至今只认经典令牌。另外它要访问组织名下的资源时，可能得等组织管理员批准。所以经典令牌没有被淘汰，只是不再是首选。

## OAuth 令牌（`gho_`）

这一类不是你手动生成的。当你把账号授权给某个应用（OAuth App）时，GitHub 会替那个应用签发一枚令牌，代表“这个应用可以以你的身份做这些事”。`gh auth login` 走浏览器那支拿到的就是它，你在日常场景中大概也最经常看到这个。

### 获取（`gh auth login`）

装了 [GitHub CLI](https://cli.github.com/) 的话，直接CLI里面敲一行：

```powershell
gh auth login
```

不带参数是一个交互式向导，依次问四件事：

1. **What account do you want to log into**：选 GitHub.com
1. **What is your preferred protocol for Git operations**：HTTPS 还是 SSH。这个设置对所有用户生效，不只是当前账号
1. **Authenticate Git with your GitHub credentials**：选 Yes 等于顺手跑一次 `gh auth setup-git`
1. **How would you like to authenticate**：用浏览器登录，或者粘贴一个现成的令牌

选浏览器那支，它会显示一个 one-time code，回车打开浏览器，把 code 粘进去授权。授权页上会列出这个应用申请的权限范围，同意之后令牌存进系统凭据管理器（macOS 的钥匙串、Linux 的 keyring 同理），`hosts.yml` 里只留账号名，不留明文。想确认存在哪的跑 `gh auth status`（确认状态）。

如果要拿令牌本体：

```powershell
gh auth token
```

它会输出一行可以直接喂给构建脚本的 `GITHUB_TOKEN`。

而如果你已经登录过，只想补权限范围的时候，不用重走整个向导：

```powershell
gh auth refresh -s workflow
```

### 和 PAT 的两个差别

- OAuth 的 scope 表达不了“按仓库授权 + 逐项权限”，所以浏览器流程不可能产出细粒度令牌。gh 走这条路拿到的是 scope 级令牌。
- 吊销的地方不一样， PAT 在 Settings → Developer settings 里撤销；OAuth 令牌得去 Settings → Applications → Authorized OAuth Apps，把那个应用的授权整个撤掉。撤完之后 gh 就要重新授权。

实际上`gh auth login` 还有一支非交互模式，可以从管道读入一个现成的令牌，适合无人值守的场景。但它只认经典令牌：细粒度令牌塞进来会因资源范围对不上而行为古怪，这种情况官方建议改用 `GH_TOKEN` 环境变量。在PowerShell走以下管道：

 ```powershell
 Get-Content mytoken.txt | gh auth login --with-token
 ```

> [!TIP]
> 你在写 GitHub Actions 时**不需要也不应该把本地任何一份令牌塞进仓库**。gh 在 Actions 里直接读 `GH_TOKEN`：
>
> ```yaml
> env:
>   GH_TOKEN: ${{ github.token }}
> ```
>
> 这里的 `github.token` 就是那个由 Actions 自动签发、只对当前仓库有效、工作流结束即失效的 `GITHUB_TOKEN`。它跟上表那三类手动准备的令牌都是两回事，用完即弃，也不用你去管过期和撤销。

关于这一点：官方的原话是：

在每个工作流作业开始时，GitHub都会**自动创建一个唯一的GITHUB_TOKEN密钥**，供你在工作流中使用。 可以使用 GITHUB_TOKEN 在工作流作业中进行身份验证。

启用 GitHub Actions 后，GitHub 会向您的存储库安装一个 GitHub App。 GITHUB_TOKEN 密钥是 GitHub App 安装访问令牌。 您可以使用安装访问令牌代表存储库中安装的 GitHub App 进行身份验证。 **令牌的权限仅限于包含您的工作流程的仓库。**

## GITHUB_TOKEN和API额度的关系

GitHub 的额度不按你的账号算，按**这次请求以什么身份发出**算。同一个接口带不带令牌能差出近百倍：

| 请求身份 | 额度 | 怎么认 |
| --- | --- | --- |
| 不带令牌 | 60 次 / 小时 | 按出口 IP，一个 IP 一份 |
| 带 PAT 或 OAuth 令牌 | 5,000 次 / 小时 | 按账号 |
| GitHub App 安装令牌 | 从 5,000 起 | 企业版组织可达 15,000 |

让我用我自己的项目，也就是这个blog来举一个例子，这个blog的首页有一个Github热力表。

![image](./images/post-20261012-2/mv4nonuc-image.png)

这个热力表的数据分两段取：

- **构建期**：`npm run build` 时抓一份快照直接渲进页面，首屏不用等接口
- **运行时**：页面加载后前端再向 worker 要一次最新数据，把快照换掉

一次刷新后将会发出去 7 个请求：

1. `/users/puresky271`，拿头像和简介
2. `/graphql`，一次查询打包拿回贡献日历、个人状态和仓库列表
3. `/users/puresky271/events/public?per_page=60`，拿最近动态
4. 最多 4 次 `/repos/{owner}/{repo}/commits/{sha}`，把最近几条推送的提交信息补全

如果我配置了`GITHUB_TOKEN`，那7 个请求对 5,000 的额度来说简直是毛毛雨，何况 worker 那边还有 10 分钟的 KV 缓存兜着，同一个访客的刷新根本打不到上游。

但如果我现在把 `GITHUB_TOKEN` 删掉呢？

- `GraphQL `直接不可用，未认证请求在` GraphQL` 端点上的额度是 0，压根不给，所以贡献日历拿不到了，只能退回解析公开页面。
- REST 的额度掉到 60 次 / 小时。

好笑的是，我现在的这台机器的匿名额度刚好用光了：

```
core: {"limit":60,"remaining":0,"used":60}
```

`curl https://api.github.com/users/puresky271` 回 403，正文：

```
API rate limit exceeded for <你的出口 IP>.
```

> [!WARNING]
> 可能你在自己电脑上一个人用感觉不到，扔到 Cloudflare Worker 上那简直就是灾难：Cloudflare 的出站 IP 是大量服务共用的，那些 IP 上的 60 次基本长期处于用完的状态。所以 worker 那侧的 `GITHUB_TOKEN` 实际是**必需的**，只有构建期才是可选。

## 一些常见的令牌的使用方式

### 1. Git 命令行使用

```bash
# 克隆私有仓库
git clone https://TOKEN@github.com/username/repo.git

# 或配置 credential helper
git config --global credential.helper store
git clone https://github.com/username/repo.git
# 第一次会提示输入用户名和密码（密码处输入 token）
```

### 2. 配置为环境变量

```bash
# Linux/macOS
export GITHUB_TOKEN="ghp_your_token_here"
echo 'export GITHUB_TOKEN="ghp_your_token_here"' >> ~/.bashrc

# Windows PowerShell
$env:GITHUB_TOKEN="ghp_your_token_here"
[Environment]::SetEnvironmentVariable("GITHUB_TOKEN", "ghp_your_token_here", "User")
```

### 3. API 请求中使用

```bash
# curl 示例
curl -H "Authorization: token ghp_your_token_here" \
  https://api.github.com/user/repos

# 或使用 Bearer 格式
curl -H "Authorization: Bearer ghp_your_token_here" \
  https://api.github.com/user
```

## 写在最后，关于GITHUB_TOKEN使用的注意事项

- 绝对不要将token硬编码到你的代码中，这种行为和直接硬编码你的`api_key`一样愚蠢！
- 优先使用细粒度令牌（Fine-grained tokens），并谨慎设置权限
- 设置有效期与定期轮换，除非是一些极为特殊的长期服务，不要设置永不过期（No expiration）

另外，ops，如果 Token 泄露了怎么办？

1. 立即撤销（Revoke）：立刻登录 GitHub，进入 Settings -> Developer settings -> Personal access tokens，找到对应的 Token 点击 Delete / Revoke。这会让该凭证瞬间失效。
1. 只在 Git 中执行 git commit --amend 或覆盖提交是不够的，提交历史记录或 GitHub 的缓存（`Commit Cache`）可能依然保留着旧记录。最安全的做法始终是直接作废 Token。
1. 检查审计日志：进入账号的 Security Log，检查近期是否有异常 IP、未授权的拉取或修改记录。

总而言之，既然GitHub 个人访问令牌最初被设计出来的目的是为了替账号密码的使用，那我们就应该也用平时对待密码的态度来对待它。
