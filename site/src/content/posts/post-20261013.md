在git的官方文档中，对于git worktree（工作树）的描述的开头部分如下：

Manage multiple working trees attached to the same repository.

A git repository can support multiple working trees, allowing you to check out more than one branch at a time. With `git worktree add` a new working tree is associated with the repository, along with additional metadata that differentiates that working tree from others in the same repository. The working tree, along with this metadata, is called a "worktree".


[这里是git worktree的官方文档](https://git-scm.com/docs/git-worktree)

git worktree可以让多个独立的工作目录分别拥有自己的`HEAD`、索引和文件状态，同时共享同一套仓库对象数据。它解决了 Git 工作流中的一个痛点：**如何在不中断当前工作的情况下处理其他任务**，而且随着当下的coding agent的流行，我们经常会开出**多个session进程并行开发**，此时git worktree的作用就愈发显得重要。现在我们就来重新认识一下Git工作树这个伟大的功能。

git worktree和git branch是密不可分的，想要了解git worltree的本质，我们首先需要把目光放到“分支”这个概念上。

## git branch的本质是什么

### 创建分支意味着什么
如果你进入任何一个 Git 仓库的根目录，并查看隐藏的`.git`文件夹，你会发现所有的所有的本地分支都存放在一个叫做 `.git/refs/heads/`的目录下。

而假设你有一个 `main`分支和一个` feature `分支，该目录下就会有两个同名文本文件：

```bash
.git/refs/heads/main
.git/refs/heads/feature
```

查看这些文件的内容（例如 `cat .git/refs/heads/main`），你会发现里面只有一行内容：**一个40位的Commit SHA-1哈希值**（加上一个换行符，共 41 字节）。

> [!TIP]
> 哈希值（Hash Value，也称散列值）是数据经过特定的数学算法（即哈希函数）计算后得到的一段固定长度的代码或数字串。对于Git而言，每次代码提交（Commit）都会生成一个 SHA-1 哈希值作为版本标识。

例如：

```text
c2b8a4f91e45d8b7636e7892...
```

假设你现在在`main`分支的基础上新开了一个`feature`分支，Git在底层做的事情仅仅是在 `.git/refs/heads/`目录下新建一个名为feature的文本文件，并把当前 Commit 的哈希值写入进去。

在 Git 中，代码历史是一棵由提交对象构成的有向无环图（DAG），每一个 Commit 对象都保存着自己的元数据（作者、时间、树对象）以及指向父 Commit 的指针（Parent Hash），分支指针始终指向该分支历史链条上的**最新一次提交**，也就是最顶端的一次Commit。

> [!IMPORTANT]
> 在Git中，我们说的”指针”和C语言中的指针不太一样，它并不是真的指向了你工作区里面的一份内存空间，而是会指向一个**“Commit对象”**

当你在这个分支上执行一次新的 `git commit` 时，Git会生成一个新的Commit对象，新Commit 的父节点指向旧Commit，而后**将当前分支文件的中的哈希值更新为新 Commit 的哈希值**，这样的话我们就说分支指针移动了。

这就和传统的版本控制系统不同，后者在创建分支时本质是复制了一整套的代码目录（这其实更符合我们的直觉），而**Git分支不包含任何文件内容**，所有的文件和目录树都属于对象库，方便很多。

### 拆开一次commit

我们可以用Git内置的底层命令`git cat-file -p HEAD`来看看当前最新 Commit 对象的原始文本：

```bash
tree d8329fc1cc938780ffdd9f94e0d364e0ea74f579    
#这是指向一个 Tree 对象的哈希值
parent 2b7a2d488e3a246815ec6690f0c057cf2cf87b2f    
#上一次提交（父 Commit）的哈希值
author puresky <puresky@example.com> 1718000000 +0800
committer puresky <puresky@example.com> 1718000000 +0800

feat: 这是一个新功能

这里是详细的提交说明。
```

对于`d8329fc1cc938780ffdd9f94e0d364e0ea74f579`这一串哈希值而言，我们假设它就是`feature`分支的最新的一次的提交的哈希值，那么此时如果你打开`.git/refs/heads/main`这个文件，你将看到**它里面只有一行文本**，就是：

```text
d8329fc1cc938780ffdd9f94e0d364e0ea74f579
```

这就是所谓的**指向**，Git只要查看这份哈希值就能知道当前提交的信息，而如果需要知道知道历史提交的信息，**一层层往上查父提交的哈希直到遇到根节点即可**。

### 为什么不能同时检出多个分支

前面我们一直在讨论 Commit 和分支指针，但真正需要注意的是：**分支指针并不是工作目录本身**。当我们在一个普通的 Git 仓库里执行 `git checkout feature` 时，Git 并不会把一份新的代码目录复制出来。它会读取 `feature` 指向的 Commit，再**用这个 Commit 对应的 Tree 对象，把当前目录中的文件更新成对应版本**，同时把当前工作区的 `HEAD` 改为指向 `feature`，并更新索引。

也就是说，一个普通工作区同时只有一套：

- 当前的 `HEAD`，用于记录“我现在在哪个分支上”；
- 索引`index`，用于记录下一次提交准备写入的文件状态；
- 工作目录中的实际文件。

你可以把分支理解成“应该取哪一个 Commit”，把索引理解成“下一次提交准备提交什么”，把工作目录理解成“正在编辑什么”。当你从 `main` 切换到 `feature` 时，Git 必须把这一整套状态一起切换过去，而不是只修改 `.git/refs/heads/` 下的某个文本文件。

**因此，在同一个工作区里不能直接同时检出两个分支。**

假设 `main` 和 `feature` 分别指向不同的 Commit，如果工作区仍然只有一套文件，那么“当前目录里的 `app.js` 到底属于哪个分支？”、“这次修改应该记录到哪个分支？”都会变成没有明确答案的问题。更具体地说，第二次 `checkout` 会改写第一次检出的文件，并且只留下一个 `HEAD` 和一份索引；如果当前还有未提交的修改，Git 甚至可能拒绝切换，以免覆盖这些修改。

这也是为什么 Git 不会把“同时检出多个分支”实现成让一个目录拥有多个 `HEAD`。**一个目录中的文件、索引和当前分支必须保持一一对应**，否则 `git add`、`git commit` 以及冲突处理都无法判断它们属于哪条分支。限制来自工作区状态只有一套，而不是来自分支数量有限，**仓库当然可以有很多分支，只是一个普通工作区在同一时刻只能承载其中一个分支的工作状态。**

而git worktree之所以能解决这个问题，就是因为它**为每个额外的工作目录提供一套独立的 `HEAD`**、索引和文件状态。

于是，一个目录可以检出 `main`，另一个目录可以检出 `feature`；两个目录各自修改、暂存和提交但是互不覆盖。因为它们仍然共享前文提到的 Commit、Tree、Blob 等对象库，所以不需要为每个分支复制一整套历史数据。

## git worktree的基本用法

所以受我们上述所言的限制，假设你正在`feature`分支开发新功能，结果出于某种原因你需要临时去`main`分支修复一个bug，那么由于你没法同时检出多个分支，你就需要在多个分支之间进行切换，流程大概会是：

```bash
# 1. 暂存当前工作，你可千万不要忘了这一步
git stash save "暂存的工作"


# 2. 切换到主分支
git checkout main

# 3. 创建修复分支
git checkout -b hotfix/XX-bug

# ... 修复代码 ...

# 4. 提交并推送
git add .
git commit -m "Fix: XX bug"
git push origin hotfix/XX-bug

# 5. 切回开发分支
git checkout feature/XX

# 6. 恢复工作
git stash pop
```

按理来说，如果你暂存`stash`之后，目标分支的原代码完全没有发生任何变化，`git stash pop` 是绝不可能产生冲突的。

但代码毕竟是由人开发的（~~现在可能不是了~~），人是不可能一直做到像机器一样精准的，在实际的开发中，可能会出以下的乱子：

1. 肌肉记忆：切回分支后顺手拉取了代码

在第 5 步 `git checkout feature/XX` 之后，很多开发者的肌肉记忆是先拉取最新代码：

```bash
git pull origin feature/XX
```
或者把刚修好的 hotfix 合并了进来：

```bash
git merge main
```

（~~别笑，我真干过~~）

一旦拉取了代码，分支的 HEAD 就往前移动了。如果别人提交的代码（或者刚修的 hotfix）改动了你暂存里正在写的文件，紧接着执行第 6 步 `git stash pop`就会直接报冲突。

2. 中途又 stash 了一次，导致“弹错栈”

`git stash` 底层是一个栈，如果在第 3~4 步修复 hotfix 的过程中，你手忙脚乱又执行了一次 `git stash`，那么栈顶就变成了 hotfix 的改动。

当你回到 feature 分支执行 `git stash pop` 时，弹出的根本不是“暂存的工作”，而是 hotfix 的临时代码，直接把 hotfix 的修改强行合入 feature 分支极大概率产生冲突。

3. 本地构建缓存与依赖文件的污染

在切去 main 和 hotfix 修复 bug 时，你可能在本地启动了项目（比如执行了 `npm install`、`mvn compile`、或者打包脚本）

这可能会生成/修改一些未提交的本地文件（如 package-lock.json、编译中间文件等）。
当你切回 feature 时，这些未跟踪或变动的文件依然残留在工作区里。
此时执行 `stash pop`，一旦暂存里也有这些文件的改动，就会报错冲突或无法还原。

---
而就像我们先前所言，如果你使用git worktree，可以在本地同时开启另一个独立文件夹去修 hotfix，你原先的代码、编辑器光标、终端运行状态甚至连存都不用存，彻底避免了这种 `stash pop` 冲突的风险。

```bash
# 1. 创建紧急修复的 worktree
git worktree add ../hotfix-XX -b hotfix/XX-bug

# 2. 进入修复目录
cd ../hotfix-XX

# 3. 修复代码
vim src/auth/login.js

# 4. 测试、提交
npm test
git add .
git commit -m "Fix: XX bug"
git push origin hotfix/XX-bug

# 5. 删除 worktree
cd ..
git worktree remove hotfix-XX

# 你的主工作目录完全不受影响
cd ~/project
git status
# 还是原来的 feature分支
# 所有修改都在
```

### 基本命令

创建新的 Worktree：

```bash
# 基于现有分支创建 worktree
git worktree add ../feature-branch feature-branch

# 基于新分支创建 worktree
git worktree add ../bugfix -b hotfix/bug-123

# 指定提交创建 worktree
git worktree add ../temp-commit abc1234
```
查看 Worktree 列表：

```bash
git worktree list
```

示例输出：

```bash
/Users/dev/project                            abc1234 [main]
/Users/dev/feature-branch          def5678 [feature-branch]
/Users/dev/hotfix-branch            3456789 [hotfix/bug-123]
```

删除worktree：

```bash
# 删除指定 worktree
git worktree remove ../feature-branch

# 删除后清理
git worktree prune
```

## 我去，gitworktree还能这样用

“临时修一个hotfix”这种场景实际上还是太小儿科了，git worktree能做到的事情远不止于此。

> [!NOTE]
> 相较于**在不中断当前工作的情况下处理其他任务**，worktree 真正有价值的地方，是把**需要同时存在的多个代码状态变成多个可以独立运行、独立验证的实验现场。**

前提是每个 worktree 对应一个明确的分支或提交，每个目录里的命令都必须在它自己的目录中执行。

### 1. 批量审查多个 PR

如果我们一次要审查多个 PR，反复在一个目录里切换来源分支很容易把构建产物、依赖和未提交文件带到下一个 PR。可以为每个 PR 建一个临时 worktree，让它们同时存在：

```bash
git fetch origin "+refs/pull/*/head:refs/remotes/origin/pr/*"

git worktree add --detach ../review-pr-421 origin/pr/421
git worktree add --detach ../review-pr-438 origin/pr/438
git worktree add --detach ../review-pr-452 origin/pr/452
```

这里使用 `--detach` 是因为审查只需要固定在 PR 当前的提交上，不需要让本地分支跟着移动。进入每个目录后分别执行安装、构建和测试，再用 `git diff origin/main...HEAD` 查看改动：

```bash
cd ../review-pr-421
git diff --stat origin/main...HEAD
npm ci
npm test
```

如果 PR 的来源分支还需要继续修改，就应该用 `-b review/pr-421` 建一个本地审查分支；纯审查则保持 detached HEAD 更能避免误提交。审查结束后可以一次性清理：

```bash
git worktree remove ../review-pr-421
git worktree remove ../review-pr-438
git worktree remove ../review-pr-452
git worktree prune
```

这里我们让每一份结果都绑定到一个确定的提交。这样 PR 继续更新时，只需删除旧 worktree，再按新的 SHA 建立审查现场，测试结果不会混入上一个版本的文件。

### 2. 用 worktree 做重构性实验

在对项目做重构的时候经常会遇到一个问题：你想比较两种实现，但又不想把半成品混进当前分支，或者是你只是想“试试看这个点子”，那么就可以从同一个基线提交建立多个实验分支：

```bash
git worktree add ../refactor-baseline main
git worktree add ../refactor-module -b experiment/module-refactor main
git worktree add ../refactor-pipeline -b experiment/pipeline-refactor main
```

三个目录初始拥有同一份代码。`refactor-module` 只尝试拆分模块，`refactor-pipeline` 只尝试替换处理流程，`refactor-baseline` 保留不变，作为性能和行为基线。每个实验都可以单独跑完整测试、基准测试和静态检查：

```bash
cd ../refactor-module
python -m pytest
python scripts/benchmark.py > module.txt

cd ../refactor-pipeline
python -m pytest
python scripts/benchmark.py > pipeline.txt
```

实验失败时，直接删除对应分支和 worktree 即可；实验成功时，再把它合并或挑选提交回正式分支。这个结构把“实现选择”和“当前正在工作的目录”分开了，也让基准结果有一个不会随实验代码变化的参照物。

> [!WARNING]
> 需要注意的是，worktree 只隔离 Git 管理的文件。**数据库、密钥、上传目录和构建缓存如果被 `.gitignore` 忽略，仍然需要显式复制、挂载或使用临时配置。**否则看似比较的是两种重构，实际比较的可能是两套运行时数据。


### 3. 探查回归测试失败的原因

你/agent在跑回归测试的时候发现失败了，请不要当前开发目录里不断修改、重跑，最后连“失败来自哪个版本”都说不清。我们可以把已知正常的提交和已知失败的提交各放进一个 worktree：

```bash
git worktree add --detach ../regression-good <最后一个通过测试的提交>
git worktree add --detach ../regression-bad <第一个失败的提交>
```

先在两个目录使用完全相同的命令和测试数据运行：

```bash
cd ../regression-good
python -m pytest tests/test_login.py -q > good.log

cd ../regression-bad
python -m pytest tests/test_login.py -q > bad.log
```

如果失败提交与通过提交之间包含很多变更，可以再从中间提交建立二分现场，配合 `git bisect` 找到第一个引入回归的提交。每个 bisect 步骤都可以使用临时 worktree运行验证脚本，避免反复改写主目录：

```bash
git bisect start
git bisect bad <第一个失败提交>
git bisect good <最后一个通过提交>
git bisect run python scripts/check_regression.py
git bisect reset
```

两个 worktree 还适合做“只替换一个变量”的验证：把失败版本的某个配置、fixture 或单个提交对应的文件带到通过版本中，再运行同一条测试。因为两个目录的 `HEAD` 和索引互不影响，实验结束后不会留下需要恢复的暂存状态。这里仍然要记录 Python、Node、数据库快照和环境变量，因为worktree 固定的是代码提交，不会自动固定整个运行环境。

### 4. 把提示词门禁做成两棵 worktree 的对拍（~~私货~~）

在那篇《我给提示词做了版本控制，因为它根本没有源文件》里，提示词被当成运行时装配出来的编译产物。于是为了避免在非提示词改动的时候造成意外的提示词漂移，我要让一棵树保留改动前的装配代码，另一棵树放改动后的代码，然后在各自目录生成 dump，最后做逐场景对拍。

例如，当前分支准备修改认知装配逻辑时，可以先建立基线树：

```bash
git worktree add --detach ../prompt-before HEAD
git worktree add ../prompt-after -b experiment/prompt-gate HEAD
```

在 `prompt-after` 中完成修改后，分别在两棵树运行上一篇文章中的固定场景 dump：

```powershell
cd ../prompt-before
py -X utf8 scripts\dump_cognitive_prompt.py --project-root . --label before_change

cd ../prompt-after
py -X utf8 scripts\dump_cognitive_prompt.py --project-root . --label after_change

git diff --no-index `
  ../prompt-before/_offline_smoke_out/cognitive_prompt_before_change.json `
  ../prompt-after/_offline_smoke_out/cognitive_prompt_after_change.json
```

就像先前所说的，两棵树必须对齐 `.streamlit/secrets.toml`、`memory_core.db`、`world_ledger.json`、`daily_journal/` 等 gitignore 文件，并使用相同的固定时间、fixture 和 patch。那篇文章里出现过的双向差异正是基线 worktree 缺少 `secrets.toml` 导致的环境漂移。

对拍结果应按门禁的覆盖范围解释：相关场景可以出现预期差异；无关场景必须逐字节一致；当前 user 消息仍要位于末尾；事实、推测和访客隐私边界不能漂移。门禁输出不能只写“通过”，还要写明 dump 路径、允许变化的场景和不覆盖的装配层。这样 worktree 提供的是可复现的代码基线，提示词 dump 提供的是可比较的运行时产物，两者合起来才构成有效的提示词版本审查。

### 5. 和 coding agent 结合：让多个 Codex agent 并行开发

#### 第一步：拆分任务并创建 worktree

worktree 和 coding agent 的结合最适合用在一个任务可以拆成多个相对独立的工作面时。以 Codex 为例，可以让一个协调 agent 保留在主工作目录，另外为每个执行 agent 建立独立 worktree。

假设需求是“给账户系统增加新的登录方式，并补齐前端入口和回归测试”。可以让协调 agent 先把任务拆成三个可以独立验收的工作面：API agent 负责接口和服务层，UI agent 负责页面交互，Test agent 负责回归测试和测试夹具。拆分时要先约定接口字段和错误码，避免把不一致推迟到最后的合并阶段。

先确认基线干净，并从同一个 `main` 创建三个分支和目录：

```bash
git status
git switch main
git pull --ff-only origin main

git worktree add ../agent-api -b agent/api main
git worktree add ../agent-ui -b agent/ui main
git worktree add ../agent-tests -b agent/tests main
git worktree list
```

三个目录初始内容相同，但分别拥有自己的 `HEAD`、索引和未提交修改。协调 agent 可以保留在主目录，或者另建一个集成 worktree；不要让多个 agent 直接共用主目录。

#### 第二步：给每个 Codex session 指定唯一目录

启动方式因人而异，关键要求是“一个 session 对应一个目录”：

```text
Codex A，工作目录 ../agent-api：实现 API 层改动，只修改 API 相关文件，完成后提交到 agent/api。
Codex B，工作目录 ../agent-ui：实现前端交互，只修改 UI 相关文件，完成后提交到 agent/ui。
Codex C，工作目录 ../agent-tests：补充回归测试和测试夹具，只修改测试相关文件，完成后提交到 agent/tests。
```

给 agent 的任务说明应包含工作目录、允许修改的范围、完成标准和提交分支。例如：

```text
你在 ../agent-api 工作，只处理登录 API 和服务层，不修改前端与测试文件。
先阅读现有认证流程，按约定的接口契约实现功能。
完成后运行 API 测试，报告测试命令和结果；确认通过后提交到 agent/api。
不要切换到其他分支，也不要修改 ../agent-ui 或 ../agent-tests。
```

这样可以让提交被协调者准确归因。每个 agent 都拥有自己的 `HEAD`、索引、未提交修改、终端进程和测试缓存，因此一个 agent 的半成品不会让另一个 agent 的 `git status` 变脏，也不会让它读到正在编辑的文件。它们仍共享对象库，所以提交、分支和历史可以被协调 agent 立即看到：

```bash
git log --oneline --all --decorate -12
git worktree list
```

#### 第三步：各自在自己的 worktree 中开发和验证

每个 agent 都应在自己的目录中完成“阅读代码、修改、测试、提交”这一闭环。比如 API agent 可以这样工作：

```bash
cd ../agent-api
git status
python -m pytest tests/api -q
# 修改代码
python -m pytest tests/api -q
git diff --check
git add path/to/api_files
git commit -m "feat: add login method API"
```

UI agent 可以启动自己的前端服务，Test agent 可以构造失败用例。它们的端口、临时输出和缓存也应尽量分开；如果项目需要共享数据库或外部服务，就要给每个 worktree 准备独立的测试数据库或只读 fixture。**worktree 能隔离 Git 状态，不能自动隔离端口、数据库和密钥。**

#### 第四步：协调者检查提交并建立集成 worktree

agent 报告完成后，协调者先检查提交内容，而不是直接合并：

```bash
git show --stat --oneline agent/api
git diff main...agent/api -- path/to/api_files
git show --check agent/api
```

确认职责没有越界后，再从同一个 `main` 建立独立的集成 worktree：

```bash
git worktree add ../integration -b integrate/feature main
cd ../integration
```

#### 第五步：按依赖顺序合并并逐层验证

这个例子中，先合并 API，再合并 UI，最后合并测试：

```bash
git merge --no-ff agent/api
python -m pytest tests/api -q

git merge --no-ff agent/ui
npm test

git merge --no-ff agent/tests
python -m pytest
```

每合并一个分支就运行该层测试，可以知道问题是由哪一次合并引入的。所有分支都合并后，再运行完整测试、构建和必要的门禁。

#### 第六步：只在集成 worktree 中解决冲突

如果两个 agent 修改了同一段代码，冲突应该在 `../integration` 中解决，并记录为单独提交：

```bash
git status
# 编辑冲突文件，保留符合接口契约的版本
git add path/to/conflicted_file
git commit -m "merge: resolve API and UI integration"
```

不要让一个 agent 直接进入另一个 agent 的目录替它改文件，也不要在某个执行 agent 的未提交状态上强行合并。若冲突暴露出接口契约不一致，协调者应先更新契约，再把具体修改发回相关 agent 的分支。

协调者的职责是管理任务边界和汇合顺序，而不是替所有 agent 共用一个目录。对于需要反复迭代的任务，可以保留长期 agent 的 worktree，把临时验证交给 detached worktree。

#### 第七步：记录结果并清理现场

集成测试通过后，协调者记录每个分支的提交、测试命令和最终集成提交。确认不再需要执行 agent 的目录后，再清理 worktree：

```bash
git worktree remove ../agent-api
git worktree remove ../agent-ui
git worktree remove ../agent-tests
git worktree remove ../integration
git worktree prune
```

如果某个 agent 还需要继续迭代，就保留它的 worktree，只清理已经完成的目录。分支和提交本身应该保留到合并完成、发布或回滚策略确定之后。

需要指出的是：并行不等于可以无条件拆分任务。多个 agent 同时改同一个接口、同一份数据库迁移或同一组提示词装配规则，最后仍然需要协调者设计合并顺序。对这类高耦合改动应先划定文件和行为边界。如果是涉及运行时数据的任务，还要为每个 worktree 准备独立的配置和数据库快照。worktree 解决的是目录和 Git 状态的隔离，任务依赖、接口契约和合并决策仍然需要由人或协调 agent 管理。
