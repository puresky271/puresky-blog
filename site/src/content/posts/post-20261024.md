在 git 的官方文档中，对于 `git rebase` 的描述可以说是非常简短：

Reapply commits on top of another base tip.

[这里是 git rebase 的官方文档](https://git-scm.com/docs/git-rebase)

用大白话说就是：**把提交重新应用到另一个基础提交之上**。

这就是 rebase 最核心的一点，变基不会去搬运旧提交本身，它做的只是把这些提交里的修改提取出来，在一个新基底上按顺序重新生成提交。

你可能会在很多文章里面见过这句话——**rebase 能把提交历史拉成一条直线**，我们不能只知道这一句，如果时刻带着这个观点去看 rebase 很容易搞反两个分支的方向，想不明白为什么提交哈希会变也分不清什么时候会把别人的分支改乱。要搞清楚rebase的本质，我们先得看 commit 和分支指针到底是怎么存的。

## git rebase 的本质是什么

此时 `main` 指向 M，`feature` 指向 D，两条分支的共同祖先是 B。

现在切换到 `feature`，执行：

```bash
git switch feature
git rebase main
```

更简单一点，这两条命令也可以合成一条：

```bash
git rebase main feature
```

问题在于，这里的两个分支到底谁在动呢：

- `feature` 是要变基的分支，上面的提交会被拿出来重放
- `main` 是新的基底，它原本的提交完全不动

所以rebase命令的意思其实很简单：**把 `feature` 分支上分叉之后多出来的改动，按顺序接到 `main` 最新的提交 M 后面**。

**需要特别指出的是：C′ 和 D′ 是两个全新的 commit 对象，绝不是把原来的提交搬了个地方。**

在上一篇 [Git Worktree](/posts/post-20261013/) 里我们聊过 commit 对象的构成——一个提交的哈希值，由它记录的 Tree（文件快照），父提交哈希，作者信息，提交时间以及提交说明共同计算出来。C′ 的父提交已经从 B 变成了 M，**哪怕里面的代码改动跟 C 一模一样，只要父提交哈希变了，算出来的新提交哈希也必然不一样。**

> [!IMPORTANT]
> rebase 改写的不只是一行分支指针。git 在对象库里为重放的提交重新串起了一条链，再把分支指针指到新链末尾。原来的旧提交暂时还在对象库里躺着，可以通过 `reflog` 找到。

这里我在图中写成 `C′`，就是为了提醒各位**它已经是一个哈希不同的全新提交了，不是原来的C了**。即便合并时没有一点冲突，哈希也一定会变。

### 分支到底去了哪里

变基前可以用下面的命令观察所有分支：

```bash
git log --oneline --graph --all --decorate
```

你会看到类似这样的结构：

```text
* d333333 (HEAD -> feature) add feature tests
* c222222 add feature page
| * m111111 (main) update main page
|/
* b000000 shared base
* a000000 initial commit
```

变基后再看：

```text
* d666666 (HEAD -> feature) add feature tests
* c555555 add feature page
* m111111 (main) update main page
* b000000 shared base
* a000000 initial commit
```

提交说明虽然没变，但是 C 和 D 的哈希却全变了。`main` 上的 M 完全没动，而 `feature` 看起来就像是刚基于 M 接着写出来的一样。

如果目标分支根本没有新提交（比如 `main` 还停在共同祖先 B），那就没有需要切换的新基底，Git 会直接提示已经是最新状态，不会有任何变化。

## rebase 和 merge 的区别

**欸，不对啊，你会发现：这从结果上来看和我直接执行一次`git merge`有什么区别呢？**

面对刚才的分叉，在 `feature` 上执行 `git merge main` 当然也能把 M 的修改纳入当前分支。**但和 rebase不同的是， merge 会保留 C 原来指向 B 的父提交关系，并在需要时新增一个同时连接 M 和 D 的合并提交。**

| 对比项 | rebase | merge |
| :--- | :--- | :--- |
| 对当前分支提交的处理 | 在新基底上重放并生成新提交 | 保留原提交及其父关系 |
| 分叉是否保留在历史中 | 当前分支呈现为线性历史 | 分叉与汇合仍然可见 |
| 是否可能出现合并提交 | 普通重放本身不创建合并提交 | 分叉合并时通常会创建 |
| 原提交哈希 | 被重放的提交会变化 | 已有提交不变 |
| 更适合表达的历史 | 整理后的顺序开发过程 | 实际发生的并行与汇合过程 |

它们各自记录历史的方式不同：**rebase 把开发过程整理成一条干净的直线，merge 则如实记下分支什么时候分开，什么时候合回来。**整齐的直线未必代表真实发生的过程，保留分叉也谈不上混乱，关键看你和团队平时想从提交历史里看清楚什么。

## 交互式 rebase 是在重放前编辑清单

普通 rebase 解决的是把提交接到哪里。交互式 rebase 还能让你在重放之前，挑挑拣拣，重新修改这些提交。

假设最近四次提交依次是：

```text
a111111 add login form
b222222 fix login validation
c333333 adjust login styles
d444444 add profile page
```

其中前三次其实都属于同一个登录功能，那么可以执行：

```bash
git rebase -i HEAD~4
```

Git 打开的待执行清单按**从旧到新**排列，和 `git log` 默认从最新提交开始显示的方向相反：

```text
pick a111111 add login form
pick b222222 fix login validation
pick c333333 adjust login styles
pick d444444 add profile page
```

注意 `HEAD~4` 表示从当前提交向前数四个提交，它选出的基底是这四个提交之前的那个提交。这个基底本身不在编辑清单中。也可以用明确的提交哈希：

```bash
git rebase -i <最早要修改的提交>^
```

这里的 `^` 表示父提交。不要直接填最早要修改的提交，否则它自己不会进入清单。

常用的清单命令如下：

| 命令 | 缩写 | 作用 |
| :--- | :--- | :--- |
| `pick` | `p` | 保留该提交并继续重放 |
| `reword` | `r` | 保留修改并重新编辑提交说明 |
| `edit` | `e` | 应用该提交后暂停，允许继续修改内容 |
| `squash` | `s` | 合并到前一个提交并编辑合并后的说明 |
| `fixup` | `f` | 合并到前一个提交并丢弃当前提交的说明 |
| `drop` | `d` | 丢弃该提交 |

直接删掉清单里的某一行，对应的提交就会被丢弃。执行前看清楚范围，尽量只整理提交结构，不要顺手把代码改得面目全非，免得出问题时不好排查。

## 冲突为什么可能连续出现

这是因为 merge 通常围绕一次三方合并处理冲突，而 rebase 是逐个重放提交。假如 C 和 D 都碰到了 M 修改过的同一处代码，那么生成 C′ 时可能冲突，继续生成 D′ 时又可能冲突，以此类推。

如果很不幸，真的发生冲突了，我们就先看状态：

```bash
git status
```

编辑冲突文件，保留当前步骤真正需要的内容，然后执行：

```bash
git add path/to/conflicted-file
git rebase --continue
```

> [!TIP]
> 这里不需要先手动执行一次普通的 `git commit`。`--continue` 会让 Git 继续完成当前重放步骤，再处理清单中的下一项。如果后续提交仍然冲突，就重复同样的过程。


你始终有三个出口：

```bash
# 解决当前冲突后继续
git rebase --continue

# 跳过当前正在重放的提交
git rebase --skip

# 放弃整个操作并回到变基前
git rebase --abort
```

`--skip` 会直接扔掉当前这个提交的所有改动，跳过去接着重放下一个，如果不确定后果就别用。而如果发现基底选错了或者解决冲突时改乱了，直接用 `--abort` 彻底撤销整个变基操作。

> [!TIP]
> rebase 中途看到工作区少了许多文件时不要立刻认定它们被永久删除。git 可能正停在某个新基底或中间提交上。先看 `git status` 和 rebase 状态，再决定继续还是中止。

## 怎样用 rebase 得到线性历史

一种常见的功能分支流程是先在 `feature` 上变基到最新 `main`，再回到 `main` 合并。

```bash
git switch feature
git fetch origin
git rebase origin/main

git switch main
git merge --ff-only feature
```

因为 `feature` 现在直接从 `origin/main` 的最新提交向后延伸，`main` 可以直接快进到 `feature` 的末端，不需要再制造一个合并提交。`--ff-only` 还会明确禁止意外产生非快进合并。

但这并不是用来死记硬背的，如果你是在 GitHub / GitLab 上提 PR，团队可能早就统一设置了只用 Merge Commit 或者 Squash。主分支通常也有保护规则，不允许直接推送。平时按照团队约定的方式来就行。

如果只是想同步当前功能分支的远端更新，可以使用：

```bash
git pull --rebase origin feature
```

**这会把远端 `feature` 上你还没有的提交作为新基底，再重放你的本地提交。**它方便的前提是这些本地提交尚未成为别人继续开发的基础。

```bash
git push --force-with-lease
```

它会在远程分支已经被别人更新过时拒绝覆盖，至少多了一层检查。但它没法帮你确认别人有没有顺手基于你的提交新建分支，因此不能当成免死金牌。

## 变基搞砸了怎么找回历史

rebase 结束之后要是发现基底选错了怎么办？先停手，不要急着敲新命令或者乱提代码。可以用 `reflog` 翻看分支指针移动前的记录：

```bash
git reflog show feature
```

找到变基之前的那个提交哈希，在 `feature` 分支上直接重置回去：

```bash
git reset --hard <旧提交哈希>
```

但是请小心：`reset --hard` 会把当前工作区和暂存区清干净，执行前一定要确保没有还没保存的改动。如果变基还在中途（比如卡在冲突界面），直接用 `git rebase --abort` 就能退回变基前的状态，不需要动用 reset。

另外要记住，`reflog` 只是本机保留的分支指针操作流水，时间长了会被自动清理，也不会同步到远程仓库。不要把它当成银弹，你自己平时操作前想清楚远比靠 reflog 兜底靠谱得多。

## 怎么选

我觉得平时用大致遵循这几个习惯就好：

- 还在自己手里折腾的功能分支的话，用 `rebase -i` 把零碎提交整理成逻辑清楚的几个节点
- 本地分支落后主干时，用 `rebase` 把分支基底更新到最新主干，方便后续合入
- 涉及到团队多人的公共分支，按团队约定的流程走，不要随便强行改写公共历史
- 已经推出去且别人可能在用的提交，绝对不 rebase，如果需要撤销，用 `revert`
- 遇到搞不懂的分支状态，先敲 `git status` 和 `git log --graph` 看看清楚，别盲目尝试 `--force`

说到底，**rebase 就是把改动拿出来，在一个新基底上重新生成一套提交。**而且父提交一变，生成的哈希就完全变了，就这样。
