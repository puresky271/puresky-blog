在数据结构中，存储一张图的本质，就是**把图中顶点之间的关系用计算机能够识别和操作的数据结构表示出来。**

所有人都知道，一张图通常抽象为二元组：

$$
G=(V,E)
$$

其中：

- $V$：顶点集合，表示图中有哪些对象
- $E$：边集合，表示这些对象之间存在哪些连接关系

它的顶点集合与边集合分别是：

$$
V=\{A,B,C\}
$$

$$
E=\{(A,B),(B,C),(A,C)\}
$$

要把这张图装进内存，计算机需要保存两类信息：

1. **顶点信息**：图里有哪些顶点，每个顶点携带什么属性
2. **边信息**：哪些顶点之间相连，每条边携带什么属性（如方向、权值）

边信息决定了整张图的拓扑骨架。计算机并不直接认识你在纸面上画的那些圆圈和线条，它只能操作数字，数组，结构体和指针。因此我们必须设计一套数据组织规则，把顶点之间的连接关系编码进去：

| 核心问题 | 存储结构需要完成的任务 |
| --- | --- |
| 图里有哪些顶点？ | 保存顶点及其数据 |
| 顶点之间如何相连？ | 保存边及其连接关系 |
| 怎样高效查询或修改连接？ | 按具体算法场景选择组织形式 |

这也是图的存储方式之所以衍生出六种经典方案的原因：**图本身没变，改变的是我们记录和检索这些关系的角度。**

## 1. 邻接矩阵存储

存储一张图需要同时交代两件事：有哪些顶点，以及谁和谁相连。那么最直观的做法是**开一个二维数组，行和列都对应各个顶点，用格子里的数字记录两个顶点之间有没有边。**

设图有 $n$ 个顶点，记作 $v_1,v_2,\dots,v_n$，邻接矩阵就是一个 $n\times n$ 的二维矩阵 $M$：

$$
M_{ij}=
\begin{cases}
1, & (v_i,v_j)\in E \\
0, & (v_i,v_j)\notin E
\end{cases}
$$

第 $i$ 行第 $j$ 列为 `1`，表示 $v_i$ 和 $v_j$ 之间有边；为 `0` 则表示没有边。无向图和有向图都能套用这套规则，区别在于同一格数字所代表的连接方向。

以下是具体代码，本质上就做了两件事：申请二维数组，加边即为对应位置的格子赋值。

:::tabs
```c
#define MAXV 100                      // 顶点数上限

int g[MAXV][MAXV];                    // g[u][v] 是 u 到 v 的边，0 表示没有边

// 初始化：n 个顶点的格子全部清零
void init(int n) {
    for (int u = 0; u < n; u++)
        for (int v = 0; v < n; v++)
            g[u][v] = 0;
}

// 加一条 u-v 的边，w 是权值，无权图传 1
void addEdge(int u, int v, int w) {
    g[u][v] = w;
    g[v][u] = w;                      // 有向图只写 g[u][v] = w;
}
```

```cpp
#include <vector>

std::vector<std::vector<int>> g;      // g[u][v] 是 u 到 v 的边，0 表示没有边

// 初始化：n 个顶点的格子全部清零
void init(int n) {
    g.assign(n, std::vector<int>(n, 0));
}

// 加一条 u-v 的边，w 是权值，无权图传 1
void addEdge(int u, int v, int w) {
    g[u][v] = w;
    g[v][u] = w;                      // 有向图删掉这一行
}
```

```java
class MatrixGraph {
    int[][] g;                        // g[u][v] 是 u 到 v 的边，0 表示没有边

    MatrixGraph(int n) {              // 初始化：n 个顶点的格子全部清零
        g = new int[n][n];
    }

    // 加一条 u-v 的边，w 是权值，无权图传 1
    void addEdge(int u, int v, int w) {
        g[u][v] = w;
        g[v][u] = w;                  // 有向图删掉这一行
    }
}
```
:::

### 无向图

在上半部分的无向图中，五个顶点 A，B，C，D，E 按顺序排在行和列上，六条边分别是 $(A,B)$，$(A,C)$，$(B,D)$，$(B,E)$，$(C,D)$，$(D,E)$。矩阵的第一行对应顶点 A，A 只与 B、C 相连，因此 B 列和 C 列为 `1`，其余三列为 `0`，整行写成 `0 1 1 0 0`。B 连着 A，D，E，对应行就是 `1 0 0 1 1`。按同样的规则，其余三行也能直接写出。

不难看出，**无向图的邻接矩阵沿主对角线对称**，右上半区与左下半区完全镜像。这是因为无向边没有方向，A 与 B 相连同时意味着 B 与 A 相连，所以 $M_{ij}$ 和 $M_{ji}$ 总是同步为 `1`，同一条关系在对称位置各记了一遍。主对角线上的元素 $M_{ii}$ 表示顶点与自身的关系，又由于简单图不含自环，这条对角线上便全是 `0`。

### 有向图

再给这六条边加上方向让它变为有向图：A 指向 B，B 指向 D 和 E，C 指向 A，D 指向 C，E 指向 D。其中 $A\to B\to D\to C\to A$ 恰好围成一个四元环。

此时 $M_{ij}=1$ 表示存在一条从 $v_i$ 指向 $v_j$ 的有向边，我们约定**行是起点，列是终点**。A 指向 B，则 A 行 B 列为 `1`。 指向 D 和 E，则 B 行为 `0 0 0 1 1`。C 指向 A，C 行便只有 A 列为 `1`。D 和 E 各自只有一条出边，对应行里也各有一个 `1`。

由于方向单向，A 指向 B 并不代表 B 指向 A，因此 A 行 B 列为 `1`，而 B 行 A 列为 `0`，矩阵不再对称。只有当两个顶点互相指向对方时，$M_{ij}$ 与 $M_{ji}$ 才会同时为 `1`。

从邻接矩阵的行与列还能直接读出顶点的度：

- **无向图**：第 $i$ 行（或第 $i$ 列）中 `1` 的个数，就是顶点 $v_i$ 的度
- **有向图**：第 $i$ 行中 `1` 的个数是 $v_i$ 的**出度**，第 $j$ 列中 `1` 的个数是 $v_j$ 的**入度**。例如图中 B 行有两个 `1`，说明 B 有两条出边，D 列有两个 `1`，说明有两条边指向 D

### 空间和效率

我说，当这种二维表单独出现的时候，你就应该对时空间复杂度敲响警钟了。

事实上的确如此，邻接矩阵用一张二维表同时承载了顶点与边，行列下标对应顶点，格中数值对应边，于是它的时空代价十分明显：

- **空间复杂度**：$O(n^2)$，固定开辟 $n\times n$ 的空间，与实际边数 $e$ 无关
- **判断两顶点是否相邻**：$O(1)$，直接读取 $M_{ij}$ 即可
- **查找顶点 $u$ 的所有邻居**：$O(n)$，需要把第 $u$ 行的 $n$ 个格子完整扫一遍
- **遍历整张图**：$O(n^2)$，需要扫描整个矩阵

因此邻接矩阵适合边数接近 $n^2$ 的**稠密图**。到了边数稀少的稀疏图里，矩阵中绝大多数格子都是闲置的 `0`，空间大量空置不说，遍历时还要在空各自上白白耗费时间。

### 带权图和自环

如果每条边带有权值（距离、费用或容量）的话，**把格中的 `1` 直接换成边的权值 $w$ **即可。给前面那张无向图的六条边标上权值后，矩阵变为：

$$
M_1'=\begin{bmatrix}
0 & 4 & 2 & 0 & 0\\
4 & 0 & 0 & 7 & 1\\
2 & 0 & 0 & 3 & 0\\
0 & 7 & 3 & 0 & 5\\
0 & 1 & 0 & 5 & 0
\end{bmatrix}
$$

这里用 `0` 代表没有边，前提是边权本身不为 `0`。若图中允许出现权值为 `0` 的边就需要换一个不会与合法边权冲突的特殊值（通常取无穷大 $\infty$，代码里用 `INF`）来表示两顶点不相邻。主对角线上的无自环位置也一并填成这个特殊标记。若图中某个顶点存在指向自身的自环，对应的主对角线元素 $M_{ii}$ 就会填入非零值。

邻接矩阵用固定大小的网格换来了 $O(1)$ 的相邻查询，却也把空间死死绑在了 $O(n^2)$ 上。

而要想在稀疏图里省下那些存 `0` 的格子，就得让存储空间跟着实际边数走，这正是邻接表的设计初衷。

## 2. 邻接表存储

邻接矩阵为每一对可能的顶点预留了空位，而**邻接表只为真正存在的边分配节点**：给每个顶点配一条单链表，把与它相连的所有邻居串在这条链表上。

邻接表的结构分为两层：

- **表头节点（`VNode`）**：存放在一维数组中，每个顶点占一格，保存顶点数据 `data` 和头指针 `firstarc`（指向依附于该顶点的第一条边）
- **边表节点（`ArcNode`）**：挂在链表上，每条边记录占一个节点，保存邻居顶点的数组下标 `adjvex`、边权 `weight` 以及指向下一条边的指针 `next`

顶点 $u$ 的所有邻居全都串在以 `head[u].firstarc` 为头的单链表里。三种语言的实现如下：

:::tabs
```c
#include <stdlib.h>
#define MAXV 100

// 边表节点：链表里的一个结点
typedef struct ArcNode {
    int adjvex;               // 边另一端的顶点下标
    int weight;               // 边权，无权图可以删掉
    struct ArcNode *next;     // 下一条边
} ArcNode;

// 表头节点：一个顶点一条边表
typedef struct VNode {
    char data;                // 顶点信息
    ArcNode *firstarc;        // 第一条边，没有边是 NULL
} VNode;
VNode head[MAXV];             // 表头数组，下标就是顶点编号

void addEdge(int u, int v, int w) {   // 头插，O(1)
    ArcNode *arc = (ArcNode *)malloc(sizeof(ArcNode));
    arc->adjvex = v;
    arc->weight = w;
    arc->next = head[u].firstarc;
    head[u].firstarc = arc;
}
```

```cpp
#include <vector>

// 边表节点：链表里的一个结点
struct ArcNode {
    int adjvex;                   // 边另一端的顶点下标
    int weight;                   // 边权，无权图可以删掉
    ArcNode *next = nullptr;      // 下一条边

    ArcNode(int v, int w, ArcNode *n) : adjvex(v), weight(w), next(n) {}
};

// 表头节点：一个顶点一条边表
struct VNode {
    char data;                    // 顶点信息
    ArcNode *firstarc = nullptr;  // 第一条边，没有边是 NULL
};

std::vector<VNode> head;          // 表头数组，下标就是顶点编号

void addEdge(int u, int v, int w) {                  // 头插，O(1)
    head[u].firstarc = new ArcNode(v, w, head[u].firstarc);
}
```

```java
class ArcNode {
    int adjvex;                // 边另一端的顶点下标
    int weight;                // 边权，无权图可以删掉
    ArcNode next;              // 下一条边

    ArcNode(int adjvex, int weight, ArcNode next) {
        this.adjvex = adjvex;
        this.weight = weight;
        this.next = next;
    }
}

class VNode {
    char data;                 // 顶点信息
    ArcNode firstarc;          // 第一条边，没有边是 null
}

class ListGraph {
    VNode[] head;              // 表头数组，下标就是顶点编号

    void addEdge(int u, int v, int w) {       // 头插，O(1)
        head[u].firstarc = new ArcNode(v, w, head[u].firstarc);
    }
}
```

### 无向图

在上半图的无向情况中，顶点 A，B，C，D，E 依次编号为 `0` 到 `4`。第 `0` 行 `data` 为 A，`firstarc` 指向 A 的边表。由于 A 连接着 B(`1`) 和 C(`2`)，链表里依次挂着 `adjvex` 为 `1` 和 `2` 的两个节点，末尾指向空指针。B 连接了 A(`0`)，D(`3`)，E(`4`)，它的边表最长，共有三个节点。整张无向图有 6 条边，五个边表加起来共 12 个边表节点，每条无向边在两个端点的链表里各存了一次。

### 有向图

有向图的邻接表通常只记录从当前顶点出发的**出边**。同样是这 6 条边，加上方向后，A 的边表里只剩 B(`1`)，B 的边表里是 D(`3`) 和 E(`4`)，C 里是 A(`0`)，D 里是 C(`2`)，E 里是 D(`3`)。此时所有边表节点的总数恰好等于有向边的条数 $e$。

但这种单向记录的代价也很明显：顺着顶点 $u$ 的链表能立刻统计出它的**出度**与所有出边，但如果你想知道“有哪些顶点指向了 $u$”（求**入度**或入边），就不得不把所有顶点的链表从头到尾翻一遍。

所以如果业务频繁需要反查入边，可以额外建一张专门存放入边的**逆邻接表**，或者改用下一节的十字链表。

### 空间和效率

邻接表的空间开销完全由顶点数 $n$ 与边数 $e$ 决定，在稀疏图上比邻接矩阵节省得多：

- **空间复杂度**：$O(n+e)$（无向图为 $n$ 个表头加 $2e$ 个边节点，有向图为 $n$ 个表头加 $e$ 个边节点）
- **查找顶点 $u$ 的所有邻居**：$O(\deg(u))$，只需沿着 $u$ 的边表走一遍，无需空扫无关顶点
- **判断 $u$ 和 $v$ 是否相邻**：$O(\deg(u))$，需要在 $u$ 的链表中顺序查找是否存在下标 $v$
- **遍历整张图**：$O(n+e)$

因此邻接表是处理**稀疏图**的主力结构。它的短板在于每次动态申请链表节点会产生指针开销，且节点在堆内存中离散分布，**CPU 缓存命中率不如连续数组**。

### 带权图

处理带权图时直接在边表节点里保留 `weight` 字段存放边权即可，无权图则可省去该字段，只留 `adjvex` 和 `next`。

邻接表把空间复杂度降到了线性级别 $O(n+e)$ 却留下了两个坑：一是有向图无法同时高效查询出边与入边，二是无向图每条边被迫存成两个节点。接下来的十字链表和邻接多重表正是为了分别补齐这两块。

## 3. 十字链表存储

邻接表存有向图时顺着出边走是很顺畅的，但反过来查入边却要扫遍全表。**十字链表（Orthogonal List）**专门面向有向图设计：它把邻接表与逆邻接表合二为一，每条有向弧只存一个节点，同时挂进起点的出边链和终点的入边链里。

十字链表包含两类节点：

- **顶点节点（`VNode`）**：`data` 存放顶点数据，`firstin` 指向以该顶点为弧头（终点）的第一条入弧，`firstout` 指向以该顶点为弧尾（起点）的第一条出弧
- **弧节点（`ArcNode`）**：`tailvex` 和 `headvex` 分别记录弧尾（起点）和弧头（终点）的下标，`tlink` 指向下一条**起点相同**的弧，`hlink` 指向下一条**终点相同**的弧

三种语言的实现如下：

```c
typedef struct ArcNode {              // 弧结点
    int tailvex;                      // 弧尾顶点下标
    int headvex;                      // 弧头顶点下标
    int weight;                       // 权值，无权图可以删掉
    struct ArcNode *hlink;            // 下一条弧头相同的弧
    struct ArcNode *tlink;            // 下一条弧尾相同的弧
} ArcNode;

typedef struct VNode {                // 顶点结点
    char data;                        // 顶点信息
    ArcNode *firstin;                 // 第一条指向它的弧
    ArcNode *firstout;                // 第一条从它出发的弧
} VNode;
VNode head[MAXV];
void addArc(int u, int v, int w) {    // 加一条 u → v 的弧
    ArcNode *arc = (ArcNode *)malloc(sizeof(ArcNode));
    arc->tailvex = u;
    arc->headvex = v;
    arc->weight = w;
    arc->tlink = head[u].firstout;    // 挂进出边链
    head[u].firstout = arc;
    arc->hlink = head[v].firstin;     // 挂进入边链
    head[v].firstin = arc;
}
```

### 怎么读表

先看左上角的两个结构模板：顶点节点分为 `data`、`firstin`、`firstout` 三格，弧节点分为 `tailvex`，`headvex`，`hlink`，`tlink` 四格。左侧一列是顶点数组，A 到 E 对应下标 `0` 到 `4`，每个顶点的 `firstout` 用蓝色箭头串起它的出边链，`firstin` 用橙色箭头串起它的入边链。

弧节点前两格的数字依次是 `(弧尾, 弧头)`。以 `1 → 3`（即 $B\to D$）这个节点为例：

- **横向看出边**：它位于 B(`1`) 这一行，说明起点是 B，它的 `tlink` 水平向右指向 `1 → 4`（$B\to E$），表明从 B 出发的另一条弧指向 E
- **纵向看入边**：它落在下标 `3` 这一列，说明终点是 D，它的 `hlink` 垂直向下指向 `4 → 3`（$E\to D$），表明除了 $B\to D$，还有 $E\to D$ 也指入 D

同一行共享起点，同一列共享终点，每个弧节点都处在横行出边链与竖列入边链的交点上，就像把邻接矩阵里有 `1` 的格子单独挑出来用双向十字指针串成稀疏网格，“十字链表”因此得名。图中的空指针记作 `∧`，例如 `0 → 1` 的 `hlink` 为 `∧`，说明整张图里只有 $A\to B$ 这一条弧指向 B。

### 空间和效率

- **空间复杂度**：$O(n+e)$，共 $n$ 个顶点节点与 $e$ 个弧节点，每条有向弧只存一份
- **查找顶点 $u$ 的所有出边**：$O(\text{出度}(u))$，从 `firstout` 出发沿 `tlink` 链遍历
- **查找顶点 $u$ 的所有入边**：$O(\text{入度}(u))$，从 `firstin` 出发沿 `hlink` 链遍历
- **判断 $u\to v$ 是否有弧**：$O(\text{出度}(u))$（或 $O(\text{入度}(v))$），沿对应链表扫描即可

如果用普通邻接表同时维护出边与入边的话必须额外再建一张逆邻接表把每条弧存两遍，十字链表通过在每个弧节点里多放一个指针消除了数据冗余，并且**让出度与入度的查询具备完全对称的效率**。

### 带权图

遇到带权有向图时，在弧节点里加上 `weight` 字段即可（上方代码已包含该字段），无权图删去 `weight` 即可节省空间。

十字链表虽然兼顾了出边和入边，但节点指针较多，手写实现容易写错指针指向。在算法竞赛与高频遍历场景中，大家往往更青睐用纯数组模拟链表的**链式前向星**。

## 4. 链式前向星存储

OK，什么是“链式前向星”？明明是在讲数据结构，怎么突然冒出了一个像天文学一样的词？而且前面已经有了 $O(n+e)$ 的邻接表，干嘛还要再造一套结构出来？

让我们先把这两个疑问解开。

### 名字是怎么来的？为什么有了邻接表还要用它？

**1. 什么是“星（Star）”和“前向星（Forward Star）”**

在图论与网络流文献（如 Ahuja、Magnanti 和 Orlin 合著的经典教材 *Network Flows*）中，把一个顶点 $u$ 以及所有与它相连的边画在一起，形状就像一颗向四周放射光芒的星星，数学家便把这组关联边的集合称为顶点 $u$ 的 **星（Star）**。

到了有向图里，只由顶点 $u$ **向外发出**的所有出边构成的集合，就叫做 $u$ 的 **前向星（Forward Star）**。反过来，所有指入 $u$ 的入边集合则叫 **后向星（Backward Star）**。因此，“前向星”原本指的就是“用连续数组记录每个顶点的出边集合”，跟天上的星星没有任何关系。

**2. 指针版邻接表有什么痛点**

第 2 节讲的邻接表在逻辑上已经很完善了，但在实际写代码（尤其是 C/C++ 高性能计算与算法竞赛）时，用 `malloc` 或 `new` 动态申请链表节点有两个不大不小的麻烦：

- **动态内存分配慢且容易泄漏**：一张图如果有 $5\times 10^5$ 条边，每加一条边就调用一次 `malloc` 或 `new`，向操作系统申请五十万次零碎的堆内存，光分配内存的时间就可能让程序超时，多组测试数据时，还得挨个 `free` 释放，稍微漏掉一点就会内存泄漏
- **内存地址碎片化，缓存不友好**：指针链表的各个节点散落在堆内存的各个角落，顺着指针跳转时 CPU 缓存频繁失效（Cache Miss）

那要是改用 C++ 的 `std::vector<Edge> adj[MAXV]` 呢？这虽然避开了手写指针，但每个 `vector` 在边数不断增加时会触发动态扩容（重新申请两倍空间并拷贝旧数据），不仅有额外的时间开销，有时还会浪费近一半的预留内存。

**3. 用“数组房间号”代替“内存指针”**

既然我们通常事先知道一张图最多有多少条边（比如题目给出 $e \le 10^5$），那干脆一开始就直接开好一个长度为 $e$ 的大数组，把它当成一排编好门牌号（下标 `0, 1, 2, ...`）的空房间：

- 每新来一条边，就按顺序住进下一个空房间里
- 原本单链表里用来存“下一个节点内存地址”的指针 `ArcNode *next`，现在改成存“下一个节点所在的数组房间号” `int next`

这就是之前说过的**静态链表（用数组模拟链表）**的核心思想。为了看清它是怎么一步步演化出来的，我们先看最初不含链表的**前向星**，再看加上 `next` 下标之后的**链式前向星**。

### 第一步：前向星（排序 + 连续区间）

最初的前向星不用指针也不用链表，只用一个**边数组**加一个 **`head` 数组**。

它的想法非常朴素：既然要找每个顶点的所有出边，不如先把读入的所有边按**起点编号**从小到大排个序。排完序后从同一个起点出发的所有边在数组里自然就挨在一起，聚成了连续的一段，这时再用 `head[u]` 记下顶点 $u$ 那一段从哪个下标开始就行：

- **边数组**：只存终点 `to` 和权值 `w`，起点编号无需重复存储，由所在区间决定
- **`head` 数组**：长度比顶点数多开一格，`head[u]` 记录顶点 $u$ 第一条边的下标，最后一格 `head[n]` 存入边总数 $e$ 作为收尾哨兵
- **定位邻居**：顶点 $u$ 的所有出边，恰好对应边数组中下标从 `head[u]` 到 `head[u+1] - 1` 的连续切片

前向星的内存完全连续，局部性极好，建好后遍历飞快（现代工业界图计算框架常用的 **CSR，压缩稀疏行** 格式，底层就是这个结构）。但它在需要边读入边建图的场景里有个明显的软肋：**必须先把所有边读齐，再花 $O(e\log e)$ 的时间按起点排序**，而且一旦排好序，后续就没法低成本地动态插入新边，因为多插一条边就得把数组后面的元素整体往后挪。

### 第二步：链式前向星（用数组下标串成链表，省掉排序）

那怎么才能既保留前向星“全放在一个连续数组里”的好处，又省掉 $O(e\log e)$ 的排序，实现来一条边就 $O(1)$ 存好一条边呢？

答案就是把第 2 节的**邻接表**搬进**静态数组**里，给前向星加上链表，变成**链式前向星**。

它不再强求同一个起点的边在数组里物理相邻，而是不管三七二十一，每读入一条新边就直接塞到边数组的末尾（下标 `cnt` 的位置），再给每条边多配一个整数 `next`，专门记录“与我同一个起点的上一条边住在数组第几号房”：

- **`head[u]`**：相当于邻接表里的表头指针 `firstarc`，记录顶点 $u$ 目前最新加入的那条出边在边数组中的下标；一开始一条边都没有，全部初始化为 `-1`
- **边数组 `e[i]`**：相当于邻接表里的边表节点 `ArcNode`，每格存放终点 `to`、边权 `w` 和 `next` 三个整数。其中 `next` 记录下一条同起点边的数组下标，`-1` 代表链表到底了（相当于指针里的 `NULL`）
- **起点隐式表达**：每条边的起点无需单独保存，它挂在哪个 `head[u]` 的链上，起点就是谁

你可以把指针版邻接表和链式前向星做个一对一的对照，就会发现它们在逻辑上完全是同一个东西：

| 逻辑角色 | 指针版邻接表（第 2 节） | 链式前向星（数组模拟版） |
| --- | --- | --- |
| 空指针标记 | `NULL` / `nullptr` | `-1`（或 `0`） |
| 顶点 $u$ 的链表头 | 指针 `head[u].firstarc` | 数组下标 `head[u]` |
| 申请一条新边 | `new ArcNode(...)` | 直接占用数组下一格 `e[cnt++]` |
| 边指向的终点与权值 | `arc->adjvex`、`arc->weight` | `e[i].to`、`e[i].w` |
| 跳向同一顶点的下一条边 | `arc = arc->next` | `i = e[i].next` |

插入新边时同样采用**头插法**，只需两步：先让新边的 `next` 记下当前 `head[u]` 里存的老头目下标，再把 `head[u]` 更新为新边自己的房间号 `cnt`。这样新加的边就排在了顶点 $u$ 出边链的最前端：

以顶点 B（下标 `1`）为例：插入 $B\to E$ 之前，`head[1]` 指向下标 `1` 的 $B\to D$。新边 $B\to E$ 追加到边数组下标 `2` 的位置，令它的 `next = 1`，再把 `head[1]` 改为 `2`，链表就变成了 $B\to E \longrightarrow B\to D$。

每次加边都是严格的 $O(1)$，既省去了排序，也不会挪动已有的边。三种语言的实现如下：

```c
#define MAXV 100                       // 顶点数上限
#define MAXE 10000                     // 边数上限

int head[MAXV];                        // u 的第一条边下标，-1 表示没有
struct Edge { int to, w, next; } e[MAXE];
int cnt;                               // 边数组已经用到的位置

void init(int n) {
    for (int i = 0; i < n; i++) head[i] = -1;
    cnt = 0;
}

void addEdge(int u, int v, int w) {    // 头插，O(1)
    e[cnt].to = v;
    e[cnt].w = w;
    e[cnt].next = head[u];
    head[u] = cnt++;
}

void visit(int u) {                    // 遍历 u 的所有出边
    for (int i = head[u]; i != -1; i = e[i].next) {
        int v = e[i].to;
    }
}
```

```java
class ForwardStar {
    int[] head;                        // u 的第一条边下标，-1 表示没有
    int[] to, w, next;                 // 边数组
    int cnt;                           // 已经用到的位置

    ForwardStar(int n, int m) {
        head = new int[n];
        for (int i = 0; i < n; i++) head[i] = -1;
        to = new int[m]; w = new int[m]; next = new int[m];
        cnt = 0;
    }

    void addEdge(int u, int v, int weight) {     // 头插，O(1)
        to[cnt] = v;
        w[cnt] = weight;
        next[cnt] = head[u];
        head[u] = cnt++;
    }
    void visit(int u) {                // 遍历 u 的所有出边
        for (int i = head[u]; i != -1; i = next[i]) {
            int v = to[i];
        }
    }
}
```

从 `head[1] = 2` 出发，先访问下标 `2` 的 $B\to E$，读出它的 `next = 1`，跳到下标 `1` 访问 $B\to D$，再读出 `next = -1`，遍历结束。访问顺序是先 $B\to E$ 后 $B\to D$，与加边顺序恰好相反，原因就在于每次头插都把新边塞到了链表头。

> [!NOTE]
> 实际上绝大多数图论算法只关心连通性与边权，遍历的先后次序不影响结果，遇到少数要求按输入顺序输出邻居的题目，只需把边倒序读入，或者改用 `std::vector` 尾插即可。


### 空间和效率

- **建图时间**：$O(e)$，每条边头插一次，无需排序
- **单次加边**：$O(1)$
- **空间复杂度**：$O(n+e)$，仅用固定大小的静态数组，零动态内存分配
- **查找顶点 $u$ 的所有出边**：$O(\text{出度}(u))$
- **遍历整张图**：$O(n+e)$

相比指针版邻接表，链式前向星把所有节点紧凑地排在连续数组里，彻底避开了 `malloc/new` 的系统调用开销与指针跳转的缓存缺失，代码不到二十行，常数极小，因而在算法竞赛中几乎成了默认标配。它的局限主要有三点：一是只能顺着出边查，无法反查入边，二是边一旦追加进数组就不便物理删除，三是存储无向图时必须拆成两条方向相反的有向边，边数组容量需要按 $2e$ 开辟。

> [!TIP]
> 边数组下标从 `0` 开始、用 `-1` 表示空链是一种写法（在网络流算法中成对的正反向边可通过下标异或 `i ^ 1` 直接互找，十分顺手），也有人习惯下标从 `1` 开始、用 `0` 表示空链，这样全局数组默认初始化就是空链，省去了手动填 `-1` 的循环。两种写法本质完全一致。

### 带权图

边数组结构体中自带 `w` 字段，带权图直接存入权值，无权图删去或忽略该字段即可。存无向图时，每读入一条无向边 $(u,v,w)$，连续调用两次 `addEdge(u, v, w)` 和 `addEdge(v, u, w)` 即可。

链式前向星是静态数组模拟链表的典范，但在处理无向图时，它和普通邻接表一样得把每条边拆成正反两份。如果你希望无向图的每条边在内存里只占一个节点，同时又能从两个端点自由访问和删除，就需要用到下一节的邻接多重表。

## 5. 邻接多重表存储

普通邻接表存无向图时，一条边 $(u,v)$ 会在 $u$ 和 $v$ 的链表里各生成一个节点；一旦要删除这条边，不仅得在 $u$ 的链表里找到 $v$ 把它摘掉，还得再去 $v$ 的链表里找到 $u$ 再摘一次。**邻接多重表（Adjacency Multilist）**专门面向无向图设计：它让一条无向边只存一个节点，并利用两个指针把这同一个节点同时挂进两个端点的边链表里。

整套结构同样由两类节点组成：

- **顶点节点（`VNode`）**：`data` 存放顶点信息，`firstedge` 指向依附于该顶点的第一条边
- **边节点（`ENode`）**：`ivex` 和 `jvex` 记录这条边两个端点的下标，`ilink` 指向下一条依附于端点 `ivex` 的边，`jlink` 指向下一条依附于端点 `jvex` 的边

遍历时的技巧在于**认清当前顶点在这条边里的身份**：从 `firstedge[u]` 出发到达某个边节点后，先看 $u$ 等于 `ivex` 还是 `jvex`。若 $u == \text{ivex}$，下一步就顺着 `ilink` 走，若 $u == \text{jvex}$，下一步就顺着 `jlink` 走。如此一来哪怕每条边只有唯一节点，每个顶点依然能顺着属于自己的指针链逛遍所有关联边。

三种语言的实现如下：

```c
typedef struct ENode {               // 边结点
    int ivex;                        // 边的一个端点
    struct ENode *ilink;             // 下一条依附于 ivex 的边
    int jvex;                        // 边的另一个端点
    struct ENode *jlink;             // 下一条依附于 jvex 的边
} ENode;
typedef struct VNode {               // 顶点结点
    char data;                       // 顶点信息
    ENode *firstedge;                // 第一条依附于它的边
} VNode;
VNode adj[MAXV];
void addEdge(int u, int v) {         // 插入一条无向边
    ENode *e = (ENode *)malloc(sizeof(ENode));
    e->ivex = u; e->jvex = v;
    e->ilink = adj[u].firstedge;
    adj[u].firstedge = e;
    e->jlink = adj[v].firstedge;
    adj[v].firstedge = e;
}
```

1. 到达 5 号边 $DE$：此时 D(`3`) 位于 `ivex` 一侧，因此看 `ilink`，顺着 `ilink = 3` 跳到 3 号边
2. 到达 3 号边 $BD$：在这条边里，`ivex` 是 B(`1`)，D(`3`) 落在了 `jvex` 一侧，因此改看 `jlink`，顺着 `jlink = 2` 跳到 2 号边
3. 到达 2 号边 $CD$：D(`3`) 依然在 `jvex` 一侧，查看它的 `jlink` 为 `-1`，整条链遍历完毕

### 空间和效率

- **空间复杂度**：$O(n+e)$，共 $n$ 个顶点节点与 $e$ 个边节点，每条无向边严格只存一份
- **查找顶点 $u$ 的所有关联边**：$O(\deg(u))$，沿 $u$ 的专属边链走到底
- **判断 $u$ 和 $v$ 是否相邻**：$O(\deg(u))$，扫描 $u$ 的边链
- **删除一条无向边或给边打访问标记**：非常顺手，因为同一条边在内存中只有唯一实体，打标记无需同步两处，删边也只需在两个端点的链上修改指针即可

与存无向图的普通邻接表相比，邻接多重表把边节点数量从 $2e$ 砍半到了 $e$（每个节点有 2 个指针，因此全图总指针数依然是 $2e$）。它的代价是遍历逻辑比单链表多了一步分支判断，代码略显绕手，且仅适用于无向图。

### 带权图

带权无向图只需在边节点中补充 `weight` 字段，无权图保留 `ivex`、`ilink`、`jvex`、`jlink` 四个核心字段即可。

前面五种结构无论怎么变形，核心目标都是“给定一个顶点，快速找到它的邻居”。而最后一种**边集数组**索性放下了这个执念，换成了纯粹以“边”为中心的视角。

```c
#define MAXE 10000

typedef struct Edge {
    int begin;                  // 起点下标
    int end;                    // 终点下标
    int weight;                 // 权值

Edge edges[MAXE];
int cnt = 0;

void addEdge(int u, int v, int w) {      // 追加一条边
    edges[cnt].begin = u;
    edges[cnt].end = v;
    edges[cnt].weight = w;
    cnt++;
}
```

### 适用场景与效率

边集数组没有为“按顶点查邻居”做任何索引：想找顶点 $u$ 的所有邻居，或者判断 $u$ 与 $v$ 是否相邻，都必须把整个数组从头扫到尾，时间复杂度为 $O(e)$。

但在另一类**按边驱动**的算法里，它却如鱼得水：

- **Kruskal 最小生成树算法**：核心步骤是把全图所有边按权值从小到大排序，再配合并查集逐条尝试合并。边集数组天然就是一块连续的边表，直接调用标准库排序即可。若用邻接表反而得先把散落在各条链表里的边重新收集出来
- **Bellman-Ford 最短路算法**：每一轮松弛操作都只需无差别地遍历全图所有边，边集数组正好一条不多，一条不少，顺序扫过时缓存极其友好
- **离线边处理与简单读写**：结构体紧凑，按数组下标即可直接修改或过滤某条边，无需维护任何链表指针

例如把上面那张图的边集数组按 `weight` 升序排列后：

| 下标 | 0 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- | --- |
| 边 | B→E | C→A | D→C | A→B | E→D | B→D |
| weight | 1 | 2 | 3 | 4 | 5 | 7 |

Kruskal 算法只需从下标 `0` 顺着往后扫，数组的物理顺序就是算法的贪心考察顺序。

空间上，边集数组只需 $O(e)$ 的边表空间（若需保存顶点自身属性，再额外配一个长度为 $n$ 的顶点数组）。它把维护邻居索引的开销降到了零，也将按顶点查询的代价留给了全表扫描。

## 7. 六种存储结构的横向对比

这六种经典存储结构每一种都是在**空间开销，查询方向，增删代价与实现复杂度**之间做出的权衡：

| 存储结构 | 空间复杂度 | 找顶点 $u$ 的邻居 | 判断 $u,v$ 相邻 | 典型适用场景 |
| --- | --- | --- | --- | --- |
| **邻接矩阵** | $O(n^2)$ | $O(n)$ | $O(1)$ | 稠密图、频繁判断两点是否相连、Floyd 最短路 |
| **邻接表** | $O(n+e)$ | $O(\deg(u))$ | $O(\deg(u))$ | 稀疏图的通用存储、DFS / BFS / Dijkstra |
| **十字链表** | $O(n+e)$ | 出边 $O(\text{出度})$ / 入边 $O(\text{入度})$ | $O(\text{出度})$ | 需要同时高频查询出边与入边的有向图 |
| **链式前向星** | $O(n+e)$ | $O(\deg(u))$ | $O(\deg(u))$ | 算法竞赛、静态图高频遍历、网络流 |
| **邻接多重表** | $O(n+e)$ | $O(\deg(u))$ | $O(\deg(u))$ | 需要频繁删边或标记边的无向图（如欧拉回路） |
| **边集数组** | $O(e)$ | $O(e)$ | $O(e)$ | 直接按边处理的算法（Kruskal、Bellman-Ford） |

工程与算法设计中没有万能的存储结构，选型的唯一标准是**接下来要在这张图上跑什么操作**。把顶点与边稳妥地安放进内存之后，下一步就是在这些错综相连的节点之间寻找路径，这便是图的遍历与图论算法的事情了。
