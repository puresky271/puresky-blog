## Nginx 的进程模型

Nginx 启动后会作为后台进程一直运行。想知道它到底开了几个进程，可以用 `ps -ef` 配合 `grep` 把 nginx 相关的进程筛出来：

```bash
ps -ef|grep nginx
```

:::photo
![在 WSL 的 Ubuntu 22.04 上执行 ps -ef | grep nginx 的输出。一个 root 运行的 master，下面挂着 16 个 www-data 运行的 worker](./images/post-20261108-2/ps-ef-grep-nginx.png)
:::

`ps -ef` 的每一行是一个进程。从左边开始依次是运行用户，PID，PPID，CPU 占用，启动时间，终端，累计 CPU 时间和完整的启动命令。

具体而言：

- Master 由 `root` 运行。绑定 80 端口这类操作需要特权
- Worker 由配置里的非特权用户运行，Ubuntu 默认是 `www-data`
- 所有 Worker 的 PPID 都等于 Master 的 PID，说明它们都是 Master 的子进程

> [!NOTE]
>为什么 Worker 非得是 16 个？Ubuntu 的 `/etc/nginx/nginx.conf` 里写的是 `worker_processes auto`，Nginx 会按 CPU 核心数决定进程数，这台机器的 WSL 正好有 16 个核。


也可以直接看进程树：

```bash
pstree -p $(pgrep -xo nginx)
```

:::photo
![同样的 Nginx 进程用 pstree 画出来的样子，master 后面挂着 16 个 worker](./images/post-20261108-2/pstree-nginx.png)
:::

`pgrep -xo nginx` 找出最早启动的那个 nginx 进程，也就是 Master。`pstree -p` 再把它的子进程树画出来，括号里的数字就是 `ps` 输出里的 PID，两边的编号一一对应。

换个角度：前面两条命令都是按进程名找进程，`lsof -i:80` 则是按端口找进程，可以直接看到是谁在监听 80 端口：

```bash
lsof -i:80
```

:::photo
![在 WSL 的 Ubuntu 22.04 上执行 lsof -i:80 的输出。COMMAND 一列全是 nginx，master 的 USER 是 root，worker 都是 www-data，NAME 都是 *:http (LISTEN)](./images/post-20261108-2/lsof-i-80.png)
:::

输出里 `COMMAND` 全是 `nginx`，Master 那一行的 `USER` 是 `root`，Worker 都是 `www-data`，`NAME` 都是 `*:http (LISTEN)`，说明 80 端口正被它们占着。`lsof` 的全名是 list open files，Linux 里套接字也是一种文件描述符，所以端口占用也能被它列出来。如果在普通用户下执行，看不到别的用户的进程，输出可能是空的，记得前面加 `sudo`。

注意结果里一共有 17 个进程，并不只有 Master 一个。监听 Socket 是 Master 在启动时打开的，之后 fork 出来的 Worker 会继承它，所以每个 Worker 手里都握着同一个监听 Socket。每个进程在输出里占两行，`6u` 是 IPv4 的监听，`7u` 是 IPv6 的监听，16 个 Worker 加起来就是 34 行。

（这个现象在后面讲到多个 Worker 共同接收连接时还会再提到）

### 一个 Master，多个 Worker

Nginx 最经典的进程架构是 Master-Worker 模型，官方文档把它叫作 master and worker processes[^1]。它把整个服务器的工作分成两类：

- 管理工作：启动，停止，监控和管理工作进程
- 业务工作：接收客户端连接，处理 HTTP 请求，返回响应

由此可以总结出几条规律：

- Master 进程通常只有一个
- Worker 进程可以有一个或多个，由 `worker_processes` 决定
- Master 不直接处理日常 HTTP 请求
- Worker 才是真正处理请求的核心
- 每个 Worker 通常是一个单线程的事件循环，可以同时盯住大量连接

以上这些也是 Nginx 和很多传统 Web 服务器在设计思路上最大的区别。

### Master ：进程管理器

Master 是整个 Nginx 实例的管理者。它的核心职责不是处理 HTTP 请求，而是维护整个实例的运行状态，主要有四件事：

- 读取并解析 `nginx.conf` 以及其中引用的其他配置文件，决定开多少个 Worker，监听哪些端口
- 根据 `worker_processes` 创建对应数量的 Worker 进程
- 监控 Worker 的运行状态。某个 Worker 异常退出时，Master 会检测到并重新创建一个，避免实例失去对应的处理能力
- 接收控制信号。执行 `nginx -s reload` 时，就是 Master 收到重新加载的信号后去协调新旧 Worker 的切换

所以 Master 更像一个进程管理器。它负责组织和维护工作进程而不是亲自接待每一个用户请求。Worker 才是真正处理请求的地方，它是整个进程模型里最重要的业务执行单元，前面几节讲到的事件驱动，非阻塞 I/O 和 epoll 主要就是在 Worker 里发挥作用。

### 一个 Worker 能处理多少连接

假设配置是这样的：

```nginx
worker_processes 4;

events {
    worker_connections 1024;
}
```

这表示启动 4 个 Worker，每个 Worker 最多配置 1024 个同时打开的连接。所以理论上的连接数上限是 4 × 1024 = 4096。

然而这里有一个很容易被忽略的细节：**`worker_connections` 数的是 Worker 能打开的连接总数，不只是客户端连接[^2]。**做反向代理（我们会在之后的篇章里面讲到这个）时，一条客户端请求要占两条连接，一条是客户端到 Nginx，另一条是 Nginx 到后端服务器，如图 2 所示：

### 为什么一个 Worker 只用一个线程

很多服务器会用多线程模型，让多个线程同时处理不同的任务。但 Nginx 的 Worker 常见形态是：**一个进程，一个事件循环线程，多个网络连接。**

这样设计有几显然的好处：

- 减少多线程之间的锁竞争
- 减少线程上下文切换
- 避免多个线程同时修改共享数据带来的复杂性
- 让事件处理流程更加可预测

当然这不代表 Nginx 完全不用线程。它提供了 `thread_pool`，可以把可能阻塞 Worker 的文件读写任务交给线程池去等，如图 3 所示[^3]：

那它们会不会打起来，~~谁是好的谁是坏的~~？

不会，因为这里有一个配置项 `accept_mutex`：打开它时 Worker 会轮流竞争接受新连接的机会，避免多个 Worker 同时被唤醒却只有一个能成功接受连接。

> [!NOTE]
> 不过现代 Linux 的 epoll 已经支持 `EPOLLEXCLUSIVE`，Nginx 在这种环境下通常不需要打开它，当前版本的默认值也是 `off`[^4]。


## 额外出现的缓存进程

除了 Master 和 Worker，Nginx 在特定配置下还会创建辅助进程。比较典型的是两个：

- Cache Loader，缓存加载进程
- Cache Manager，缓存管理进程

它们只在配置了磁盘缓存之后才会出现。Cache Loader 负责在启动阶段把磁盘上已有缓存的元信息加载进内存，加载完就退出。Cache Manager 则负责在运行期间周期性地检查缓存，清理过期或者超出大小限制的缓存文件[^5]。

| 进程 | 职责 | 工作方式 |
| --- | --- | --- |
| Cache Loader | 加载已有缓存的元信息 | 启动阶段工作，完成后退出 |
| Cache Manager | 管理和清理缓存 | 周期性运行 |

1. Master 收到 HUP 信号
2. Master 检查新配置的语法，并尝试打开新的日志文件和监听端口
3. Master 启动一批使用新配置的 Worker
4. 旧 Worker 不再接受新连接，但会把手头已有的请求处理完，所以新旧 Worker 会短暂并存
5. 旧 Worker 处理完请求后退出，重载完成

如果新配置检查失败，Master 会放弃这次变更，原有 Worker 继续按旧配置工作。这也是 Nginx 能做到平滑配置更新的关键[^6]。

快速总结一下：Master 管进程，Worker 管连接，缓存进程按需出现，reload 只是换一批 Worker。

## 服务启停

前面都是一步步手动执行 `nginx` 来启动，实际部署时这样未免有些笨，更常见的做法是把 Nginx 交给 systemd 管理。systemd 是 Linux 上负责服务启动和监控的系统管理器，Ubuntu 上的 Nginx 安装包会自动注册一个 `nginx.service`，启动，停止，重启，开机自启都可以用 `systemctl` 完成。

最常用的几条命令：

| 命令 | 作用 |
| --- | --- |
| `sudo systemctl start nginx` | 启动 Nginx |
| `sudo systemctl stop nginx` | 停止 Nginx |
| `sudo systemctl restart nginx` | 重启 Nginx |
| `sudo systemctl reload nginx` | 重新加载配置 |
| `sudo systemctl status nginx` | 查看运行状态 |
| `sudo systemctl enable nginx` | 设置开机自动启动 |
| `sudo systemctl disable nginx` | 取消开机自动启动 |

这里具体讲一下几个操作里最容易混的两对：start 和 restart，restart 和 reload

- start：让 Nginx 开始运行。如果服务已经在运行，再执行一次通常不会多开一套实例
- stop：停止服务，不再接受新的连接
- restart：先停止当前服务，再重新启动
- reload：让 Nginx 读取最新配置，在条件允许时平滑地切换 Worker，不直接中断正在处理的请求

> [!TIP]
> 改完配置之后优先用 reload 是一个好习惯。


### 为什么改配置用 reload 而不是 restart

哦拜托，热重载相较于直接重开肯定是有它的好处的。

假设网站正在运行，用户还在请求页面，这时你修改了配置，如果执行 `sudo systemctl restart nginx`，服务会被整个停掉再拉起来，中间有一小段时间无法响应，正在处理的请求也可能被掐断，那用户大概就得来问候你了，对吗（

但如果你执行 `sudo systemctl reload nginx`，Master 会先读取新配置并检查语法和资源，比如配置格式，日志文件，监听端口这些。检查通过后启动一批用新配置的 Worker，旧 Worker 不再接新连接，把手上的请求处理完再退出，也就是前面“一次 reload 到底发生了什么”那套流程（图 6）。新配置检查失败的话，Master 会保留旧配置继续工作，服务不会直接挂掉。

这也是生产环境里尽量用 reload 的原因：**改配置不该把正在服务的请求一起中断掉。**

### 用 nginx -s 直接给主进程发信号

除了 systemctl，Nginx 自己也提供了控制命令：

```bash
sudo nginx -s stop
sudo nginx -s quit
sudo nginx -s reload
sudo nginx -s reopen
```

| 命令 | 对应操作 | 含义 |
| --- | --- | --- |
| `nginx -s stop` | 快速停止 | 尽快终止服务 |
| `nginx -s quit` | 优雅停止 | 完成当前请求后退出 |
| `nginx -s reload` | 重载配置 | 读取新配置并平滑切换 |
| `nginx -s reopen` | 重新打开日志 | 重新打开日志文件 |

`-s` 的意思是向 Nginx 主进程发送控制信号，比如 reload 对应 Linux 的 `SIGHUP`，stop 对应 `SIGTERM`，quit 对应 `SIGQUIT`，reopen 对应 `SIGUSR1`。

两种方式的定位不太一样：`systemctl` 是通过操作系统的服务管理器管理整个服务，`nginx -s` 是直接给主进程发信号。日常在 Ubuntu 上建议先用 `systemctl` 管理服务，改完配置先用 `nginx -t` 检查语法。

> [!TIP]
> 改配置的固定动作：先 `sudo nginx -t` 确认语法没问题，再 `sudo systemctl reload nginx` 生效。

例如你现在把服务停掉，再访问 `localhost`，刚才的欢迎页就没有了，浏览器会提示无法访问：

```bash
sudo systemctl stop nginx
```

这也说明 Nginx 已经不再监听 80 端口。想确认服务状态可以执行：


`Active:` 那一行会变成 `inactive (dead)`。需要它继续工作的时候，再 `sudo systemctl start nginx` 启动起来就好。

> [!NOTE]
> 如果你在 WSL 里执行 `systemctl` 提示 systemd 没有运行，说明当前 WSL 没有启用 systemd。可以先试试 `sudo service nginx start`，`sudo service nginx stop`，`sudo service nginx reload` 这几条，能不能用取决于 WSL 的初始化配置。
