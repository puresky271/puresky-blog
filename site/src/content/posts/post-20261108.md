在 Nginx 官方博客的开头，有这么一段话：

*In the early 2000s, an exciting journey began – one that would shape the fabric of the internet as we know it today. For those of us who have been using NGINX since its early days, it’s been incredible to witness how an open source tool originally created to solve the C10K problem has grown into a cornerstone of modern web infrastructure.*[^1]

Nginx 可以说是目前最流行的 Web 服务器之一。它最初并不是为了成为互联网基础设施中的重要组件而诞生的，而是为了处理一个非常具体的工程问题：**如何让一台服务器同时处理成千上万个网络连接，而不消耗大量计算资源？**

在 20 世纪 90 年代，互联网开始快速发展，网站访问量不断增加。当时非常流行的 Web 服务器是 [Apache HTTP Server](https://httpd.apache.org/)。

> [!NOTE]
> Apache（阿帕奇）指的是 **Apache 软件基金会（Apache Software Foundation，ASF）**[^2]及其旗下的一系列开源软件项目。它是互联网基础设施发展史上非常重要的组织之一。
>
> 需要区分：
> - Apache HTTP Server：一个具体的 Web 服务器软件。
> - Apache Software Foundation：管理和孵化大量开源项目的非营利组织。
> - Apache 项目：Apache 基金会旗下的各种开源软件。
>
> Apache 最初因 Web 服务器而闻名，后来发展成了一个庞大的开源软件生态系统。

Apache 在当时是一款非常成熟的服务器软件，但当时它有一个问题：**当大量用户同时访问网站时，服务器需要管理越来越多的并发连接，而传统的处理方式会产生较大的资源开销。**这也就涉及一个非常经典的计算机网络问题：**C10K**。

> [!NOTE]
> **C10K Problem（C10K 问题）**
>
> C10K 中的 C 代表 Concurrent Connections（并发连接），10K 代表 10,000。[^3]
>
> 它提出的问题是：
> **一台服务器如何高效地同时处理 10,000 个客户端连接？**
>
> 假设有 10,000 个用户同时打开一个网页，即使很多用户并没有持续发送请求，服务器仍然需要维护它们的网络连接。如果服务器采用比较传统的处理方式，为每个连接分配一个独立的进程或线程，那么：
>
> - 每个进程或线程都会消耗内存。
> - 线程之间的切换会产生上下文切换开销。
> - 大量连接可能导致系统资源被耗尽。
> - 很多线程实际上只是在等待网络数据，却仍然占据着系统资源。
>
> 这就像一家餐厅为了服务 10,000 名顾客，直接雇佣 10,000 名服务员，每个人只负责一张桌子。顾客吃饭的时候，服务员大部分时间都在等待，但餐厅必须一直支付这些服务员的管理成本。

而 Nginx 正是为解决这一问题而生的。它由伊戈尔·赛索耶夫（Igor Sysoev）开发，最初用来满足包括俄罗斯大型门户网站 Rambler.ru 在内的多个站点的需要，第一个公开版本 0.1.0 发布于 2004 年 10 月 4 日[^4]。

按官方的说法，事件驱动架构让 Nginx 可以在现代硬件上扩展到数十万个并发连接[^5]。此后 Nginx 的市场份额逐步上升，最高的时候一度达到 40% 左右[^6]。时至今日，Nginx 依旧是最主流的 Web 服务器之一，像国内的百度，京东，新浪，网易，腾讯，淘宝等都在使用 Nginx。

## Nginx 的核心工作架构

在理解 Nginx 之前，我们需要先区分两个概念：

- 并发连接（Connection）：客户端和服务器之间建立的网络通信关系
- 并发请求（Request）：客户端通过连接向服务器发送的具体任务

它们并不是一回事。例如你打开了一个网站，浏览器可能与服务器建立一个 HTTP 长连接，然后通过这个连接请求网页，以及网页引用的图片，样式表和脚本，**即使你暂时没有操作，连接也可能仍然保持着。**

因此服务器面临的一个问题是：**大量客户端可能同时保持连接，但它们并不一定同时向服务器发送请求。**服务器需要维护这些连接，但没必要为每一个连接安排一个一直等待的工作线程。这就是 C10K 问题的核心矛盾：**如何用有限的系统资源，管理大量同时存在的连接？**

## 传统解决方案：一个连接对应一个线程

我们先看一种容易理解的设计。

假设服务器每收到一个客户端连接，就创建一个线程专门负责它。

整个工作过程大致是这样：

1. 客户端 A 连接服务器
2. 服务器创建线程 A
3. 线程 A 等待客户端发送数据
4. 客户端 B 连接服务器
5. 服务器创建线程 B
6. 线程 B 等待客户端发送数据

这个模型非常直观，一个连接配一个线程，写起来也简单。但它有三个绕不开的问题：

### 问题一：线程本身需要占用内存

每个线程都需要自己的线程栈和线程控制信息，线程栈通常要预留几百 KB 到几 MB 的地址空间，内核还要为每个线程维护调度相关的数据结构。当连接数量不断增加时，线程数量也随之增加，内存消耗自然越来越大。

### 问题二：上下文切换开销

CPU 核心数量有限，操作系统却要调度大量线程。当 CPU 从线程 A 切换到线程 B 时，需要保存线程 A 的执行现场，再恢复线程 B 的执行现场，这个过程叫作上下文切换（Context Switch）。线程越多，调度和切换的管理成本就越高。

### 问题三：大量线程实际上都在等待

假设线程 A 正在等待客户端发送数据，而客户端可能需要 5 秒钟才会发来下一条数据。

在这 5 秒钟里，线程 A 没有做任何有意义的计算，却一直占着线程栈，也一直参与操作系统的调度。

---

于是我们自然会产生一个想法：

**能不能不要让线程一直等待，而是在真正有事情发生的时候才去处理它？**

这就是事件驱动模型的出发点。

## 事件驱动模型：有事情发生时，才安排处理

我们换一种思路。

假设服务器仍然有 A，B，C 三个客户端，但这次不再为每个客户端创建一个专属线程，而是让一个工作线程同时管理三个连接。

那么现在，这个线程的工作方式变成了：

1. 看看 A，B，C 三个连接上有没有网络事件
2. 如果 A 有数据到达，就处理 A
3. 如果 B 没有数据，就先不管 B
4. 如果 C 有数据到达，就处理 C
5. 处理完这一批事件，继续等待下一批

你可以看到，现在线程不再绑定某一个客户端，而是负责处理所有客户端产生的事件。

我们把这种设计称为**事件驱动（Event-Driven）**。它的核心思想是：

*不需要持续关注每一个连接，而是等待事件通知，只在事件发生的时候执行对应的处理逻辑。*

### 什么是事件

在网络服务器中，常见的事件包括：

| 事件 | 含义 |
| --- | --- |
| 连接到达 | 有新的客户端希望建立连接 |
| 数据可读 | 客户端发送了数据，服务器可以读取 |
| 数据可写 | 发送缓冲区有空间，可以继续发送数据 |
| 连接关闭 | 客户端关闭了连接 |
| 异常事件 | 连接出现错误等情况 |

例如，客户端 A 向服务器发送了一条 HTTP 请求。这时操作系统会知道 A 对应的网络套接字（Socket）已经有数据可以读取了，服务器就可以处理这个事件。

> [!NOTE]
> **Socket（套接字）**
> 
> 我们这里暂时不对Socket作过多的展开，你可以把 Socket 理解为操作系统提供给程序的网络通信接口。服务器通过它接收客户端连接，读取数据，发送响应。


### 什么是非阻塞 I/O

先看阻塞 I/O，假设服务器执行下面这行代码：

```java
int size = inputStream.read(buffer);
```

在传统的阻塞读取模式下，如果当前没有数据到达的话线程可能会一直等待，直到有数据可以读取，或者连接关闭，或者出现错误。

这意味着，线程可能因为等待网络数据而无法继续处理其他工作。

非阻塞 I/O（Non-blocking I/O）则不一样。当程序尝试读取数据时：

- 如果已经有数据，就读取数据
- 如果暂时没有数据，就立即返回，不让线程一直等待

这样一来，一个线程在等待某个连接的数据时，就可以转去处理其他连接。

> [!WARNING]
> 非阻塞不意味着读取操作永远不会等待任何东西，而是说当数据暂时不可用时，读取调用不会让当前线程一直卡在那里。

现在将这两个概念结合起来，就形成了 Nginx 高并发处理能力的重要基础：

- 非阻塞 I/O：让线程不必为等待数据而停下来
- 事件驱动：让线程知道什么时候应该处理哪个连接

### 操作系统如何通知服务器

既然一个线程要管理成千上万个连接，那么它怎么知道哪个连接已经有数据了？难道每隔一段时间，就把所有连接挨个检查一遍？

这样显然是一个很愚蠢的方法，于是就需要操作系统提供的 I/O 多路复用（I/O Multiplexing）机制。

在 Linux 系统中，最重要的机制之一就是 **epoll**。

可以把 epoll 理解为一个事件通知系统。服务器把需要关注的 Socket 注册给操作系统，然后等待操作系统通知：

- 哪些 Socket 已经有数据可以读取
- 哪些 Socket 现在可以继续写入
- 哪些 Socket 出现了异常

这样服务器就不用每次都遍历全部连接，只需要处理操作系统返回的那一小部分。

> [!NOTE]
> Linux 的 epoll 主要采用的是**就绪通知（Readiness Notification）**机制[^7]。它告诉程序某个 Socket 已经处于可读或者可写的状态，但具体的数据读取和发送仍然由程序完成。

另外，不同操作系统使用的机制并不一样：

- Linux：epoll
- BSD 与 macOS：kqueue
- Solaris：event ports

Nginx 会根据操作系统选择合适的事件处理机制[^8]，这也是它能够适应不同 Unix 类操作系统环境的原因之一。

## Nginx 如何把这些技术组合起来

现在我们已经认识了三个概念：

1. 事件驱动（Event-Driven）
2. 非阻塞 I/O（Non-blocking I/O）
3. I/O 多路复用（I/O Multiplexing）

Nginx 将它们结合起来，形成了自己的核心工作架构。

这其中有两个重要角色：

**Master Process（主进程）** 主要负责管理工作进程，例如：

- 读取和验证配置文件。
- 启动和停止 Worker 进程。
- 监控 Worker 的运行状态。
- 在配置更新时协调平滑重载。

**Worker Process（工作进程）** 真正负责处理客户端连接和请求。

每个 Worker 通常采用单线程事件循环的方式工作，可以同时管理大量网络连接。

为什么不只创建一个 Worker？因为现代服务器通常拥有多个 CPU 核心。Nginx 可以启动多个 Worker，让它们分别运行在不同的 CPU 核心上，从而充分利用多核处理器的计算能力。

例如：

```nginx
worker_processes auto;
```

这里的 auto 表示让 Nginx 根据可用的 CPU 核心数自动选择 Worker 数量[^10]。

注意 **Worker 数量和连接数量不是一回事**。一个 Worker 可以管理很多连接。

整个过程大致如下：

1. **接收连接**。Worker 通过监听 Socket 接收客户端建立的连接
2. **监听 I/O 事件**。Worker 将连接注册到事件处理机制，等待客户端发送数据
3. **读取并解析 HTTP 请求**。当 Socket 可读时，Worker 读取数据，解析 HTTP 请求头和请求路径
4. **执行请求处理**。根据配置找到对应的资源，或者把请求转发到后端应用服务器
5. **发送 HTTP 响应**。当 Socket 可写时，Worker 将响应数据发送给客户端
6. **处理连接后续状态**。根据 HTTP Keep-Alive 等机制，继续复用连接或者关闭连接

当 Worker 等待某个客户端发送数据时，它不需要停在那里，它可以继续处理其他客户端的事件。例如：

| 时间 | Worker 正在做什么 |
| --- | --- |
| T1 | 读取 A 的 HTTP 请求 |
| T2 | 等待 A 的后续数据，转而处理 B |
| T3 | 处理 B 的请求 |
| T4 | C 的数据到达，处理 C |
| T5 | A 的数据已经就绪，继续处理 A |

这就是事件循环（Event Loop）的基本思想。

### 事件循环的伪代码

可以将它简化为下面的形式：

```java
while (true) {

    // 等待操作系统通知 I/O 事件
    Event[] events = epoll.wait();

    // 逐一处理发生的事件
    for (Event event : events) {

        if (event.isReadable()) {
            readData(event.socket());
        }

        if (event.isWritable()) {
            writeData(event.socket());
        }
    }
}
```

（这不是 Nginx 的真实源代码，而是为了理解其工作原理而简化的伪代码）

其中最重要的是：

```java
Event[] events = epoll.wait();
```

Worker 不需要一直遍历所有连接，而是等待操作系统返回已经就绪的事件。接下来处理这些事件，然后继续等待下一批事件。

因此一个 Worker 就可以管理成千上万个连接，而不需要为每个连接创建一个线程。

## 为什么这种架构性能更好

我们可以做一个简单的对比：

| 对比维度 | 传统线程模型 | Nginx 事件驱动模型 |
| --- | --- | --- |
| 连接管理 | 通常由线程负责连接 | Worker 管理多个连接 |
| 等待数据 | 线程可能阻塞等待 | 使用非阻塞 I/O |
| 事件检测 | 线程等待各自的 I/O | 通过 I/O 多路复用 |
| 线程数量 | 可能随连接数增长 | 通常远少于连接数 |
| 调度开销 | 大量线程可能增加开销 | 减少线程调度和切换 |

但这里有一个容易产生的误解：**Nginx 并不是因为完全不需要线程所以性能才高。**它的优势实际上来自几个因素的共同作用：

- 减少大量连接对应的线程管理开销
- 避免线程因为网络 I/O 等待而长期阻塞
- 利用操作系统提供的高效事件通知机制
- 通过多个 Worker 利用多核 CPU

另外，**Nginx 并不是所有操作都绝对不会阻塞**。某些耗时的文件 I/O 或者第三方模块操作仍然可能影响 Worker，因此 Nginx 也提供了线程池等机制来处理部分阻塞任务[^11]。

> [!NOTE]
> 回到我们之前提到的Apache：Apache 并非一直停留在传统的一个连接对应一个线程的模式，它后来也发展出了支持异步处理 Keep-Alive 连接的 Event MPM[^12]。Nginx 的优势不是简单地证明 Apache 不行，而是它从一开始就围绕事件驱动架构进行了设计。

## 安装 Nginx

Nginx 的安装方式大致可以分成三类：

- 直接安装：下载官方发布的压缩包或者源码，手动解压或者编译安装
- 包管理器：用系统或者社区提供的包管理器一条命令装好，升级和卸载也交给它管理
- Docker：拉取官方镜像，把 Nginx 跑在容器里，不往本机目录里装东西

三种方式没有绝对的好坏。如果你是本地学习的话当然用 Docker 最省事，服务器上通常用包管理器，需要特定模块或者更新的版本时再考虑源码编译。下面按 Windows，macOS，Linux 三个平台分别给出三种方式的命令，文中的版本号以 1.31.8 为例（撰写时的主线版），实际安装时换成官网下载页上的最新版本即可[^13]。

### 在 Windows 上安装

**方式一：直接安装（官方 zip 包）**

官方为 Windows 提供了预编译的 zip 包，下载解压就能用，不需要安装器[^14]。

打开 nginx.org 的下载页面，在 Windows 那一栏下载 `nginx-1.31.8.zip`，解压到没有中文和空格的目录，比如 `C:\nginx-1.31.8`。Windows 10 和 11 自带的 tar 就能解开 zip，也可以在右键菜单里选“全部解压缩”。然后进入解压出来的目录并启动：

```bat
cd C:\nginx-1.31.8
start nginx
```

打开浏览器访问 `http://localhost`，能看到欢迎页就说明启动成功。也可以查看进程和响应头：

```bat
tasklist /fi "imagename eq nginx.exe"
curl.exe -I http://localhost
```

Windows 版本身是一个控制台程序，不是 Windows 服务，它会把**运行目录**当作自己的前缀，所以要先 cd 进去再执行命令。配置在 `conf\nginx.conf`，日志在 `logs`，默认站点在 `html`。它靠 `nginx -s` 系列命令管理[^15]：

```bat
nginx -s stop     REM 立即停止
nginx -s quit     REM 等当前请求处理完再退出
nginx -s reload   REM 重新加载配置
nginx -s reopen   REM 重新打开日志文件
```

> [!WARNING]
> 官方明确说明 Windows 版仍处于 beta 状态，只使用 select 和 poll 两种连接处理方式，高并发和可扩展性不能和 Linux 版相提并论[^14]。它适合本地开发和测试，不建议用来跑生产流量。

**方式二：包管理器**

Windows 上三条路都能走：系统自带的 winget，社区常用的 Chocolatey 和 Scoop。三者的安装位置和管理方式不一样，需要分开看[^16]。

winget 装的是官方 zip 的便携版，不需要管理员权限：

```powershell
winget install --id nginxinc.nginx -e
```

它不会注册 Windows 服务，安装目录默认在 `%LOCALAPPDATA%\Microsoft\WinGet\Packages\` 下。装完新开一个终端执行 `nginx -v` 验证，启动时仍然要先进入安装目录再执行 `start nginx`。

Chocolatey 需要管理员权限的 PowerShell：

```powershell
choco install nginx -y
```

Chocolatey 的 nginx 包会用 nssm 把它注册成 Windows 服务，服务名默认是 `nginx`，安装目录默认是 `C:\tools\nginx-1.31.8`。所以它的启停走 Windows 服务：

```powershell
Get-Service nginx
Start-Service nginx
Stop-Service nginx
```

不想注册服务可以加 `/noService` 参数，想改端口或者目录可以用 `/port` 和 `/installLocation`。默认的 80 端口被占用时安装会失败。

Scoop 用普通用户权限即可，默认装到用户目录：

```powershell
scoop install nginx
nginx -p "$env:NGINX_HOME"
```

Scoop 版也不是服务，而且它把 `NGINX_HOME` 设成了包目录，必须用 `-p` 指定前缀，否则 Nginx 会把当前目录当成前缀找不到配置文件。

**方式三：Docker**

需要先安装并启动 Docker Desktop，然后执行：

```powershell
docker run --name nginx-demo -d -p 8080:80 nginx
```

浏览器访问 `http://localhost:8080`。要把本地静态页面挂进容器，可以把当前目录下的 `html` 挂到容器的站点目录：

```powershell
docker run --name nginx-demo -d -p 8080:80 -v "${PWD}\html:/usr/share/nginx/html:ro" nginx
```

容器里的站点目录是 `/usr/share/nginx/html`，配置文件是 `/etc/nginx/nginx.conf`[^17]。`nginx` 镜像的 latest 标签跟随主线版，生产上更建议用 `nginx:stable`，或者干脆固定版本号。

### 在 macOS 上安装

**方式一：直接安装（源码编译）**

macOS 上官方没有提供预编译包，所谓直接安装就是下载源码自己编译。先装好 Xcode 命令行工具，再用 Homebrew 装 PCRE2：

```bash
xcode-select --install
brew install pcre2
```

然后下载源码并编译。configure 的默认安装前缀是 `/usr/local/nginx`，下面的 include 和 lib 路径用来让 configure 找到 Homebrew 装好的 PCRE2[^18]：

```bash
curl -O https://nginx.org/download/nginx-1.31.8.tar.gz
tar -xzf nginx-1.31.8.tar.gz
cd nginx-1.31.8
./configure \
  --with-pcre \
  --with-cc-opt="-I$(brew --prefix pcre2)/include" \
  --with-ld-opt="-L$(brew --prefix pcre2)/lib"
make -j$(sysctl -n hw.ncpu)
sudo make install
```

装好后启动：

```bash
sudo /usr/local/nginx/sbin/nginx
```

配置文件在 `/usr/local/nginx/conf/nginx.conf`。源码编译默认不会带上 HTTPS 等模块，需要的话在 configure 时加 `--with-http_ssl_module` 之类的参数。要注意官方文档没有给出 macOS 专用的依赖写法，上面两条 Homebrew 参数属于社区常见做法。如果 configure 还是报找不到 PCRE2建议直接改用下面的 Homebrew 方式，别在编译上耗时间。

**方式二：包管理器（Homebrew）**

```bash
brew install nginx
```

Homebrew 会把 Nginx 装在自己的前缀目录下，并把默认端口改成 8080，这样普通用户不用 sudo 也能启动[^19]。配置文件和站点目录分别是：

- Apple Silicon：`/opt/homebrew/etc/nginx/nginx.conf` 和 `/opt/homebrew/var/www`
- Intel Mac：`/usr/local/etc/nginx/nginx.conf` 和 `/usr/local/var/www`

如果不确定自己的前缀，用 `brew --prefix` 查。启动和停止交给 Homebrew 的服务管理：

```bash
brew services start nginx    # 启动并设置开机自启
brew services stop nginx
brew services restart nginx
```

访问 `http://localhost:8080` 验证。

**方式三：Docker**

同样先装好 Docker Desktop，命令与 Windows 一致：

```bash
docker run --name nginx-demo -d -p 8080:80 nginx
```

访问 `http://localhost:8080`。挂载静态页面时用 macOS 的路径写法：

```bash
docker run --name nginx-demo -d -p 8080:80 -v "$(pwd)/html:/usr/share/nginx/html:ro" nginx
```

### 在 Linux 上安装（推荐）

**方式一：直接安装（源码编译）**

以 Debian 和 Ubuntu 为例，先安装编译依赖：

```bash
sudo apt update
sudo apt install build-essential libpcre2-dev zlib1g-dev libssl-dev
```

RHEL 系换成：

```bash
sudo dnf install gcc make pcre2-devel zlib-devel openssl-devel
```

然后下载源码，按默认前缀 `/usr/local/nginx` 编译安装[^18]：

```bash
curl -O https://nginx.org/download/nginx-1.31.8.tar.gz
tar -xzf nginx-1.31.8.tar.gz
cd nginx-1.31.8
./configure --prefix=/usr/local/nginx --with-http_ssl_module
make -j$(nproc)
sudo make install
```

启动并检查配置：

```bash
sudo /usr/local/nginx/sbin/nginx
sudo /usr/local/nginx/sbin/nginx -t
```

配置文件在 `/usr/local/nginx/conf/nginx.conf`，站点目录在 `/usr/local/nginx/html`。用源码装的 Nginx 没有 systemd 服务，机器重启后不会自动启动，需要的话得自己写一个 service 文件。

**方式二：包管理器**

Debian 和 Ubuntu：

```bash
sudo apt update
sudo apt install nginx
sudo systemctl start nginx
sudo systemctl enable nginx
```

Fedora 和 RHEL：

```bash
sudo dnf install nginx
sudo systemctl start nginx
sudo systemctl enable nginx
```

RHEL 上如果提示找不到包，先启用 EPEL 仓库，或者干脆按官方文档添加 nginx.org 的源。配置文件在 `/etc/nginx/nginx.conf`，默认站点目录是 `/var/www/html`。日常管理用 systemctl：

```bash
sudo systemctl status nginx
sudo systemctl reload nginx
sudo systemctl restart nginx
```

发行版仓库里的版本通常比官网旧，比如 Ubuntu 24.04 自带的还是 1.24。服务器上如果要用主线版或者更新的稳定版，可以按官方文档添加 nginx.org 的 APT 或者 YUM 源再安装。官方源和发行版自带的 nginx 包会冲突，装之前先把发行版包卸掉[^20]。

**方式三：Docker**

Linux 服务器上通常直接安装 Docker Engine，然后：

```bash
docker run --name nginx-demo -d -p 8080:80 nginx
```

如果 Docker 是以 root 身份安装的，普通用户执行 docker 命令需要加 sudo，或者把用户加入 docker 组。容器里的日志会输出到标准输出，用 `docker logs` 查看，不要进容器里找日志文件。挂载配置和静态目录的写法与前面相同：

```bash
docker run --name nginx-demo -d -p 8080:80 \
  -v "$(pwd)/html:/usr/share/nginx/html:ro" \
  -v "$(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro" \
  nginx
```

想改配置又不想从零写，可以先把镜像里的默认配置导出来：

```bash
docker run --rm --entrypoint=cat nginx /etc/nginx/nginx.conf > nginx.conf
```

日常操作用 Docker 自己的命令：

```bash
docker logs -f nginx-demo     # 实时看日志
docker restart nginx-demo     # 重启容器
docker stop nginx-demo        # 停止
docker rm nginx-demo          # 删除
docker pull nginx             # 更新镜像，之后删掉旧容器重新创建
```

### 安装完成后检查这几项

无论用哪种方式安装，装完之后都可以用这几条命令确认：

```bash
nginx -v                      # 查看版本
nginx -t                      # 检查配置语法，读不了配置时加 sudo
curl -I http://localhost      # 包管理器或源码安装，默认 80 端口
curl -I http://localhost:8080 # Homebrew 和 Docker 方式
```

总结一下：

| 安装方式 | 配置文件 | 默认端口 |
| --- | --- | --- |
| Windows 官方 zip 包 | 解压目录下的 `conf\nginx.conf` | 80 |
| Windows winget | `%LOCALAPPDATA%\Microsoft\WinGet\Packages\` 下的包目录 | 80 |
| Windows Chocolatey | `C:\tools\nginx-<版本>\conf\nginx.conf` | 80，默认注册成服务 |
| Windows Scoop | `%USERPROFILE%\scoop\apps\nginx\current\conf\nginx.conf` | 80 |
| macOS Homebrew | `$(brew --prefix)/etc/nginx/nginx.conf` | 8080 |
| macOS 源码编译 | `/usr/local/nginx/conf/nginx.conf` | 80 |
| Linux 包管理器 | `/etc/nginx/nginx.conf` | 80 |
| Linux 源码编译 | `/usr/local/nginx/conf/nginx.conf` | 80 |
| Docker | 容器内 `/etc/nginx/nginx.conf` | 80，映射到宿主机 `-p` 指定的端口 |

启动方式也和安装方法有关：官方 zip 包和源码安装是命令行程序，包管理器安装的 Linux 版本交给 systemd，macOS 用 `brew services`，Chocolatey 版注册成了 Windows 服务，Docker 则用 `docker` 命令管理容器。

> [!TIP]
> 安装后最常见的两个问题是端口被占用和没有权限监听 80 端口。Nginx 默认监听 80，Linux 上需要 root 或者 `CAP_NET_BIND_SERVICE`。macOS 用 Homebrew 安装时默认已经换成 8080。Docker 用 `-p 8080:80` 把容器里的 80 映射到宿主机的 8080，所以本地访问时要记得带端口号。
