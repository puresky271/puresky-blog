前两节我们把 Nginx 装上并跑了起来，但一直没管过它到底读的是哪份配置。这一节就从配置文件开始，把 Nginx 变成一个能放我们自己网页的静态服务器。

## 配置文件在哪

首先，还是打开你的命令行，输入：

```bash
nginx -V
```

这个命令的意思是：查看 Nginx 的版本，安装目录和编译参数。回车执行它：

![在 WSL 的 Ubuntu 22.04 上执行 nginx -V 的输出。第一行是版本号，第二三行是编译时用到的 OpenSSL 和 TLS SNI 支持，最后一行是一长串 configure arguments，其中高亮的是 --conf-path=/etc/nginx/nginx.conf](./images/post-20261109-3/mw9a7dmz-image.png)

我去这么一大坨，先别急，这些输出大致可以分三块：第一块是版本号 `nginx version: nginx/1.18.0 (Ubuntu)`，第二块是编译时用到的 OpenSSL 和 TLS SNI 支持，第三块是最后那行看不到头的 `configure arguments`。打包 Nginx 的人把这一串参数传给 `./configure`，它决定了 Nginx 装在哪里，日志和配置文件放在哪里，又启用了哪些模块。

> [!NOTE]
> `-V` 的 V 是大写，表示 verbose，除了版本号还会打印编译参数和依赖信息。小写的 `nginx -v` 只打印第一行版本号，平时确认版本用它就够了。另外 `nginx -V` 的输出走的是标准错误，想存成文件得写成 `nginx -V 2> /tmp/nginx-build.txt`。截图里那一长行在终端里被折成了好几行，实际只是一行。

虽然这些参数都很有用，但在这里我们没必要每一个都看，找出以下的这个参数：

```text
--conf-path=/etc/nginx/nginx.conf
```

这代表的是 Nginx 主配置文件的路径，Nginx 启动时会去这个位置读配置。这条 `configure arguments` 里还有几个路径参数，后面排查问题时会经常用到：

| 参数 | 含义 |
| --- | --- |
| `--prefix=/usr/share/nginx` | 安装前缀，Nginx 自己的文件放在这里 |
| `--conf-path=/etc/nginx/nginx.conf` | 主配置文件，就是这一节要看的文件 |
| `--http-log-path=/var/log/nginx/access.log` | 访问日志 |
| `--error-log-path=/var/log/nginx/error.log` | 错误日志 |
| `--pid-path=/run/nginx.pid` | 主进程 pid 文件 |

实际上由于安装 Nginx 的方式不同，配置文件并不都在 `/etc/nginx/nginx.conf`，一些常见的默认路径是：

| 安装方式 | 默认配置文件 |
| --- | --- |
| Ubuntu / Debian 用 apt 安装 | `/etc/nginx/nginx.conf` |
| CentOS / RHEL 用 yum 或 dnf 安装 | `/etc/nginx/nginx.conf` |
| 从源码编译安装（默认前缀 `/usr/local/nginx`） | `/usr/local/nginx/conf/nginx.conf` |
| FreeBSD 用 pkg 安装 | `/usr/local/etc/nginx/nginx.conf` |
| macOS 用 Homebrew 安装 | Apple 芯片是 `/opt/homebrew/etc/nginx/nginx.conf`，Intel 芯片是 `/usr/local/etc/nginx/nginx.conf` |

你不用背这些路径，在自己机器上用 `nginx -V` 看一眼就ok。

然而实际上我们还有一个更简单的方式来查看配置文件的路径：`nginx -t` 是 Nginx 提供的配置文件语法检查命令，用于检查配置文件是否存在语法错误，以及配置文件引用是否有效：

```bash
nginx -t
```

![在 WSL 的 Ubuntu 22.04 上执行 nginx -t 的输出。第一行提示 /etc/nginx/nginx.conf 语法检查通过，第二行提示加载测试成功](./images/post-20261109-3/mw9ahczp-image.png)

 `syntax is ok` 说明语法没问题，`test is successful` 说明配置能被正常加载，比如 `include` 引用的文件都存在，日志和 pid 的路径也都能访问。同时它会把检查过的文件路径打印出来，这也是为什么它能用来找配置文件。

> [!NOTE]
> 要注意 `nginx -t` 只是把配置“试读”一遍，它不会让新配置生效，也不会重启 Nginx。如果配置写错了，它会直接报出文件名和行号，比如少一个分号：
> 
> nginx: [emerg] unexpected end of file, expecting ";" or "}" in /etc/nginx/nginx.conf:84
> 
> nginx: configuration file /etc/nginx/nginx.conf test failed
> 


在 Ubuntu 上 Nginx 是系统服务，读配置时可能要碰一些只有 root 才能访问的路径，所以习惯上加上 `sudo`：

```bash
sudo nginx -t
```

> [!TIP]
> 还有一个更有用的参数 `-T`：`sudo nginx -T` 会把 `include` 进来的文件全部展开，打印最终生效的完整配置。排查“到底哪个文件在起作用”的时候它比 `nginx -t` 直观得多。

## 打开配置文件

现在我们直接打开这个配置文件看看，在终端里输入：

```bash
code /etc/nginx/nginx.conf
```

`code` 是 VS Code 的命令行入口，你在它后面跟一个文件路径的话就会用 VS Code 打开这个文件。如果 Nginx 装在 WSL 里，在 WSL 的终端里执行这条命令，VS Code 会自动连到 WSL，把 Linux 里的这份配置文件当成远程文件打开，左下角会显示 `WSL: Ubuntu-22.04` 的标记：

![在 WSL 里执行 code /etc/nginx/nginx.conf 之后，VS Code 以 WSL 远程的方式打开了 /etc/nginx/nginx.conf，状态栏左下角显示 WSL: Ubuntu-22.04](./images/post-20261109-3/vscode-nginx-conf.png)

> [!NOTE]
> 如果提示 `code: command not found`，说明 VS Code 没有装好，或者没把命令行工具加进 PATH。Windows 上可以在 VS Code 里按 `Ctrl+Shift+P`，执行 “Shell Command: Install 'code' command in PATH” 把命令补上。在 WSL 里用 `code` 打开文件，还需要装好 VS Code 的 Remote - WSL 扩展。

如果没装 VS Code，用系统自带的编辑器也一样，比如 `nano`：

```bash
sudo nano /etc/nginx/nginx.conf
```

或者 `vim` 也ok，这里用什么编辑器不影响后面的内容，能打开文件看清楚结构就行。

## 修改页面内容

回到你一开始执行 `nginx -V` 得到的那一大坨参数，我们现在需要找到 Nginx 的安装路径，找到 `--prefix` 后面的这个路径，以本机为例，它是：

```text
--prefix=/usr/share/nginx
```

然后我们来到这里，执行：

```bash
ls -ltr
```

![在 /usr/share/nginx 下执行 ls -ltr，能看到 html 和 modules-available 两个目录](./images/post-20261109-3/mw9dmg7l-image.png)

可以看到这其中有一个名为 `html` 的文件夹，再进到这里面看看有什么东西：

![进入 html 目录再执行 ls -ltr，里面只有一个 index.html](./images/post-20261109-3/mw9dom6p-image.png)

发现了一个叫 `index.html` 的文件，打开它：

```bash
cat index.html
```

![在 /usr/share/nginx/html 下执行 cat index.html，终端里打印出默认页面的 HTML 源码](./images/post-20261109-3/cat-index-html.png)

`cat` 会把文件内容直接打印到终端里。可以看到这个所谓的“默认页面”就是一个很朴素的 HTML 文件：开头一个 `doctype`，`head` 里写着标题和一点样式，`body` 里是欢迎语和两段说明—— Nginx 的默认页面并没有什么魔法，它只是安装时一起带进来的一个静态文件。

那直接把 `Welcome to nginx!` 改成别的内容，再刷新 localhost就完事了呗？先别急，如果你真的改了，会发现刷新之后页面一点变化都没有。

这里的问题出在“浏览器到底会拿到哪个文件”这件事上：决定它的不是 `--prefix`，而是 server 块里的 `root` 和 `index` 两个指令。Ubuntu 用 apt 安装时，默认站点的配置放在 `/etc/nginx/sites-enabled/default`，我们把和路径有关的两行挑出来：

```bash
grep -nE "^\s*(root|index)" /etc/nginx/sites-enabled/default
```

![在终端里用 grep 看默认站点配置中的 root 和 index 指令](./images/post-20261109-3/default-site-root.png)

这条 `grep` 只是把以 `root` 或 `index` 开头的行挑出来，跳过注释，`-n` 会顺便显示行号。`root /var/www/html;` 说明这个站点的网页文件都放在 `/var/www/html` 目录下。`index` 后面那串文件名是“访问一个目录时依次查找的首页文件”，排在前面的找不到就试下一个。这个目录里只有 `index.nginx-debian.html`，`index.html` 和 `index.htm` 都不存在，所以刚才 localhost 返回的其实是 `/var/www/html/index.nginx-debian.html`。

而 `/usr/share/nginx/html/index.html` 是 Nginx 软件包自带的一份默认页面副本，内容和它一模一样。源码编译安装时，默认站点的 root 恰好就是 `--prefix` 下面的 `html` 目录，那时候改 prefix 里的文件是生效的。但 apt 安装的 Ubuntu 把默认站点的目录换成了 `/var/www/html`，所以在 Ubuntu 上改 `/usr/share/nginx/html/index.html` 看不到任何变化。

明白了这一点，改页面就有两种做法：直接改 `/var/www/html` 下的首页文件，或者把 `root` 指向自己的目录。第二种才是部署自己站点的正确姿势，后面会用到，这里先演示第一种。用刚才的 `code` 打开真正被访问的那个文件：

```bash
code /var/www/html/index.nginx-debian.html
```

![在 WSL 里用 code 打开 /var/www/html/index.nginx-debian.html，VS Code 的面包屑里能看到 var > www > html 的路径，左下角是 WSL: Ubuntu-22.04](./images/post-20261109-3/vscode-index-html.png)

把里面整个换成自己的页面，比如：

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <title>我的第一个网页</title>
  <style>
    body { display: grid; place-items: center; min-height: 100vh; margin: 0;
           background: #f6f7f9; color: #1b1b1f; font-family: sans-serif; }
    h1 { margin: 0 0 .5rem; font-size: 2.5rem; }
    p  { margin: 0; color: #666; }
  </style>
</head>
<body>
  <main>
    <h1>Hello, Nginx!</h1>
    <p>这个页面是我自己写的，Nginx 正在把它发给浏览器。</p>
  </main>
</body>
</html>
```

保存后回到浏览器刷新 localhost，就能看到自己的页面了：

![刷新 localhost 后，页面变成了自己写的 Hello, Nginx!](./images/post-20261109-3/localhost-custom-page.png)

顺便说一句，改 HTML 这类静态文件不需要重载 Nginx，它每次收到请求都会直接从磁盘读文件，刷新浏览器就够了。只有改配置（比如接下来要动的 `root`）才需要先 `nginx -t` 检查，再 `systemctl reload nginx` 让它生效。如果刷新之后还是旧页面，可以按 `Ctrl+F5` 强制刷新，这多半是浏览器缓存。

到现在，“默认页面是怎么来的”就清楚了：它就是 `root` 目录下被 `index` 列表命中的那个 HTML 文件。想让 Nginx 展示自己的网页的话把网页文件放进站点目录就行。

不过直接改默认站点的文件只是临时做法，真正部署自己的博客时我们会新建一个目录，再把 `root` 指过去，这也就是接下来的内容。

## 用 Astro 搭一个本地博客

到目前为止我们改的都是 Nginx 自带的默认页面。真实的博客当然不会手写一个 HTML 文件，一般会用某个静态站点生成器把 Markdown 编译成 HTML，再交给 Nginx 发出去。这一节就用 **Astro** 走一遍完整流程：建项目，构建，把产物放进站点目录，改 root，最后访问 localhost。

Astro 的定位是内容优先的静态站点框架，默认就把页面构建成纯静态 HTML。产物和前面我们手写的 `index.html` 是一类东西，所以它和 Nginx 是天然的搭配：Nginx 只负责发文件，Astro 只负责生成文件。

### 准备 Node.js

Astro 需要 Node.js 18 以上。先确认一下版本：

```bash
node -v && npm -v
```

![在 WSL 里执行 node -v && npm -v，输出 Node 24 和 npm 11 的版本号](./images/post-20261109-3/node-version.png)

我这里用的是 WSL 里 nvm 装的 Node 24。如果你还没有装 Node，可以用 nvm 或者 NodeSource 的 22 LTS 装一个，装完再回来执行上面的命令。

### 用官方模板建项目

Astro 官方仓库里有几个模板，其中 `blog` 模板已经带好了文章列表和文章详情，还有 RSS 和 sitemap，最适合做一个最简单但能用的博客。用脚手架直接拉下来：

```bash
cd ~
npm create astro@latest blog -- --template blog --no-install --no-git --no-ai --yes
```

![执行 npm create astro@latest 拉取 blog 模板，最后提示 Project initialized](./images/post-20261109-3/astro-create.png)

这几个参数提前把交互答案给掉，省得一路回车：`--template blog` 指定模板，`--no-install` 先不装依赖，`--no-git` 不初始化 git 仓库，`--no-ai` 不生成 AI 助手的说明文件，`--yes` 让其余提示都用默认值。

进到项目目录里把依赖装上：

```bash
cd blog
npm install
```

### 构建

Astro 项目里写的是 `.astro` 组件和 Markdown 文章，`npm run build` 会把它们编译成静态文件，输出到 `dist/` 目录：

```bash
npm run build
```

构建完成后看看 `dist` 里有什么：

```bash
ls dist
```

![ls dist 的输出：_astro，about，blog，index.html，rss.xml，sitemap 等，全是静态文件](./images/post-20261109-3/astro-dist.png)

`_astro/` 里是打包好的 CSS，JS 和优化过的图片，`blog/` 和 `about/` 是各个页面的目录，`index.html` 是首页，另外还有 RSS 和 sitemap。它们全部是静态文件，没有任何需要服务器执行的代码——这正是 Nginx 最擅长的东西。

> [!NOTE]
> 开发的时候不用每次都 build，在项目目录里执行 `npm run dev` 会启动 Astro 自带的开发服务器（默认 4321 端口），改代码浏览器会实时刷新。这个开发服务器只用于本地预览，和 Nginx 没有关系，部署时用的是 `dist/`。

### 部署到 Nginx

先建站点目录，把 `dist` 里的东西拷过去：

```bash
sudo mkdir -p /var/www/blog
sudo cp -r dist/* /var/www/blog/
ls /var/www/blog
```

![拷贝构建产物到 /var/www/blog，ls 能看到同样的那批静态文件](./images/post-20261109-3/deploy-copy.png)

站点目录要放在 `/var/www` 这种 nginx 的 worker 用户（Ubuntu 上是 www-data）能读到的地方，别放在 `/root` 下面，否则 Nginx 会报 403。

然后把默认站点的 `root` 从 `/var/www/html` 换成新的目录，检查配置并让 Nginx 重新加载：

```bash
sudo sed -i 's|/var/www/html|/var/www/blog|' /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx
```

![用 sed 把 root 改成 /var/www/blog，nginx -t 通过后 reload](./images/post-20261109-3/deploy-root.png)

这里的 `sed` 只是把配置文件里那一行 `root /var/www/html;` 原地替换掉。`nginx -t` 确认语法没问题，`systemctl reload` 让新配置生效。改的是静态站点的 root，所以这次只需要 reload，不用重启。

刷新 localhost：

![部署到 Nginx 之后访问 localhost，看到的是 Astro blog 模板的首页](./images/post-20261109-3/astro-blog-home.png)

模板首页还是 Astro 自带的那张欢迎页，点开导航里的 Blog 就能看到模板自带的几篇文章，点进任意一篇就是正常的文章页面：

![点开模板自带的文章，看到文章标题和正文](./images/post-20261109-3/astro-blog-post.png)

到这里一个最简单的本地博客就部署好了。以后要换内容，只改 `src/` 里的组件和 Markdown，重新 `npm run build`，再把 `dist/*` 拷到 `/var/www/blog/` 覆盖就行。Nginx 不需要重启，因为发的一直是同一批静态文件。

> [!TIP]
> 想换回 Nginx 的默认页面，把 `root` 改回 `/var/www/html` 再 reload 就行。前面那个 Hello, Nginx! 的页面文件还在 `/var/www/html` 里，没有被动过。
