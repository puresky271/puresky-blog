前面四节里，我们一直在把 Nginx 当成一台静态文件服务器用：把 Astro 构建出来的 `dist` 放进站点目录，配好 `root` 和 `location`，它就能把网页稳稳地发出去。

但如果你去看 Nginx 官网对自己的介绍，或者翻一翻别人的架构图，会发现它更常被提起的两个身份是**反向代理**和**负载均衡器**。这两件事其实都建立在一个更基础的概念上：**代理服务器**。

## 什么是代理服务器

代理服务器，就是**位于客户端与目标服务器之间，代替其中一方进行网络通信的中间服务器**[^1]。

正常情况下，客户端直接向目标服务器发送请求，中间不需要任何人转手。

但是哪来那么多正常情况，在很多实际场景中，我们并不希望客户端直接与目标服务器通信，于是就在中间加入一台代理服务器。

如果中间加了一台代理服务器，过程就变成：客户端先把请求发给代理，代理再和目标服务器通信，最后把响应按原路返回给客户端。

如图 1 所示，上半部分是客户端直接连接目标服务器，下半部分是中间多了一台代理服务器。代理服务器可以承担不同的职责，由此产生了两种非常重要的代理方式：

- **正向代理（Forward Proxy）**：代表客户端工作
- **反向代理（Reverse Proxy）**：代表服务器工作

它们最大的区别其实只有一个问题：**代理服务器究竟在代表谁？**

> [!NOTE]
> 另外要说明一句，代理不一定都在 HTTP 这一层。像 SOCKS5 这类代理更贴近传输层，只负责把 TCP 连接转发出去，并不关心里面跑的是什么协议。这一节聊的主要还是 HTTP 这一层的代理。


## 正向代理

### 什么是正向代理

正向代理是代表客户端工作的代理服务器。

客户端希望访问某个目标服务器，但它不直接访问，而是先把请求交给代理服务器，由代理服务器代替自己去访问目标服务器。

举个最简单的例子。假设你在一台无法直接访问某个网站的计算机上，但同一网络里有一台能访问该网站的代理服务器，那么只要让这台代理服务器替你把请求发出去，你就能间接拿到页面。

如图 2 所示，请求从客户端出发先到正向代理，再由代理发往目标网站，响应沿原路返回。

总体而言：

- 客户端知道自己要访问哪个网站
- 客户端知道自己正在使用代理服务器
- 目标网站收到的网络连接通常来自代理服务器，而不是客户端本身

但也有例外，有些网关会做**透明代理**，客户端既没有做任何代理设置，也不知道自己在走代理。这种情况在“客户端是否知道代理”这一项上就和普通的正向代理不同了。

配置过代理的机器上，用 `curl -I` 访问一个 HTTPS 地址时，输出的最前面常常会先多出一行：

```text
HTTP/1.1 200 Connection established
```

这一行不是目标网站返回的，而是代理服务器对 `CONNECT` 请求的应答。HTTPS 的内容是加密的，普通的正向代理只需要在客户端和目标网站之间建立一条 TCP 隧道，把字节流原样转发，并不关心里面传了什么[^2]。这也是正向代理能替你出门，却不一定能看见你具体访问了什么的原因。当然如果走的是明文 HTTP 的话，代理就能看到完整的请求，企业代理也正是靠这一点做访问审计的。

### 为什么需要正向代理

主要用途有三个：

**突破网络访问限制（懂的都懂）。** 某些网络环境会限制客户端直接访问特定网站。通过一台有相应访问权限的代理服务器，客户端就能间接访问目标资源。

**隐藏客户端的真实网络地址。** 目标服务器通常看到的是代理服务器的 IP，而不是客户端直接连接时用的出口 IP。不过具体能不能藏住还取决于代理协议，以及代理有没有在里面加 `X-Forwarded-For`，`Via` 这类请求头。

**统一管理客户端的网络访问。** 在企业或学校里，可以部署一台统一的代理服务器，用它记录网络访问行为，限制访问特定网站，缓存经常访问的资源，也把整个网络的出口收在一处管理。

### 正向代理的典型应用

| 场景或软件 | 它做什么 |
| --- | --- |
| 企业网络代理 | 员工访问互联网的流量统一经过代理服务器，访问策略，审计和出口都在这一层做 |
| Squid | 一个很经典的开源代理缓存软件，主要用来做正向代理，访问控制和缓存 |

Squid 在上世纪九十年代就出现了，很多公司内网和学校的出口代理至今还在用它[^3]。一个典型的配置是：内网机器只放行到代理服务器的连接，员工的浏览器和命令行通过系统代理或者 `HTTPS_PROXY` 环境变量把请求交给它，由它统一出网。

## 反向代理

### 什么是反向代理

反向代理是代表服务器工作的代理服务器。

客户端希望访问某个网站，但它并不直接连接真正提供业务服务的后端服务器，而是先连接反向代理服务器。反向代理再根据请求情况，把请求转发给合适的后端服务器。

例如你访问 `https://www.example.com`，你以为自己正在访问一台服务器。但实际上，背后可能是一台 Nginx 反向代理服务器，三台 Java 后端服务器，两台 Python 服务，还有一套数据库系统。客户端只需要和 Nginx 通信，不需要知道后端服务器的具体结构：

如图 3 所示，这里的关系和正向代理恰好相反：

- 客户端只知道自己访问的网站
- 客户端通常不知道背后具体有哪些后端服务器
- 后端服务器把 Nginx 当作请求的直接上游客户端

有一个容易产生的误解：**反向代理并不意味着后端服务器永远不暴露给客户端，而是说正常的访问路径由代理服务器作为统一入口**。内网里的后端如果被直接扫到端口，照样能连上，只是那已经不是设计里的正常路径了。

反过来也很容易验证：在 Nginx 里配一条 `proxy_pass`，它就会把收到的请求转发给你指定的后端，而客户端那边的地址栏从头到尾没有变过[^5]。

反向代理离我们其实很近。在终端里执行：

```bash
curl -I https://example.com/
```

把响应头里和服务器有关的部分挑出来，会看到类似这样的几行：

```text
Server: cloudflare
CF-RAY: a5854a6f2c4fae45-SIN
cf-cache-status: HIT
Age: 2
```

`example.com` 只是一个内容极简的示例页，但它并不是由“一台叫 example.com 的服务器”直接返回的。你实际连上的是 Cloudflare 的边缘节点，由它替你去取真正的内容[^4]。响应头里从头到尾没有出现源站的地址，这就是反向代理在客户端这一侧的效果：你只知道自己在和 Cloudflare 说话，不知道它把请求交给了谁。（这几行是我 2026 年 11 月 10 日在本机取到的，由于节点编号和缓存状态每次都不一样，你那边看到的不会和这里完全一致。）

### 为什么需要反向代理

反向代理在现代 Web 架构里非常重要，主要有四个用途。

#### 隐藏后端服务器

假设你有三台服务器，IP 分别是 192.168.1.10，192.168.1.11 和 192.168.1.12。

如果直接让客户端访问这些服务器，客户端就得知道它们的地址，而且地址一变所有调用方都得跟着改。

用了反向代理之后，客户端只需要知道 `www.example.com`，由 Nginx 去决定把请求交给哪台后端。

#### 负载均衡

假设后端还是那三台服务器。如果所有请求都交给第一台，就会出现一种很尴尬的情况：第一台忙得喘不过气，另外两台却在闲着什么也不干。

反向代理可以把请求分给不同的后端。比如采用轮询策略：

| 请求 | 分配到的服务器 |
| --- | --- |
| 请求 1 | 后端 A |
| 请求 2 | 后端 B |
| 请求 3 | 后端 C |
| 请求 4 | 后端 A |
| 请求 5 | 后端 B |

写成 Nginx 的配置，大概是这么一组 `upstream`：

```nginx
upstream backend {
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;
    server 192.168.1.12:8080;
}
```

在 Nginx 里，`upstream` 把几台后端组成一组，不写任何策略时默认就是轮询[^6]。后面还可以按需求换成加权轮询，按来源 IP 粘住，或者交给当前连接数最少的那台，这些我们马上就会在动手配置里看到。

#### 统一处理 HTTPS

客户端可以通过 HTTPS 和 Nginx 建立加密连接，Nginx 再根据配置和后端服务器通信。这样 TLS 证书管理和 HTTPS 接入就都集中在代理这一层了，后端可以只在内网用 HTTP 提供服务。证书续期，协议版本，加密套件这些事只需要在 Nginx 上管一次。

#### 缓存静态资源或响应

Nginx 可以缓存符合条件的响应。客户端重复请求同一个资源时，Nginx 有机会直接从缓存返回，不必每次都去问后端[^7]。对变化不频繁的页面和静态资源来说，这一层能明显减轻后端的压力。

### 反向代理的典型应用

| 场景或软件 | 它做什么 |
| --- | --- |
| Nginx | 非常典型的反向代理服务器，接收 HTTP 请求后转发给不同的后端应用 |
| Cloudflare | 提供反向代理，CDN 和网络安全，站在网站流量进入源站之前的代理层 |

Cloudflare 这类 CDN 的接入方式也很能说明问题：网站把自己的域名解析到 Cloudflare 的节点，访客连上的是 Cloudflare 而不是源站，由 Cloudflare 决定回源还是直接返回缓存[^4]。前面 `example.com` 的响应头就是这么一个例子。

## 正向代理与反向代理的区别

| 对比维度 | 正向代理 | 反向代理 |
| --- | --- | --- |
| 代表谁工作 | 客户端 | 服务器 |
| 主要隐藏谁 | 客户端的网络地址 | 后端服务器的具体结构 |
| 客户端是否知道代理 | 通常知道 | 通常不知道 |
| 主要使用场景 | 网络访问控制，统一出口 | 负载均衡，HTTPS，缓存 |
| 典型软件 | Squid | Nginx |

另外，关于正向代理和反向代理的区别，你也可以这么记忆：

- **正向代理替客户端出门办事。** 客户端告诉代理：“我要访问这家网站，你替我去一趟。”
- **反向代理替服务器接待访客。** 客户端告诉代理：“我要访问这个网站。”代理再决定让哪台后端服务器来接待。

如图 6 所示，两者最根本的区别不是代理服务器站在网络拓扑的左边还是右边，它们很可能就处在同一个位置。真正的区别是**代理服务的对象和信任边界**不同：正向代理站在客户端这一侧，客户端信任它，它替客户端越过网络边界去访问外部世界。反向代理站在服务器这一侧，后端信任它，它守在边界上替后端接待每一个来自外网的访客。

## 让 Nginx 做反向代理

概念讲清楚了，现在回到 Nginx 自己身上。

为了不动前面几节配好的默认站点，这一节的实验都放在 8080 端口上。后端不用真的写代码，Python 自带的 `http.server` 就够用了：它会把指定目录下的文件当静态页面发出来，正好方便我们看清请求落到了哪台机器上。

先在 home 目录里准备三个目录和三张页面：

```bash
mkdir -p demo/a demo/b demo/c
echo 'I am backend A' > demo/a/index.html
echo 'I am backend B' > demo/b/index.html
echo 'I am backend C' > demo/c/index.html
```

然后各起一个服务，端口分别是 8001，8002 和 8003：

```bash
nohup python3 -m http.server 8001 -b127.0.0.1 -d demo/a >/tmp/a.log &
nohup python3 -m http.server 8002 -b127.0.0.1 -d demo/b >/tmp/b.log &
nohup python3 -m http.server 8003 -b127.0.0.1 -d demo/c >/tmp/c.log &
```

注意：

- `-d demo/a` 指定要发布的目录，也就是把哪个目录当成网站根目录
- `-b127.0.0.1` 让服务只监听回环地址。除了本机其他地方连不上它
- `nohup ... &` 把进程挂到后台，关掉终端之后它也不会跟着退出

直接访问三个端口，应该能分别看到三行文字，`ss -ltn` 也能确认它们只监听了 `127.0.0.1`：

![在 WSL 的 Ubuntu 22.04 上准备三个后端目录，用 Python 的 http.server 在 8001 到 8003 端口启动三台后端并直接访问，三台分别返回 I am backend A，I am backend B 和 I am backend C，最后的 ss -ltn 显示三个端口都只监听在 127.0.0.1 上](./images/post-20261110-2/proxy-backends.png)

现在让 Nginx 站到 8080 端口上，做这三台后端的统一入口。新建一个站点配置文件：

```nginx
server {
    listen 8080;
    server_name _;

    location / {
        proxy_pass http://127.0.0.1:8001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

把它写进 `/etc/nginx/sites-available/proxy-demo`，软链到 `sites-enabled`，检查并重载配置，然后从 8080 发几个请求：

```bash
ln -sf /etc/nginx/sites-available/proxy-demo /etc/nginx/sites-enabled/
nginx -t
nginx -s reload
curl -s http://localhost:8080/
curl -i -s http://localhost:8080/ | head -n 5
```

![在 WSL 里 cat 出反向代理的站点配置，内容是监听 8080，把 location / 转发到 127.0.0.1:8001，并设置 Host，X-Real-IP 和 X-Forwarded-For 三个请求头。之后 nginx -t 检查通过，reload 后 curl 8080 返回 I am backend A，响应头里的 Server 是 nginx/1.18.0 (Ubuntu)](./images/post-20261110-2/proxy-config.png)

具体而言：

- `listen 8080` 是客户端访问的入口。真实站点这里是 80 和 443，用 8080 只是为了避免和默认站点抢 80 端口
- `proxy_pass http://127.0.0.1:8001` 是核心，它把匹配到的请求原样交给 8001。Nginx 自己不是内容的生产者，只负责转发，再把后端的响应原样还给客户端
- `proxy_set_header Host $host` 解决的是后端看到的 Host 头。默认情况下，Nginx 发给后端的 Host 是 `proxy_pass` 里的地址，也就是 `127.0.0.1:8001`，很多应用会拿 Host 做虚拟主机或者拼绝对链接，所以要改回客户端请求时带来的域名[^8]
- `X-Real-IP` 和 `X-Forwarded-For` 解决的是后端看到的客户端地址。后端收到的 TCP 连接来自 Nginx，`$remote_addr` 是 Nginx 看到的客户端 IP，带上这两个头，后端日志里才不会全是 `127.0.0.1`
  
从截图里能看到：8080 返回的是后端 A 的那一行，响应头里的 `Server` 是 `nginx/1.18.0 (Ubuntu)`，这说明这个响应是 Nginx 发回来的。客户端只认识 8080 一个端口，8001 在背后干活。

只转发到一台后端的时候这件事看起来只是换了个端口，没什么大用。真正有意思的是后端不止一台的时候。

## 用 upstream 做负载均衡

Nginx 把多台后端组织在一起用的是 `upstream`。把 `proxy_pass` 的地址换成一个 upstream 名字，再把三台后端写进 `upstream` 块：

```nginx
upstream backend {
    server 127.0.0.1:8001;
    server 127.0.0.1:8002;
    server 127.0.0.1:8003;
}

server {
    listen 8080;
    server_name _;

    location / {
        proxy_pass http://backend;
    }
}
```

检查，重载，然后连续请求六次：

```bash
nginx -t
nginx -s reload
for i in 1 2 3 4 5 6; do curl -s http://localhost:8080/; done
```

![在 WSL 里 cat 出 upstream 配置，upstream backend 里列了三台后端，proxy_pass 指向 http://backend。reload 之后连续请求六次 8080，依次返回 I am backend A，B，C，A，B，C](./images/post-20261110-2/load-balancing-round-robin.png)

六次请求的顺序是 A，B，C，A，B，C，三台后端被轮流分到了请求，这就是**轮询（round-robin）**。`upstream` 默认就是轮询，不写任何策略也是这个效果，`proxy_pass` 从指向一台机器变成指向一组机器，负载均衡就生效了[^6]。

> [!NOTE]
> 为了让分配顺序看得清楚，演示环境里把 `worker_processes` 临时改成了 1。多个 Worker 的时候，每个 Worker 各自维护一份轮询状态，整体顺序看起来会交错，但只要请求够多，落点仍然是均分的。

### 加权轮询

三台机器性能不一样的时候轮询就不够用了。比如一台新机器顶得上两台老机器，可以给它的 `server` 加一个 `weight`：

```nginx
upstream backend {
    server 127.0.0.1:8001 weight=3;
    server 127.0.0.1:8002;
    server 127.0.0.1:8003;
}
```

改完配置重载，再请求五次：

```bash
nginx -t
nginx -s reload
for i in 1 2 3 4 5; do curl -s http://localhost:8080/; done
```

![在 WSL 里把 upstream 的后端 A 改成 weight=3，重载之后连续请求五次 8080，依次返回 I am backend A，B，A，C，A，其中后端 A 出现了三次](./images/post-20261110-2/load-balancing-weight.png)

五次请求的顺序是 A，B，A，C，A。A 的权重是 3，所以五次里它出现了三次，B 和 C 各一次。Nginx 没有把权重大的一口气塞满，而是把 A 的请求均匀插在中间，避免某一台突然被打满。

### 其他常用的策略

除了轮询和加权轮询，upstream 里还有几个常用的设置：

| 策略 | 写法 | 适合的场景 |
| --- | --- | --- |
| 轮询（默认） | 不写 | 后端配置差不多，请求也差不多 |
| 加权轮询 | `server ... weight=3` | 机器性能不一样 |
| 源地址哈希 | 在 upstream 里加 `ip_hash` | 同一个客户端要固定落在同一台后端，比如后端的 session 存在本地 |
| 最少连接 | 在 upstream 里加 `least_conn` | 请求耗时差别大，让闲着的后端多接一点 |
| URL 哈希 | 在 upstream 里加 `hash $request_uri` | 同一个资源固定到同一台后端，配合后端缓存 |

`ip_hash` 和 `hash` 都是让同一类请求固定落在一台后端上，前者按客户端 IP 算，后者按请求的 URI 算。它们解决的是会话粘性和缓存命中的问题，代价是流量分配可能没那么均匀。

### 后端挂了会怎样

讲负载均衡绕不开一个问题：一台后端突然挂了，请求会怎么样？

我们直接把 A 杀掉，再连续请求六次看看：

```bash
pgrep -af "http.server"
pkill -f "http.server 8001"
pgrep -af "http.server"
u=localhost:8080/
for i in {1..6}; do curl -s -o /dev/null -w '%{http_code}\n' $u; done
grep -c "connect() failed" /var/log/nginx/error.log
```

![在 WSL 里先用 pgrep 确认三台后端都在，pkill 杀掉 8001 之后只剩两台。接着连续请求六次 8080，状态码全是 200。错误日志里 connect() failed 的计数只从 4 变成 5](./images/post-20261110-2/load-balancing-health.png)

两次 `pgrep` 的输出能看到 A 确实下去了，但六次请求的状态码全是 `200`。错误日志里 `connect() failed` 的计数只从 4 变成了 5，说明六次请求里只有一次真的撞上了挂掉的 A。

原因是 Nginx 对上游失败有一套默认的处理[^9]：

- 请求分到 A 时连接失败，Nginx 会立刻把同一个请求重试到下一台健康的后端。这个行为由 `proxy_next_upstream` 控制，默认在 `error` 和 `timeout` 两种情况下重试，所以客户端拿到的还是 200
- 同时 A 被标记为不可用。`max_fails` 默认是 1，一次失败就算数。`fail_timeout` 默认是 10 秒，这 10 秒里 Nginx 不会再给它分请求，10 秒之后才重新尝试。这就是为什么六次请求只多了一次失败记录
- 错误日志里会写清楚是哪台上游失败：

```text
[error] ... connect() failed ... while connecting to upstream,
client: 127.0.0.1, server: _, request: "GET / HTTP/1.1",
upstream: "http://127.0.0.1:8001/", host: "localhost:8080"
```

这套机制叫**被动健康检查**：Nginx 不开定时探测，只看真实请求的结果。开源版 Nginx 只有被动健康检查，主动健康检查是 Nginx Plus 才有的功能。所以如果所有后端都挂了，就没有“下一台”可以重试，客户端会直接拿到 502。

### 结束之后

演示用的配置和进程记得收掉，免得和真正要用的站点打架：

```bash
pkill -f "http.server"
rm -rf demo
rm -f /etc/nginx/sites-enabled/proxy-demo /etc/nginx/sites-available/proxy-demo
nginx -t && nginx -s reload
```

总结一下：代理服务器站在客户端和目标服务器之间，代表其中一方工作。代表客户端的是正向代理，代表服务器的是反向代理。落到 Nginx 的配置上，反向代理和负载均衡其实就两件事，`proxy_pass` 决定把请求交给谁，`upstream` 把多台后端组成一组，再配上轮询，权重和失败重试，就是一个能扛住单台后端挂掉的入口了。

当然，Nginx 能做的事不止这些。缓存，压缩，限流，日志和访问控制，都可以堆在这个统一入口上。这一组文章从安装和进程模型讲到这里已经把这台服务器最常用的几块过了一遍，剩下的就留到以后遇到具体问题时再写了。
