在正式修改配置文件之前，还是先确认一下当前的配置文件是否正确。

还是用上一节的那个命令：

```bash
nginx -t
```

确认无误之后，我们用 VS Code 打开配置文件，还是老样子，在命令行里输入 `code` 加文件路径就行：

```bash
code /etc/nginx/nginx.conf
```

但这一次我们不急着改，先好好看一看它的结构。

## 配置文件的结构

打开文件往下翻，会发现它整体是一个大括号套大括号的结构。Nginx 的配置按“上下文（context）”分层，一条指令写在哪个上下文里就只对这个范围生效。

最外面那层叫 `main` 上下文，也有人叫它全局块，它里面的指令管整个 Nginx 的启动和运行。从外到内，常用的上下文有这么几层：

| 上下文 | 位置 | 主要管什么 |
| --- | --- | --- |
| `main` | 最外层 | 用户，worker 进程数，pid 文件，日志，include |
| `events` | `main` 里 | 事件驱动模型，比如连接数上限 |
| `http` | `main` 里 | 所有 HTTP 配置的容器，站点配置都在这层底下 |
| `server` | `http` 里 | 一个虚拟主机，靠 `listen` 和 `server_name` 区分 |
| `location` | `server` 里 | 按 URL 分发的处理规则 |
| `upstream` | `http` 里 | 反向代理用的上游服务器组，和 `server` 平级 |

先看 `http` 外面的部分，也就是 `main` 和 `events`：

```nginx
# main 上下文：整个 Nginx 的全局设置
user www-data;
worker_processes auto;
pid /run/nginx.pid;
include /etc/nginx/modules-enabled/*.conf;

events {
    worker_connections 768;
}
```

再看 `http` 里面。一个 `http` 可以装很多个 `server`，每个 `server` 是一个虚拟主机，里面的 `location` 再按 URL 分发：

```nginx
http {
    include /etc/nginx/mime.types;

    upstream backend {
        server 127.0.0.1:3000;
    }

    server {
        listen 80 default_server;
        server_name _;
        root /var/www/html;

        location / {
            try_files $uri $uri/ =404;
        }

        location /api/ {
            proxy_pass http://backend;
        }
    }

    include /etc/nginx/sites-enabled/*;
}
```

上面只是骨架示意，真实文件里的值不会和它完全一样。

普通指令以分号 `;` 结尾，块指令用一对大括号把一组指令包起来，右大括号后面不加分号。还有一个 `include`，它的作用是把另一个文件的内容原样拼进来，不是运行时调用，例如 `http` 里最后那句 `include /etc/nginx/sites-enabled/*;` 就是把 Ubuntu 的站点配置文件都拼进 `http` 里。

> [!NOTE]
> Ubuntu 自带的 `/etc/nginx/nginx.conf` 很短，站点参数大多不在里面。它把配置拆成了“主配置文件 + 每个站点一个文件”的形式，站点文件放在 `/etc/nginx/sites-available/`，`sites-enabled/` 里是指向它们的软链接，最后由 `include` 拼进 `http`。
>
> 所以要改某个站点监听哪个端口或者根目录在哪里得先去 `sites-enabled/` 里找，不要只在 `nginx.conf` 里翻。

这些层之间还有继承关系：里层会继承外层的指令，在里层重新写一遍就是覆盖外层的值。比如 `root` 写在 `server` 里，这个站点下面的所有 `location` 都跟着用，在某个 `location` 里再写一次 `root`就只对这个 `location` 生效。如果你改完配置发现某条指令没起作用的话，可以先检查一下是不是被更里层覆盖了。

另外，我们也可以输入：

```bash
sudo nginx -T
```

这会把所有 `include` 展开并按最终层级打印整份配置（缩进就是层级）。输出里每一段前面还会用 `# configuration file ...` 标出来源文件，这样就能确认某个 `server` 到底是从哪份文件里读进来的：

![在 WSL 的 Ubuntu 22.04 上执行 sudo nginx -T 并用 head 和 grep 截取输出。上半部分是展开后的开头，能看出 main 里的指令在最外层，events 和 http 缩进一级，下半部分是 grep 出来的文件列表，每一行前面是行号，后面是这段配置来自哪个文件](./images/post-20261110/nginx-T.png)

截图里能对上前面说的分层：`main` 的指令压在最外层，`events` 和 `http` 缩进一级，`http` 里的 `server` 再缩进一级。列表里的数字是行号，`mime.types` 从第 106 行一直展开到第 196 行，光这一个文件就占了 90 行。

> [!NOTE]
> 完整的 `-T` 输出加起来有近三百行，所以截图里只截了开头和文件列表。

## 修改进程数

先看文件开头，最前面几行是这样的：

![在 VS Code 里打开的 /etc/nginx/nginx.conf，开头几行是 user www-data 和 worker_processes auto，再往下是 pid 和 include 指令](./images/post-20261110/mwamikl5-image.png)

这几行就是前面说的 `main` 上下文（全局块）。截图里面的这四条各自管理的部分如下：

- `user www-data;` 指定 worker 进程用哪个用户运行
- `worker_processes auto;` 指定 worker 进程的数量，它就是这一节要改的
- `pid /run/nginx.pid;` 指定 master 进程的 PID 写进哪个文件，`nginx -s reload` 这类命令要读它
- `include /etc/nginx/modules-enabled/*.conf;` 把动态模块的配置引进来

要理解 `worker_processes`，得先回到 Nginx 的进程模型。我们在第二节看 `ps -ef | grep nginx` 的时候已经见过：Nginx 是一个 master 带着一群 worker，master 负责读配置，绑定端口，管理 worker，真正接收和处理请求的是 worker。`worker_processes` 决定的就是这群干活的进程有几个。

而现在看到的值是 `auto`。`auto` 不是一个固定的数字，Nginx 启动时会读一下机器的 CPU 核心数，有几个核就起几个 worker（这个写法从 1.3.8 和 1.2.5 开始支持）。以我的本机为例，这台机器的 WSL 有 16 个核，所以第二节看到的输出里正好是 16 个 worker。

> [!NOTE]
> 想确认自己机器上有几个核的话，可以执行 `nproc`。要是只看到 1，多半是虚拟机或者容器分到的核心少，不是 Nginx 的问题。

现在我们把 `auto` 改成 `10`，保存文件。

嗯，然后呢？就生效了吗，并没有。

上一节提醒过：`nginx -t` 只是把新配置读一遍做检查，不会让它生效，也不会重启 Nginx。这时候直接执行 `ps -ef | grep nginx`，看到的还是 16 个 worker，因为 Nginx 根本没有重读配置。要检查新配置照旧：

```bash
nginx -t
```

要让新配置生效，得让 Nginx 重新加载一遍配置：

```bash
nginx -s reload
```

这条命令给 master 发一个 reload 信号。master 重新读一遍配置，按新配置起 10 个新 worker，再让旧的 16 个 worker 把手头的连接处理完自己退出。整个过程 master 不重启，端口一直有人监听，已经建立的连接也不会被掐断，master 的 PID 不会变，换掉的只是 worker。如果新配置写错了，master 会拒绝加载，继续按旧配置跑，不会把正在服务的 Nginx 搞挂。

> [!NOTE]
> 在 Ubuntu 上 Nginx 是系统服务，等价的写法是 `sudo systemctl reload nginx`，用哪种都行。reload 成功时没有任何输出，没有消息就是最好的消息，有输出反而要注意。

然后就可以看进程数了：

```bash
ps -ef | grep nginx
```

![在 WSL 的 Ubuntu 22.04 上先执行 nginx -t 和 nginx -s reload，再执行 ps -ef | grep nginx。master 的 USER 是 root，后面跟着 10 个 www-data 的 worker，最后一行的 grep 是命令自己](./images/post-20261110/worker-processes-10.png)

跟之前那 16 个 worker 比，现在只剩 10 个，正好对上 `worker_processes 10;`。

再看细节：

- 第一行是 master，USER 是 `root`，因为绑定 80 端口这类操作需要特权
- 后面 10 行都是 worker，USER 是 `www-data`，也就是配置里 `user` 指定的用户
- 所有 worker 的 PPID 都是 268，正好是 master 的 PID，说明它们是同一个 master 的子进程
- 最后一行 `grep --color=auto nginx` 不是 Nginx 的进程，而是我们刚敲的这条命令里的 grep 自己

> [!NOTE]
> `grep nginx` 会匹配到自己的命令行，所以输出的末尾总会多出一行。不想看到它可以把命令写成 `ps -ef | grep "[n]ginx"`，方括号让 grep 自己的命令行不匹配这个模式。也可以直接用 `pgrep -c nginx` 数进程数，只是它会把 master 一起算进去，10 个 worker 的结果是 11。

 需要特别强调的是：worker 不是越多越好。每个 worker 都是独立的进程，多一个就多一份内存，还会和别的 worker 抢 CPU。这台机器 16 个核，起 16 个 worker 刚好一核一个，再往上加对 CPU 密集的请求没有帮助，只有在 worker 大量做阻塞 I/O（同步读写大文件或者上游响应很慢）的时候才可能多一点。所以生产环境一般保持 `auto`，这里的 `10` 只是演示值。
 
worker 能接的连接数也不是无限的。`events` 块里的 `worker_connections` 规定每个 worker 最多同时开多少条连接，Ubuntu 的默认配置是 768，总数大致是 `worker_processes × worker_connections`，10 个 worker 就是 7680 条。连接数不够的时候错误日志里会出现 `worker_connections are not enough`。

> [!TIP]
> 如果你在改动完毕后想确认生效的是哪份配置，可以执行 `sudo nginx -T | grep worker_processes`。`-T` 会把 `include` 进来的文件全部展开，打印最终生效的完整配置，再筛出这一行，看到 `worker_processes 10;` 的话就说明 reload 已经读进去了。

## HTTP 和 HTTPS

前面几节访问的一直是 `http://localhost`，地址栏前面没有锁，有的浏览器还会在地址栏里标一句“不安全”。这不是浏览器没事找事：HTTP 本身不加密，请求行，请求头和 Cookie，响应正文在网络上都是明文，链路上任何一个能抓包的节点都能看见也能改。

而 HTTPS 不是另一套协议，而是 HTTP 外面套了一层 TLS（更早的时候叫 SSL）。它在 HTTP 和 TCP 之间补了三件事：

- 加密：浏览器和服务器在握手阶段协商出一个临时的对称密钥，之后的数据都用它加密，抓包只能看到密文
- 完整性：数据带校验，路上被改过接收方会发现
- 身份认证：服务器出示证书，浏览器用内置的 CA 信任列表验证这张证书确实属于这个域名，防止连到冒充的服务器

代价是握手要多一个往返，加解密也要花一点 CPU，不过在 TLS 1.3 和会话复用之下这丁点开销大部分场景可以忽略。

| 对比项 | HTTP | HTTPS |
| --- | --- | --- |
| 默认端口 | 80 | 443 |
| 传输内容 | 明文 | TLS 加密后的密文 |
| 防篡改 | 没有，中间人可以改 | 有完整性校验 |
| 服务器身份 | 不验证 | 用证书验证 |
| 浏览器提示 | 可能标“不安全” | 地址栏显示锁 |
| 配置写法 | `listen 80;` | `listen 443 ssl;` 加证书路径 |

其中的身份认证靠证书，而证书得有人来签：公开站点找 CA 签（免费的选择后面列），本机测试可以自己签一张自签名证书，自己既是申请人也是签发人。

这种既要又要的法子当然不正经，浏览器没在信任列表里见过这个签发者会拦一下，但手动点过去就能用，正好适合本地实验。

## 用自签名证书配置 HTTPS

让我们在本机把 `https://localhost` 跑起来，过程大致分三步：生成证书，把证书路径写进 Nginx 的配置，reload 之后在浏览器里验证。

### 生成自签名证书

Ubuntu 自带 openssl，先建一个目录放证书文件：

```bash
mkdir -p /etc/nginx/ssl
cd /etc/nginx/ssl
```

然后执行这三条命令：

```bash
openssl genrsa -out private.key 2048
openssl req -new -key private.key -out cert.csr -subj "/CN=localhost"
openssl x509 -req -in cert.csr -out cacert.pem -signkey private.key -days 365
```

![在 WSL 的 Ubuntu 22.04 上依次执行 openssl 的三条命令，再用 chmod 收紧私钥权限，ls -l 能看到 cacert.pem，cert.csr 和 private.key 三个文件](./images/post-20261110/openssl-gen-cert.png)

具体而言：

- `genrsa` 生成 2048 位的 RSA 私钥 `private.key`。**私钥是服务器身份的核心，不能泄漏，也不能提交到仓库里**
- `req -new` 用私钥生成证书签名请求 `cert.csr`，里面装着公钥和一段主题信息。`-subj "/CN=localhost"` 是让 openssl 不要把主题信息一条条问出来，直接写死。`CN` 是 Common Name，表示这张证书签给哪个名字，这里填 `localhost`，和访问用的地址一致
- `x509 -req` 用同一把私钥给请求签名，生成最终的证书 `cacert.pem`。签发人就是自己，所以叫自签名证书。`-days 365` 把有效期设成一年，不加的话默认只有 30 天

> [!NOTE]
> 想把主题信息填全，可以写成 `-subj "/C=CN/ST=Liaoning/L=Shenyang/O=PureSky/CN=localhost"`，其中 C 是国家，ST 是省份，L 是城市，O 是组织。测试证书里这些字段不影响使用，关键只有 CN 要和访问地址一致。

运行完目录里多出三个文件：

- `private.key` 私钥，Nginx 拿它完成 TLS 握手，权限收紧到 600 只让自己读
- `cert.csr` 签名请求文件，证书签出来之后就用不上了，留着或删掉都行
- `cacert.pem` 证书本体，浏览器会收到它，里面是公钥，主题信息，还有签名

### 修改 Nginx 配置

回到站点配置。希望你还记得我们之前部署博客时改的是 `/etc/nginx/sites-enabled/default`，这次还是它，用 VS Code 打开：

```bash
code /etc/nginx/sites-enabled/default
```

找到文件里的 `server {`，在 `listen 80` 那两行下面加上 443 的监听和证书路径。默认文件里本来就留了一段注释掉的 `# SSL configuration`，把那几行替换成这样：

```nginx
server {
    listen 80 default_server;
    listen [::]:80 default_server;

    # SSL configuration
    listen 443 ssl default_server;
    listen [::]:443 ssl default_server;
    ssl_certificate /etc/nginx/ssl/cacert.pem;
    ssl_certificate_key /etc/nginx/ssl/private.key;

    # 剩下的站点配置不用动
}
```

![在 VS Code 里打开的 sites-enabled/default，server 块里多了 listen 443 ssl 和 ssl_certificate 和 ssl_certificate_key 两组配置](./images/post-20261110/vscode-ssl-config.png)

注意 `listen 443 ssl` 里的 `ssl` 参数不能省，省了 Nginx 会把 443 当成明文端口用。`ssl_certificate` 指向证书，`ssl_certificate_key` 指向私钥，写绝对路径是最稳妥的。这两条指令也可以只写文件名，相对路径是相对 Nginx 的 `--prefix` 目录（`/usr/share/nginx`），很容易找错。

> [!NOTE]
> 同样的，这里改的是站点配置而不是页面内容，必须 reload 才生效。

检查并重载：

```bash
nginx -t
nginx -s reload
```

再用 curl 确认一下 TLS 已经起来了，`-k` 是让 curl 跳过证书校验（自签名证书它也不认）：

```bash
curl -kI https://localhost
```

![执行 nginx -t 检查通过，nginx -s reload 重载，再用 curl -kI https://localhost 看到 HTTP/1.1 200 OK](./images/post-20261110/nginx-t-reload-curl.png)

### 用浏览器验证

打开浏览器，地址栏输入 `https://localhost`。因为证书是自己签的，Chrome 没在信任列表里见过这个签发者，会先拦一下：

![Chrome 打开 https://localhost 时显示“您的连接不是私密连接”，错误码 ERR_CERT_AUTHORITY_INVALID](./images/post-20261110/https-cert-warning.png)

点页面左边的“高级”，会展开一段说明，最底下有一个“继续前往localhost（不安全）”的链接：

![点开“高级”之后显示自签名证书的原因，底部出现“继续前往 localhost（不安全）”的链接](./images/post-20261110/https-cert-advanced.png)

点这个链接，页面就正常打开了，地址栏里能看到 `https://localhost`：

![继续前往之后博客首页正常显示，地址栏是 https://localhost，左边仍然标着“不安全”](./images/post-20261110/https-cert-ok.png)

注意地址栏左边还是标着“不安全”，这是正常的：点“继续前往”只是让浏览器对这一次访问放行，不代表它认可这张证书。换一个浏览器或者清掉浏览器数据之后再访问，警告还会再出现一次。

> [!NOTE]
> 自签名证书只适合本机和内网测试。公网域名用自签名证书的话每个访客都会看到这个警告，而且浏览器没法验证签发者，还容易被中间人冒充。线上一定要用受信任的 CA 签的证书。

## 免费证书从哪里来

当然，正式上线的话就需要浏览器信任的 CA 签证书。什么你说你没钱？预算为零也没关系，下面这些都能拿到免费证书，但有效期都很短，政策也会变，用之前以官网为准：

| 平台 | 免费额度 | 特点 |
| --- | --- | --- |
| Let’s Encrypt | DV 证书，90 天 | 最常用，支持 ACME 自动签发和续期，配 certbot 或 acme.sh 用。2027 年 2 月起有效期会缩短到 64 天 |
| ZeroSSL | DV 证书，90 天 | 有网页控制台也支持 ACME，可以当 Let’s Encrypt 的备选 |
| Cloudflare | Universal SSL 免费 | 域名接入 Cloudflare 代理后自动签发和续期，覆盖根域名和一级子域名。回源可以用免费的 Origin CA 证书，只被 Cloudflare 信任 |
| 阿里云 | 个人测试证书（免费版），90 天，每个自然年 20 张 | 单域名，不支持泛域名，官方定位是测试场景 |
| 腾讯云 | 免费 DV 证书，90 天，一个账号最多 50 张 | 单域名，不支持泛域名和 IP |

如果域名已经解析到这台机器，用 Certbot 一条命令就能申请并自动改好 Nginx 配置：

```bash
sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d example.com -d www.example.com
```

Certbot 会顺带装好自动续期的定时任务，证书到期前自动换新的，不用手动处理。前提是域名解析到这台机器，80 端口能从公网访问，本机的 localhost 是不行的。

> [!NOTE]
> 免费证书基本都只签单域名 DV 证书。泛域名证书 Let’s Encrypt 也支持，但必须用 DNS-01 方式验证，也就是在 DNS 里加一条 TXT 记录，需要你对域名的 DNS 有控制权。
