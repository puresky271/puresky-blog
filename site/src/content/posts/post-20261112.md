## 数据库和数据库管理系统

我们经常说“把数据存进 MySQL”，“这个项目的数据库是 MongoDB”，严格来说这两句话都不太对。CMU的课程讲义里给数据库下的定义是这样的：

> A database is an organized collection of inter-related data that models some aspect of the real-world.
>
> 数据库是一种有组织的，相互关联的数据集合，它描绘现实世界的某个方面。

- 有组织，说明它不是随便堆在磁盘上的一坨字节
- 相互关联，说明数据之间有关系，比如专辑属于某个歌手
- 描绘现实世界，说明数据库是对现实的建模，不是现实本身

此外，**人们经常把“数据库”和“数据库管理系统”当成同一件事**，比如把 MySQL，Oracle，MongoDB，Snowflake 这些软件都叫作“数据库”。这些软件的正确名字是 DBMS（database management system，数据库管理系统），它们的定义是：

> A database management system (DBMS) is software that allows applications to store and analyze information in a database.
>
> 数据库管理系统是让应用能够存取并分析数据库里信息的软件。

数据库是数据本身，以及数据之间的组织方式。DBMS 是管理这些数据的软件，它替你处理存储，查询，并发，故障恢复这些脏活。你安装的是 DBMS，你创建的是 database，你写 SQL 是写给 DBMS 的。[^1]

### 一个音乐商店和两个 CSV 文件

CMU的第一讲基本只用一个例子：一个数字音乐商店（digital music store），类似 Spotify 那种。

> [!NOTE]
> Spotify（声田） 是全球最知名的音乐流媒体平台之一，可以简单理解为音乐领域的 Netflix。
> 它允许用户通过互联网在线收听音乐、播客和有声内容，而不需要提前下载音频文件。

这里的商店里面有两类东西：一类是歌手（Artist），包括名字，年份（乐队的成立年份或歌手的出道年份），国籍。另一类是专辑（Album），包括名字，歌手，发行年份。用课程里的数据写出来大概是这样：

Artist

| name          | year | country |
| ------------- | ---- | ------- |
| Wu-Tang Clan  | 1992 | USA     |
| Notorious BIG | 1992 | USA     |
| GZA           | 1990 | USA     |

Album

| name             | artist       | year |
| ---------------- | ------------ | ---- |
| Enter the Wu-Tang | Wu-Tang Clan | 1993 |
| St.Ides Mix Tape  | Wu-Tang Clan | 1994 |
| Liquid Swords     | GZA          | 1995 |

> [!TIP]
> 注意 Album 表里 artist 这一列存的是歌手的名字，而不是歌手的编号。**这个看起来很自然的决定会在后面几乎每一个环节里制造麻烦**。请你先记住这一点，我们马上就会用到。

欸，但是一个只有几十个歌手和几十张专辑的小店真的需要数据库吗？我们用文本文件存下来，程序读一读写一写似乎就够了。

这种方案其实有自己的名字：**扁平文件稻草人（flat file strawman）**，strawman 指故意搭得很简单，专门用来被拆穿的方案。

那么假设我们要做一个数字音乐商店的数据库，记录艺人和他们发行的专辑，这就需要两类信息：艺人的名字，年份，国家，以及专辑的名字，所属艺人，发行年份，每个实体一个文件。

字段如下：

Artist(name, year, country)
Album(name, artist, year)

落到磁盘上就是两个 CSV（comma-separated values，逗号分隔值）文件，每行一条记录，字段用逗号分开，字段含逗号时用双引号包住。

这里数据直接用课上的示例，artist.csv ：

```csv
"Wu-Tang Clan",1992,"USA"
"Notorious BIG",1992,"USA"
"GZA",1990,"USA"
```

album.csv ：

```csv
"Enter the Wu-Tang","Wu-Tang Clan",1993
"St.Ides Mix Tape","Wu-Tang Clan",1994
"Liquid Swords","GZA",1995
```

![CMU 15-445 Fall 2024 Lecture #01 第 10 页：把音乐商店的数据放进 Artist 和 Album 两个 CSV 文件](./images/post-20261112/slide-flat-file.png)

可以看到，这里的所有字段都充当了字符串，比如年份 1992 在文件里只是四个字符，想当数字用你还得得自己转，也就是**应用每次读写记录都必须自己解析文件**（the application must parse the files each time they want to read/update records）。[^2]

如果还要记录单曲或订单就继续加文件，每个实体一个。因为文件之间没有连接，所以唯一的联系是字段里写着的名字。

课程的第一个查询很朴素：GZA 是哪一年单飞（~~我很抱歉~~）的？CSV 方案的代码大概是这样，parse 由程序员自己写：

```python
file = open("artist.csv", encoding="utf-8")

for line in file.readlines():
    record = parse(line)
    if record[0] == "GZA":
        print(int(record[1]))
```

这几行代码把整个文件读进内存逐行 parse 再逐行比较，这就是**全表扫描**（full table scan），表里有三行就扫三行，有三千万行就扫三千万行，代价随行数线性增长。这是因为文件里没有索引，没有结构告诉程序“GZA 大概在第几行”。

偶尔这样查一次还能忍，查询多了可就麻烦大了，我们的应用会慢慢长成简陋的查询引擎，这很不好。

### 麻烦一：数据完整性

数据完整性（data integrity）指数据要满足业务规则：CSV 不拦任何东西，写进去就算数，规则执行全靠写文件的程序自觉。

- 怎么保证专辑里的艺人和艺人表里是同一个？有人把“Wu-Tang Clan”打成“Wu Tang Clan”，join 就对不上。名字是唯一联系，而名字并不唯一
- 谁把专辑年份覆盖成非法字符串？比如改成“nineteen ninety three”。CSV 没有类型，程序忘了检查，坏数据就进去了，读的时候才报错
- 一张专辑有多个艺人怎么办？feat. 的客串往哪放？Album.artist 只有一个字段，塞拼接字符串吧，格式立刻不统一
- 删除有专辑的艺人呢？从 artist.csv 删掉 GZA，album.csv 里的 Liquid Swords 还在，这就是孤儿记录（orphan）。谁来级联删除？


### 麻烦二：查询与实现

还有第二关：应用代码和文件格式绑死在一起。

文件格式本身变成了接口。Python 写了一份解析逻辑，Java 服务要用这份数据就得再写一份。逗号怎么切，引号怎么处理，换行和编码怎么办，两套代码只要有一处理解不同，读写就可能不一致。更糟的是改结构：给专辑加一个流派字段所有读写代码都要跟着改，因为字段位置写死在代码里。

然后是机器。数据在 A 机器的本地磁盘上，B 机器读不到。用网络共享盘挂过去，延迟和文件锁又是一堆新问题。

### 麻烦三：并发

两个线程同时写同一个文件会怎样？最典型的是丢失更新（lost update）。两个请求同时改同一张专辑，A 把整个文件读进内存改成 1994，B 也读进内存改成 1995，A 先写回，B 再写回，A 的修改没了，两个人都以为自己成功了。

如果两个线程同时追加记录，写入不是一步完成时两行可能交错。一个线程正在写，另一个读到写了一半的内容，看到的是不存在的中间状态。A 读到旧值后 B 改了文件，A 再基于旧值写回，也覆盖掉 B 的更新。

文件锁（file lock）能挡一部分冲突，但粒度通常是整个文件，一个请求写时别人做不了事。跨机器共享盘时锁的行为也不一定可靠。想细一点就要自己实现读写锁，锁顺序，死锁检测和超时，那是在应用里重写并发控制。

### 麻烦四：持久性

机器在更新记录时崩溃会怎样？磁盘上的文件可能是旧版本，新版本或者写了一半的垃圾。CSV 没有日志和提交记录，程序重启后无法判断上次操作完成没有。

还有一个更隐蔽的丢失：写接口返回成功，数据可能还躺在操作系统的页缓存里，没有真正到磁盘，这时候断电就没了。用户看到了“保存成功”，但重启后数据就没了。

---

同时CSV 也没有任何访问控制，谁能读文件谁就能看到全部数据。而数据库可以按用户，按表，按列授权，这是管理的一部分。

CSV 不是唯一的靶子，换成 JSON 文件，压缩包，网络共享盘，麻烦一个都不会少，因为问题来自“应用自己管理存储”。要一次性解决，就需要专门的软件接管，把数据模型 / 查询语言 / 索引 / 并发控制 / 恢复 / 权限打包进来。这就是 DBMS。

## 数据库管理系统要解决的

| 麻烦 | 用 CSV 时会怎样 | DBMS 的接手机制 |
| --- | --- | --- |
| 数据完整性 | 歌手名拼错，年份是乱字符串，删歌手留下孤儿专辑 | 模式与约束（类型 / NOT NULL / UNIQUE / PRIMARY KEY / FOREIGN KEY / CHECK） |
| 查询 | 找一个 GZA 要扫全表，关联两张表要手写循环 | 索引，查询优化器 |
| 实现耦合 | 文件格式就是接口，换语言要重写解析，换机器读不到文件 | 声明式查询语言（SQL），客户端/服务端 |
| 并发 | 两个线程读改写同一文件，更新丢失或读到半截 | 事务（transaction），并发控制（锁 / MVCC） |
| 持久性 | 写一半断电，文件不一致，没有回滚和副本同步 | 预写日志（WAL），崩溃恢复（recovery），复制（replication） |

DBMS其实就是让应用存取数据库里信息的软件。完整版还规定了它要支持什么：按照某种数据模型，完成数据库的定义，创建，查询，更新和管理（definition, creation, querying, update, administration）。

最重要的词可能是通用（general-purpose）。DBMS 不是为音乐商店写的程序，而是为所有应用准备的软件，任何应用带自己的模式来都能用。正因通用，它才有动力把公共的麻烦做进内核：索引做一次，所有查询受益。[^3]

### 声明式接口

回到 GZA 的查询。用 CSV 时要打开文件，解析，循环，比较。

然而有了 DBMS，写成一句 SQL 就ok：

```sql
SELECT year FROM Artist WHERE name = 'GZA';
```

这句 SQL 只说了要什么：Artist 表里 name 是 GZA 那一行的 year 列。它没说从哪行开始找，没说要不要走索引，没说文件怎么读，这些由 DBMS 决定。课程把查询语言分两类：过程式（procedural）要你指定策略，比如用 for 循环扫所有记录数数。非过程式（non-procedural，也叫声明式 declarative）只说想要什么。

```python
count = 0
for line in file.readlines():
    count += 1
print(count)
```

```sql
SELECT COUNT(*) FROM Artist;
```

这里的两段代码做同一件事，只是第一段把“怎么数”写死在应用里，第二段留给 DBMS。

差别不只在于代码的长短，数据量小可以全表扫，name 上有索引可以直接走索引，行数变化还能换计划，应用看到的 SQL 始终不变。这就是数据独立性（data independence）：**应用依赖逻辑结构，不依赖物理实现**。SQL 还是关系型数据库事实上的标准语言，各语言发出去的是同一种查询。

声明式不等于不管性能，你仍然要建合适的索引，仍然要知道一条查询会扫多少行，只是“怎么执行”的决策权集中到了查询优化器（query optimizer）手里，不再散落在每个应用里。

## 数据模型：组织数据的几种世界观

DBMS 能管理各种应用的数据靠的正是先约定一套描述数据的方式。还是那家音乐商店，还是 GZA 和他的专辑，同样是“GZA 在 1995 年发行了 Liquid Swords”这一件事，在四种模型里面这样放：

- 关系模型里，它是 Album 表里的一行，通过 artist_id 指向 Artist 表里的一行
- 键值模型里，它是某个键对应的一个值，值里面写了什么，数据库不关心
- 图模型里，它是两个节点和一条边
- 文档模型里，它是嵌套在 GZA 文档里的一个数组元素

这其中的区别在于你以后要怎么查它，以及你愿意让数据库承担多少约束。

### 数据模型，模式，实例

数据模型是一组用来描述数据库中数据的概念。模式（schema）是用某个数据模型对一份具体数据做出的描述。

数据模型回答的是“可以用什么样子的积木”。是表和行，还是键和值，还是节点和边。它是一套概念，不针对某一份具体数据。

模式回答的是“这份数据具体由哪些积木组成”。决定用关系模型之后，写下 Artist 表有 id，name，year，country 四个属性，每个属性各是什么类型，哪一个是主键。

实例（instance）回答的是“此刻里面装了什么”。模式说 Artist 有四个属性，实例是此刻表里那三行记录。今天插入一行，明天删掉一行，模式不动，实例一直在变。

没有模式，你手里就是一堆没有意义的随机比特。一串字节之所以能变成“艺人记录”，是因为有人规定了前面的整数是 id，后面的字符串是名字。

> [!NOTE]
> 还有一个常见的误会。文档数据库经常被说成“无模式”。更准确的说法是：它不强制你事先把结构声明完整，结构不一样的记录可以放在一起，但应用读数据时仍然要假设某种结构。模式没有消失，只是从数据库挪到了应用代码里。


### 关系模型

关系模型（relational model）用关系的集合来描述数据。落到最常见的实现上，一个关系就是一张二维表（table），一行是一条记录，也叫元组（tuple），一列是一个属性（attribute）。

音乐商店在关系模型里通常是两张表。

Artist 表：

| id | name | year | country |
| --- | --- | --- | --- |
| 101 | Wu-Tang Clan | 1992 | USA |
| 102 | Notorious BIG | 1992 | USA |
| 103 | GZA | 1990 | USA |

Album 表：

| id | name | artist_id | year |
| --- | --- | --- | --- |
| 11 | Enter the Wu-Tang (36 Chambers) | 101 | 1993 |
| 22 | St.Ides Mix Tape | 101 | 1994 |
| 33 | Liquid Swords | 103 | 1995 |
| 44 | Beneath the Surface | 103 | 1999 |
| 55 | Wu-Tang Forever | 101 | 1997 |

两张表之间没有任何指针。Album 里存的是 artist_id 这个值，它恰好等于 Artist 表里某一行的 id。数据库靠主键（primary key）和外键（foreign key）保证这个对应关系成立：不能插入指向不存在艺人的专辑，也不能随手删掉还有专辑的艺人。

于是“GZA 有哪些专辑”是一句按 artist_id 过滤的查询，“Liquid Swords 是谁的”是一次按 id 连接的查询。你写的是要什么，怎么找到由 DBMS 决定，这种风格叫声明式。

优点是结构稳定，约束由数据库把关，跨表查询和事务都很成熟。代价是模式比较硬，要给专辑加一个录音室属性，得先改表再迁移数据。它最适合结构清楚，关系明确，要求一致性的业务数据。典型产品有 PostgreSQL，MySQL，SQLite，Oracle 和 SQL Server，课件给它的标注是“Most DBMSs”。

### 键值模型

键值模型（key-value model）把整个数据库看成一个巨大的字典：每个键（key）对应一个值（value）。数据库只承诺一件事：**给一个键还你一个值，值的内部是什么它不解释**。

```text
artist:101  ->  {"name": "Wu-Tang Clan", "year": 1992, "country": "USA"}
artist:103  ->  {"name": "GZA", "year": 1990, "country": "USA"}
album:33   ->  {"name": "Liquid Swords", "artist_id": 103, "year": 1995}
```

“artist:101”这种把类型和编号拼进键的写法叫键前缀约定（key prefix），是键值库里最普通的技巧。数据库没有表和列的概念，只能靠你给键起名字来区分数据种类。

操作也很朴素：GET 按键取值，PUT 写入或覆盖，DELETE 删除。没有 WHERE，没有 JOIN，也没有 GROUP BY。想查“GZA 的全部专辑”，要么在应用里遍历所有 album: 开头的键，要么自己再维护一份从艺人到专辑的索引。数据库省下的工作，被推回了应用。

课件第 19 页给它的标注是“Simple Apps / Caching”，简单应用和缓存。典型产品有 Redis，Memcached，Amazon DynamoDB 和 etcd。用来存登录会话，计数器，排行榜和配置项最合适。一旦查询变成按值里的某个字段过滤，键值模型就不帮忙了。

### 图模型：关系本身也是数据

图模型（graph model）由两种东西组成：节点（node）和边（edge）。节点表示实体，边表示实体之间的关系。边可以有方向，有类型，还可以挂属性，这类实现叫属性图（property graph）。

音乐商店在 Neo4j 的查询语言 Cypher 里可以这样写：

```cypher
CREATE (gza:Artist {id: 103, name: "GZA", year: 1990})
CREATE (wu:Artist {id: 101, name: "Wu-Tang Clan", year: 1992})
CREATE (ls:Album {id: 33, name: "Liquid Swords", year: 1995})
CREATE (gza)-[:RELEASED {year: 1995}]->(ls)
CREATE (gza)-[:MEMBER_OF]->(wu)
```

关系模型里，“GZA 发行了 Liquid Swords”这件事没有自己的存储位置，它是从 Album 表里 artist_id 这个值推出来的。但在图模型里它是一条实实在在存着的边。单跳查询看不出差别，跳数一多就贵得不一样。问“和 GZA 合作过的艺人还发行过哪些专辑”，图数据库顺着边走两跳就够，但关系数据库要 JOIN 好几次。

图模型适合关系本身就是主要信息的场景，比如社交网络，知识图谱（knowledge graph），推荐和风控。典型产品有 Neo4j，Amazon Neptune 和 JanusGraph。它不擅长整表聚合，也不适合无方向地遍历超大图，所以图数据库通常只管关系，流水和统计放在别的模型里。

### 文档模型

文档模型（document model）把一条记录存成一个文档（document）。文档里是一层一层的字段和值，字段的值可以是标量，可以是数组，也可以再嵌一个文档。现代实现用 JSON，老一些的系统用 XML 或者自定义对象。

同一个 GZA，在文档模型里可能长这样：

```json
{
  "id": 103,
  "name": "GZA",
  "year": 1990,
  "country": "USA",
  "albums": [
    { "id": 33, "name": "Liquid Swords", "year": 1995 },
    { "id": 44, "name": "Beneath the Surface", "year": 1999 }
  ]
}
```

如果用关系模型，这个对象被拆进两张表，取出来要先 JOIN 再拼装。这个麻烦有个专门的名字，叫关系与对象的阻抗不匹配（relational-object impedance mismatch），文档模型就是冲着它来的。

它的灵活之处在于，结构不一样的记录可以放在同一个集合（collection）里，不用先改表。

代价也有，那就是关联变弱了，GZA 的信息如果嵌在每个专辑文档里，他改个名字就要改很多份。课件也提醒，文档模型仍然会遇到扁平文件那一节里的大部分问题。嵌套也不是越深越好，更新深层字段要先读出整份文档。约束少还意味着错误发现得晚。

文档模型适合整条记录一起读写的场景，比如商品详情，文章和用户档案。典型产品有 MongoDB，CouchDB 和 Couchbase。

### 宽列模型

宽列模型（wide-column model）也叫列族模型（column-family model）。它像一张表，但行和行的列可以完全不同，列按列族（column family）分组，每一行由一个行键（row key）唯一标识。数据库按行键排序存放数据，落在同一段行键范围里的行会被放进同一个分区（partition），所以按行键取一整行非常快。空列不占空间，这对稀疏数据（sparse data）很关键。

音乐商店可以按艺人来组织宽行：

```text
row key: artist:101
  info:    name=Wu-Tang Clan  year=1992  country=USA
  albums:  album:11=Enter the Wu-Tang (36 Chambers) 1993
           album:55=Wu-Tang Forever 1997

row key: artist:103
  info:    name=GZA  year=1990  country=USA
  albums:  album:33=Liquid Swords 1995
           album:44=Beneath the Surface 1999
```

列族分成 info 和 albums 两组。同一个艺人的信息落在同一行里，读“GZA 的所有专辑”就是一次行内顺序扫描。Cassandra 这类产品把这种结构落成主键加排序列（clustering column）。

宽列模型是查询驱动设计：先想清楚按什么键查，再决定表怎么建。想换一种查法，比如按专辑名查，通常要再建一张以专辑名为行键的表。它适合超大规模写入和水平扩展，代价是查询方式被钉得很死，JOIN 基本没有，跨行事务很弱，很多产品只保证最终一致（eventual consistency）。典型产品有 Google Bigtable，Apache HBase，Apache Cassandra 和 ScyllaDB，设计思想来自 Google 的 Bigtable 论文。

### 数组与向量

数组模型（array model）把数据组织成数组，矩阵，张量（tensor），值大多是数字，运算以整块数组为单位。课件把它写成 Array (Vector, Matrix, Tensor)，标注是“ML / Science”，面向机器学习和科学计算。

音乐商店的播放数据很适合用数组表示。把一张专辑最近 7 天，每天 24 小时的播放量存成一个 7 × 24 的矩阵，想看哪张专辑在周末晚上更受欢迎，就在矩阵上按行求和。

```text
               0点  1点  2点  ...  23点
周一           120   98   76  ...   201
周二            98   77   65  ...   180
...
周日           310  280  260  ...   420
```

今天更常被单独讲的是数组模型的一维特例，向量模型（vector model）。做法是先把一段内容，比如专辑名和歌词，交给一个机器学习模型压成一个固定长度的高维向量，这个向量叫嵌入（embedding）。语义相近的内容，向量在空间里的距离也近。课件第 63 页的定义是一维数组，用于最近邻（nearest-neighbor，NN）搜索，常见用途是对 Transformer 模型生成的嵌入做语义搜索。

```text
专辑 11 -> [0.32, 0.78, 0.30, ...]    // 768 维
专辑 33 -> [0.99, 0.19, 0.81, ...]
专辑 44 -> [0.01, 0.18, 0.85, ...]
```

“找出和 Liquid Swords 相似的专辑”这种查询没法用 WHERE 写，因为它要的是向量距离最近，不是字符串相等。所以向量数据库会为向量建专用索引，常见做法有 HNSW 和 IVFFlat，常见工具包括 Meta 的 Faiss 和 Spotify 的 Annoy。查询时把问题也编码成向量，索引返回一组最接近的编号。为了速度，实际系统通常用近似最近邻（approximate nearest neighbor，ANN）搜索，牺牲一点精度换数量级的加速。

向量模型适合语义搜索，推荐，以图搜图和检索增强生成（retrieval-augmented generation，RAG）。它和传统查询是互补的，专用向量数据库有 Milvus 和 Pinecone，很多关系数据库也加了向量扩展，比如 PostgreSQL 的 pgvector。向量只表达像不像，不表达是不是，通常是关系表存结构化字段，向量索引负责召回。[^5]

### 还有几个历史与设计向的模型

层次模型（hierarchical model）把数据按树组织。一个父节点可以有多个子节点，一个子节点通常只有一个父节点，像文件系统的目录树。音乐商店里把 Artist 放在上层，他的专辑放在下层就很自然，但一张专辑有多个艺人时就不好放，同一份数据常常要在好几个分支里重复存。代表实现是 IBM 的 IMS。

网状模型（network model）想解决多对多的问题，记录之间用指针链接，查询靠程序员顺着指针导航。音乐商店里 Artist 和 Album 可以互相连指针，代价是每次查询都要自己顺着链接走。它曾经很主流，但它把逻辑关系和物理存储绑得太紧，后来输给了关系模型。

语义模型（semantic model）关心数据的含义，用概念和规则描述世界。音乐商店里的一条事实可以写成三元组（triple）：“GZA”是主语，“发行”是谓语，“Liquid Swords”是宾语。代表技术是 RDF 和 SPARQL，知识图谱建在这一套上面。

实体关系模型（entity-relationship model，E-R 模型）不是数据库运行时用的模型，而是设计阶段用的画图方法。先找出实体（entity），比如 Artist 和 Album，再画出两者之间的一对多关系（relationship），然后把图翻译成表。

### NoSQL 到底是什么

“NoSQL”这个词不是新词。它在今天的意思最早出现在 2009 年 6 月旧金山的一次非正式聚会。更早在 1998 年，Carlo Strozzi 曾用它命名过一个开源关系型数据库。今天最常见的解释是“Not Only SQL”，意思是“不只是 SQL”，不是“完全不要 SQL”。那批系统反对的是“所有数据都必须塞进关系表”这个前提，不是反对 SQL 这门语言。[^4]

那它为什么会出现呢，这是因为互联网的数据量和并发涨得比单台机器快，关系数据库靠换更强的机器（垂直扩展，vertical scaling）越来越贵，拆到很多台机器上（水平扩展，horizontal scaling）又受制于跨机器的事务和 JOIN。同时很多新数据的结构本来就不整齐。那批系统做了一个交换：放松模式和事务，换扩展性和灵活结构。

![CMU 15-445 Fall 2024 Lecture #01 第 20 页：十种数据模型排成一列，红框圈出的三种属于 NoSQL](./images/post-20261112/slide-data-models.png)

常见的四分法把 NoSQL 分成四类：

| 类别 | 数据形态 | 代表产品 | 典型场景 |
| --- | --- | --- | --- |
| 键值 | 键对应值 | Redis 与 DynamoDB | 缓存，会话，计数 |
| 文档 | JSON 文档 | MongoDB 与 CouchDB | 内容，商品，档案 |
| 图 | 节点和边 | Neo4j 与 Neptune | 社交，知识图谱 |
| 宽列 | 行键加列族 | Cassandra 与 HBase | 日志，时序，超大规模写入 |

在这四类之外，向量数据库是近几年崛起的新类别，但它服务的是机器学习。层次模型和网状模型比 NoSQL 早得多，不该混进这四类。

关系型和非关系型放在一起对照：

| 维度 | 关系型 | 非关系型 |
| --- | --- | --- |
| 数据模型 | 表，行，列 | 键值，文档，图，宽列 |
| 模式 | 写入前通常先定义 | 通常更宽松，由应用保证 |
| 查询语言 | SQL，跨产品接近统一 | 各家 API 和查询语言不同 |
| 事务 | ACID 支持成熟 | 部分支持，能力因产品而异 |
| 扩展 | 传统上以垂直扩展为主，现代产品也支持分片 | 通常为水平扩展设计 |
| 关联 | JOIN | 应用侧拼装或图遍历 |
| 代表产品 | PostgreSQL，MySQL，Oracle | Redis，MongoDB，Neo4j，Cassandra |

> [!NOTE]
> 现而今，这条分界线正在变模糊。关系数据库吸收了 JSON 类型和向量索引，非关系数据库也在补 SQL 接口和多文档事务。


### 怎么选数据模型

选模型之前先问三个问题：

- 数据之间的关系有多重要，查询要跳几层？
- 访问方式是按键取整条，还是按多个条件过滤再组合？
- 一致性和事务的要求有多硬，能不能接受短暂不一致？

我们需要记住：**要让最常执行的那些查询来选模型，而不是让流行度来选模型。**

| 你主要想解决的问题 | 优先考虑 | 原因 |
| --- | --- | --- |
| 转账，下单，库存扣减 | 关系模型 | 强事务，约束，多表关联 |
| 登录会话，缓存，访问计数 | 键值模型 | 按单个键读写，延迟低 |
| 社交关注，知识图谱，路径分析 | 图模型 | 多跳关系遍历快 |
| 商品详情，文章，用户档案 | 文档模型 | 整条记录一次读写，结构灵活 |
| 日志，时序，超大规模写入 | 宽列模型 | 按行键和时间范围读写，易扩展 |
| 语义搜索，推荐，RAG | 向量模型 | 按相似度召回 |
| 报表，统计分析 | 关系模型或分析型数据库 | 复杂 JOIN 与聚合成熟 |

真实系统很少只选一种：一个电商可能用关系数据库管订单和库存，用 Redis 挡缓存，用文档数据库存商品详情，再挂一个向量库做推荐。这种做法叫多模型持久化（polyglot persistence），选型不是站队而是分工。

讲到这里，你会发现关系模型在课件里被反复圈中，这不是课程的偏爱。[^6]下一节我们就来看看它出现之前程序员的日子有多难过，以及它凭什么是最后的赢家。

## 历史插曲：数据该怎么看

关系模型今天看起来很朴素，一张二维表而已。但在 1960 年代末，数据库的世界完全不是这个样子。

那个年代的商用数据库以 IDS，IMS，CODASYL 为代表。它们有一个共同的毛病：逻辑层和物理层是紧紧耦合在一起的。逻辑层描述数据库有哪些实体和属性，物理层描述这些实体和属性实际怎么存放。在早期系统里物理层直接写进应用代码，数据库管理员想改一下数据的存储方式，所有用到这份数据的程序都要跟着重写。

一个特别能说明问题的例子是：假设一个应用需要按键查值，逻辑上最合适的数据结构是哈希表。后来另一个开发者提出，他想做范围查询，找出键落在 a 和 b 之间的所有值，那哈希表就不好用了，B 树才是正确答案。

为了同时支持两种查询，数据库要么对外提供两套接口，要么应用代码把两套实现都写一遍。两种选择都很难看。

用今天的话说，那时候的程序员在写数据库之前，就得先把“未来会执行什么查询”猜个八九不离十。幻灯片上对那个年代的总结只有一句：Computers were expensive, humans were cheap，计算机很贵，人很便宜，所以让人去迁就机器的存储布局。

### CODASYL：顺着指针爬行

那个年代最有代表性的就是 CODASYL 网状模型。它把数据组织成记录和记录之间的集合（set），一个 set 有一个 owner 记录和若干 member 记录，比如一个 Customer 拥有多个 Order。记录之间用指针串成环形链表，Next 指向下一个 member，Prior 指向上一个，Direct 直接指回 owner。举个最小的例子，一个 Customer 下面挂着 Order 1 和 Order 2，从 Customer 出发，顺着 Next 先到 Order 1，再到 Order 2，读完的 Next 又指回起点。

这种数据库被称为导航式数据库（navigational database）。想查“某个顾客的所有订单”，程序必须自己写循环，先找到顾客记录，再顺着 Next 指针一条一条往下走。查询的性能好不好直接取决于程序员对物理指针链的理解。1973 年，CODASYL 的代表人物 Charles Bachman 在图灵奖演讲里把程序员比作导航员（navigator），这个比喻后来成了那个时代数据库编程的代名词。[^8]

问题在于，逻辑上的“顾客拥有订单”和物理上的“指针怎么串”被绑死了。数据在磁盘上挪个位置，上层的程序就可能失效。也就是说，数据库想优化一下存储布局还先得问问所有应用同不同意。

### Codd 的 1969 年

转折点来自 IBM 研究院的一位数学家，Edgar F. Codd。

Codd 看到的景象是，IBM 的开发者每次数据库的结构或者布局一改，就要重写一遍数据库程序。他想找一种办法，让数据怎么存这件事从应用的世界里彻底消失。

![CMU 15-445 Fall 2024 Lecture #01 第 25 页：IBM 的数学家 Ted Codd 与他在 1969 年提出的关系模型](./images/post-20261112/slide-codd.png)

:::photo right 36%
![Codd 1969 年的 IBM 研究报告 RJ 599 首页](./images/post-20261112/slide-1969-paper.png)
:::

1969 年，Codd 提出了关系模型（relational model）。1970 年，他把这个想法写成了论文 A Relational Model of Data for Large Shared Data Banks，发表在《Communications of the ACM》上。这篇论文后来被公认为数据库领域的奠基之作。[^7]

关系模型的主张可以概括成三条：

- 用简单的数据结构存数据，也就是关系（relation）
- 物理存储交给 DBMS 的实现去决定
- 通过高级语言访问数据，由 DBMS 自己找出最好的执行策略

第一条把数据从指针网里解放出来，变回一张张独立的表。第二条是关键，数据怎么摆在磁盘上，是 DBMS 内部的事，应用不需要知道。第三条更重要，程序员只要说清楚要什么，至于先过滤还是先连接，走索引还是全表扫描，交给 DBMS 去规划。

### 辩论

理论出来后，旧的势力并没有立刻认输。1974 年 5 月，ACM SIGFIDET 研讨会在密歇根州安娜堡开了一场会，会上有一篇论文的标题叫 The Differences and Similarities Between the Data Base Set and Relational Views of Data，直译过来就是《数据库的 Set 视图与关系视图之异同》。CODASYL 派和关系派正面交锋，这就是数据库史上著名的“大辩论”。[^9]

前面那张幻灯片的左半边就是四位当事人的照片。左起是 Codd，然后是 Bachman，后面还有 Jim Gray 和 Michael Stonebraker。这张照片本身就是一段历史，**四个人后来都拿了图灵奖**。

那场辩论当场没分出胜负，但几十年后的结果很清楚：关系模型赢了。

赢在哪里？答案不是“表比指针好看”，而是数据独立性。

关系模型把数据库切成三层。最底下是物理模式（physical schema），描述页，文件，区段这些存储细节。中间是逻辑模式（logical schema），描述有哪些表，有哪些约束，也就是你写 SQL 时面对的那一层。最上面是外部模式（external schema），也就是视图，针对某个应用裁剪出来的数据子集。

应用只和逻辑层或者外部层打交道。物理层怎么改，只要逻辑层不变，应用一行代码都不用动。反过来，DBMS 也可以根据机器环境，数据量和负载特点，自己调整底层布局，甚至在运行中重新优化。应用和存储从此各过各的。

这就是关系模型真正的胜利。它赢的不是性能，而是可维护性。表结构让数据变得可读，数据独立性让系统变得可改。后来的 SQL 之所以能成为事实标准，也是因为它是声明式的，你描述结果，不描述过程。

## 关系模型长什么样

关系模型把数据组织成 relation，这个词在中文里翻成关系。课程在术语和日常说法之间做了一个很省事的对应：

- relation（关系）约等于 table（表）
- tuple（元组）约等于 row（行）
- attribute（属性）约等于 column（列）
- domain（域）是属性允许取值的集合

定义写下来是这样的：A relation is an unordered set that contains the relationship of attributes that represent entities。一个关系是一个无序集合，里面的元素是描述实体的属性之间的关系。再直白一点，一行就是一个实体，一列就是实体的某个属性特征，整张表就是一类实体的集合。

![CMU 15-445 Fall 2024 Lecture #01 第 32 页：relation，tuple，domain 的定义，以及 n 元关系与 n 列表格的对应](./images/post-20261112/slide-relation-tuple.png)

还有几个和 tuple 有关的细节：

- 一个 tuple 是一组属性值，每个值都必须落在对应属性的 domain 里，比如 year 只能填整数
- 传统上要求每个值都是原子值（atomic）或者标量（scalar），也就是说单元格里不能再塞一张表。这被称为第一范式，现代一些数据库放宽了这条限制，允许数组和嵌套结构，但关系模型的原教旨版本是严格的
- 有一个特殊值叫 NULL，它属于每一个 domain，表示这个属性的值未知或者不存在。NULL 带来的麻烦比初看上去多得多，后面的 SQL 部分会专门和它纠缠

一个有 n 个属性的关系叫 n 元关系（n-ary relation），等价于一张有 n 列的表。这句话就是幻灯片上那个等号的来源。

> [!NOTE]
> relation 在数学定义上是无序集合，而 SQL 的表允许重复行，物理上也有存储顺序，但语义上不保证顺序，想要顺序必须写 ORDER BY。这不是课程讲错了，而是工程实现对模型的妥协。初学阶段不必纠结集合和多重集的区别，但知道“表是关系的工程化实现”而不是“关系的定义本身”，以后读论文会轻松很多。


课程把关系模型拆成三个侧面来看。结构（structure）定义关系和数据长什么样，完整性（integrity）保证内容满足约束，操作（manipulation）是访问和修改数据的编程接口。

![CMU 15-445 Fall 2024 Lecture #01 第 30 页：关系模型的三个侧面，结构，完整性与操作](./images/post-20261112/slide-relational-tenets.png)

### 主键：一行到底是谁

三行数据放在一起，凭什么说第一行和第二行是两条记录？

靠主键（primary key）。关系的主键唯一标识表里的一个 tuple。幻灯片上的定义只有一句话，A relation's primary key uniquely identifies a single tuple。

以 Artist 表为例，加上 id 之后，每一行有了一个编号，编号不重复，一眼就能指认：

| id  | name          | year | country |
| --- | ------------- | ---- | ------- |
| 101 | Wu-Tang Clan  | 1992 | USA     |
| 102 | Notorious BIG | 1992 | USA     |
| 103 | GZA           | 1990 | USA     |

这里有两个实践上的细节：

- 第一，不是每张表都必须由人手动指定主键，有些 DBMS 在表没有定义主键时，会自己造一个内部主键
- 第二，即使定义了主键，人也不一定想手动编数字，所以 DBMS 普遍支持自增主键，这门课把它叫 identity column。不同数据库的写法不一样，SQL 标准里叫 IDENTITY，PostgreSQL 和 Oracle 用 SEQUENCE，MySQL 用 AUTO_INCREMENT

![CMU 15-445 Fall 2024 Lecture #01 第 34 页：给 Artist 表加上 identity 列当主键](./images/post-20261112/slide-primary-key.png)

没有主键的表，两条完全相同的记录在语义上就无法区分，改哪一条删哪一条都只能靠猜。更麻烦的是一旦别的表要通过外键指向这张表，没有主键就无从指起。

### 外键：把两张表接起来

回到音乐商店。Album 表里如果只存一个 artist 名字，那问题很快就会出现：Wu-Tang Clan 的专辑不止一张，每张都要把组合名字抄一遍，抄一次就有一次抄错的机会。更麻烦的是现实中一张专辑可能有多位歌手，一位歌手也可能出现在很多专辑里，这是典型的多对多关系，一个格子塞不下。

关系模型的做法是把“谁属于谁”从行里拆出去。第一步，给 Album 里的 artist 列换成一个编号，指向 Artist 的主键，变成 Album(id, name, artist_id, year)。第二步，如果一张专辑可能有多位歌手，就把这层关系再抽出来，单独变成一张中间表 ArtistAlbum，只存 artist_id 和 album_id 两列，Album 只留下自己的属性：

```sql
Artist(id, name, year, country)
Album(id, name, year)
ArtistAlbum(artist_id, album_id)
```

ArtistAlbum 里的 artist_id 是 Artist.id 的外键（foreign key），album_id 是 Album.id 的外键。外键的定义是，一个关系里的某个属性，映射到另一个关系里的某个 tuple，通常就指向另一张表的主键。

外键换来的保证叫引用完整性（referential integrity）。你不可能往 ArtistAlbum 里插一个根本不存在的 artist_id，也不可能随随便便把一个还有专辑挂着的歌手删掉，数据库要么拒绝这次操作，要么按事先约定的规则把它关联的数据一起处理。回头看看扁平文件那一节里的孤儿专辑，同一件事在关系模型里从“祈祷它别发生”变成了“数据库不让你发生”。

### 约束：把业务规则写进结构里

外键只是约束（constraint）的一种。约束的定义是用户定义的，数据库的任何实例都必须满足的条件。它可以在一个 tuple 内部校验，也能跨关系校验。

下面是一个典型的例子：

```sql
CREATE TABLE Artist (
  name VARCHAR NOT NULL,
  year INT,
  country CHAR(60),
  CHECK (year > 1900)
);
```

语句里的 NOT NULL 规定 name 不能为空，CHECK 规定 year 必须大于 1900。除此之外还常见 UNIQUE 唯一约束和主键约束，以及刚讲过的引用约束。约束的意义在于，DBMS 会挡住所有违反规则的修改，不管这个修改来自哪个应用，哪种语言。数据完整性从应用代码里的 if 判断，上移成了数据库结构的一部分。

### 关系代数的一小步预告

表建好了，接下来是怎么从表里拿数据。课程把数据库对应用暴露的这套接口叫 DML（data manipulation language，数据操纵语言），并把它分成两大类。

- 过程式：查询里要指定“怎么找”，用循环，集合操作这些手段描述执行策略。比如写一个 for 循环扫完整张表来数有多少条记录
- 非过程式，也叫声明式：查询里只说“要什么”，不说“怎么找”。比如直接写 SELECT COUNT(*) FROM artist

![CMU 15-445 Fall 2024 Lecture #01 第 40 页：过程式 DML 与声明式 DML 的分野](./images/post-20261112/slide-dml.png)

声明式是关系模型最深的一个设计。拿一句最简单的 SQL 举例：

```sql
SELECT name, year FROM Artist WHERE country = 'USA';
```

这句话只说了要美国歌手的名字和年份，没有说要走索引还是全表扫描，也没有说先过滤还是先投影。选择执行策略是 DBMS 的工作。下一篇要讲的关系代数（relational algebra），就是描述这些操作的数学语言，选择，投影，并，交，差，笛卡尔积，连接，每个运算符吃进一张或几张表，吐出另一张表。SQL 是它的外套，关系代数是里面的骨架。[^10]

## 操作系统是朋友，也是敌人

DBMS 看上去直接和磁盘打交道，其实它只是跑在操作系统上的用户态程序。第 6 讲 Buffer Pools 的课件里有一句很直白的话：The OS is not your friend，操作系统不是你的朋友。但数据库又离不开它，为什么既是朋友又是敌人，要看它给的服务和它自作主张的策略。[^11]

### 朋友：它给了数据库一切基础服务

说操作系统是朋友一点不夸张，DBMS 需要的底层能力几乎都由它提供。

文件系统是第一位。DBMS 把数据页组织成文件，打开，读取，写入，追加，目录和大文件的支持，页在文件里的偏移，都由它包了。

设备抽象是第二位。机械硬盘，固态硬盘，网络存储对上层都是块设备，DBMS 不用为每种硬件写驱动。线程和调度也是它给的，线程的创建，阻塞，唤醒和 CPU 时间分配都由操作系统负责。

还有虚拟内存和网络。应用申请的大块内存由操作系统映射，客户端/服务端架构的 socket 也是它提供的。没有这些，DBMS 得从写驱动开始。

### 敌人：页缓存和延迟刷盘

问题不在操作系统做得差，而在它不知道数据库的语义。它服务所有程序，策略必须通用，通用策略碰上数据库的专门需求会打架。最典型的两处是页缓存（page cache）和延迟刷盘（delayed write）。

数据库要自己管缓存，理由只有一句话：只有它知道哪一页马上还要用。

操作系统读文件时会把块留在内存，写文件也先写进内存，下次访问同一块直接命中。缓存统一管理，内存不够时按替换策略淘汰页面，常见的是近似 LRU（最近最少使用）。

数据库有自己的热点知识。索引页反复被访问，不能轻易淘汰。可一次全表扫描会把几百万页面读进来，每个只用一次。操作系统按 LRU 判断新读的该留下，于是把索引页挤了出去。

扫描结束后，索引查询全部落回磁盘。课程把这种现象叫顺序泛滥（sequential flooding）：一次性大扫描污染缓存，把有用的页面冲走。数据库知道扫描用完就扔，却没法告诉操作系统“这些页别缓存”，也不知道它缓存了什么，何时淘汰谁。

再看延迟刷盘。程序调用 write，通常只是把数据拷进内核页缓存就返回，真正写磁盘由操作系统之后批量完成。吞吐高了，但数据库需要的保证比“迟早会写下去”硬得多。

预写日志的规则是：日志必须先落到稳定存储，对应的数据页才能落盘。否则崩溃后可能数据页已经写下去，日志还在内存里，恢复时看到的就是一份日志缺失的数据，重放出错误结果。

可操作系统不知道这条规则，它只看见一堆脏页，哪个先刷，刷多少，由回写策略决定。数据库要的顺序，可能被一次好心的提前刷盘打乱。

主动调 fsync 强制刷盘行不行？fsync 是同步等待，代价高，只能保证“我要求刷的这部分”，对其余脏页的顺序和时机仍然没有控制权。数据库要的是每个依赖顺序都被保证，不是大部分时候没问题。

还有人用 mmap 把数据文件映射到地址空间。但缺页（page fault）由操作系统决定何时取页，脏页何时写回也由它决定，数据库看不到这些事件，也就无法预测下一次访问会不会卡住。

### 于是数据库开始绕过操作系统

既然通用策略不适用，数据库就自己做一套，这就是缓冲池（buffer pool）的由来。

DBMS 启动时申请一大块内存，切成固定大小的帧（frame），每个帧装一个数据页。页表记录哪个页在哪个帧，脏标记（dirty flag）表示页被改过需要写回，引用计数（pin count）表示有多少线程在用，用着的页不许驱逐。替换策略自己定，比如 LRU-K，CLOCK，或者按查询划分缓冲区，把一次性大扫描限制在小块区域。什么时候写回磁盘也自己排。

这样一来，内存里有什么，该淘汰谁，日志和数据谁先写，全都心中有数。相当于在用户态实现了一个面向数据库的小操作系统，把决策权拿了回来。

再进一步是直接 I/O（direct I/O）。Linux 打开文件时可以加 O_DIRECT 标志，读写绕过内核页缓存，数据直接在磁盘和数据库的缓冲区之间走。Windows 上对应 FILE_FLAG_NO_BUFFERING。好处是没有双重缓存，也完全清楚哪些页在内存里，刷盘顺序可控。

但代价也要说清楚，绕过页缓存就失去操作系统的预读（readahead）和写合并，直接 I/O 还要求缓冲区地址，偏移和长度按块大小对齐，小随机读写可能变慢。所以很多系统把它做成可选项，日志和大表扫描用直接 I/O，小随机访问仍走缓冲 I/O。不是所有数据库都靠 O_DIRECT 活着，但把 I/O 决策权拿回来的方向是共通的。

这些细节第 3 篇讲存储与缓冲池时再展开，这里只要记住数据库把 I/O 的决策权拿回来了。

回看 CSV 方案，它连“要不要缓存”都问不出来，缓存是操作系统替它做的。DBMS 用操作系统的底层调用，却不用它的高层策略：朋友给的工具照用，敌人的自作主张绕开。后面学存储引擎，缓冲池，日志和恢复的原因就在这里。
