先说一个基本问题：你用记事本写一段话，得到的是长长一串字符，每个字符只有一条信息：它是哪个字母，或者哪个汉字。用 Word 写同样一段话，你还能给几个词加粗，给整段设字号，把某一行改成标题。多出来的这些格式，存放在哪里？

区别在于内容和格式是不是分开存。纯文本里，字符就是全部，格式和字符是一体的，没有单独放格式的地方。富文本把两者拆开，字符之外还能再存格式和结构。加粗是贴在字符上的标记，标题是加在整段上的结构，它们都不在文字本身里，而是和文字一起构成一份文档。

这件事看着简单，却引出了大部分难题。一旦允许文字之外还有格式，就要回答三个问题：格式存在哪，编辑时听谁的，多个人同时编辑时怎么不冲突。现代富文本编辑器的难点，基本就是这三件事。

## 一、富文本是什么

把一份富文本文档拆开，是三层。

最底层是文字本身，一段字符序列。中间是字符级的格式，也就是贴在某个字符或某段字符上的标记，加粗、斜体、颜色、链接。最上面是块级结构，段落、标题、列表、表格，它们不附着在单个字符上，而是把一串字符组织成有层级关系的整体。

这个三层模型的价值不在分类，而在于它决定了数据怎么存。字符级格式适合贴在字符上一起存，块级结构适合组织成一棵树。后面的编辑器，本质都是在用不同方式回答同一件事：这三层信息，各自放进什么数据结构，又怎么保证它们互相不打架。

## 二、富文本的历史

富文本编辑不是网页时代才有的东西，它起源于半个世纪前。

1974 年，Xerox PARC 的 Butler Lampson、Charles Simonyi 等人在 Xerox Alto 上做出了 Bravo，被公认是第一个所见即所得（WYSIWYG）的文档程序[^1]。在 Bravo 之前，排版和内容是两道分开的工序，作者写的是带标记的代码，要等打印出来才知道长什么样。Bravo 第一次让屏幕上的样子和最终打印出来的一致，作者直接看着成品编辑。它背后有一个前提：Alto 有能逐点显示图形的位图屏幕，才装得下“所见即所得”。

1987 年，微软发布了 Rich Text Format（RTF），一种用纯文本描述富格式文档的交换格式[^2]。它把所有格式写成一串带反斜杠的控制词，比如 `{\b bold}` 表示加粗。RTF 的目的不是给某个程序当内部格式，而是让 Word 和别的软件之间能互相读懂带格式的文档。它主要确立了一个观念：富文本可以脱离具体的程序，变成一种能传输、能解析、能再生成的中立表示。

真正把富文本带进浏览器的是 2000 年。微软在 Internet Explorer 5.5 里引入了 `contentEditable` 和 `designMode` 两个特性，让网页里的任意元素可以编辑[^3]。这一步影响很大，因为它把“所见即所得”的载体从桌面软件的私有渲染引擎，换成了浏览器通用的 DOM。从此任何人都能在网页里做一个富文本编辑器，代价是，也从此背上了 DOM 这副担子。

## 三、contentEditable 的几个坑

`contentEditable` 的设计初衷是给表单用的，不是给文档创作用的。它把一个 DOM 元素变成编辑面，但浏览器到底往这个 DOM 里写什么，很多地方没有统一定义。现代编辑器要处理的坑，多数来自这里。

第一个坑是浏览器之间的不一致。同样一次回车，Chrome 在一个空标题里可能插入 `<div>`，Firefox 可能插入 `<p>`，Safari 可能是 `<br>`。同样一次粘贴，各家塞进去的包装标签、`mso-*` 私有类名都不一样。如果你的数据源是 DOM 本身，同一份操作会在不同浏览器上产生不同的文档，你的文档就会因为浏览器不同而变得不一样。

第二个坑是输入法组合输入，也就是 IME。中文、日文、韩文这些语言靠输入法把多次击键合成一个字符。用户在输入法里拼“qingkong”的过程中，浏览器会持续发出组合事件，中途的 DOM 状态是临时的、不完整的。编辑器如果在这个阶段强行拦截或者重写，就会打乱输入法的候选框，出现字符翻倍、候选框闪烁这类问题。

第三个坑是选区。光标和选中范围是编辑器的核心，但 Selection 和 Range 这套 API 在很多边界上没有规范定义。光标落在零宽度的块边界上，三击选中，跨嵌套块选中，这些操作每个浏览器都有自己的一套算法。编辑器要把 DOM 坐标翻译回自己的数据模型坐标，再在需要时翻译回去，这段来回映射是全编辑器最容易出 bug 的地方。

第四个坑是撤销粒度。什么算一次可以撤销的动作，一次击键，一个词，一次格式切换，还是一次批量操作，浏览器不会替你决定。如果每个字符都是一个撤销步，改一行字要按几十次 Ctrl+Z 才能退回去。

更要命的是，曾经唯一的标准化富文本 API `document.execCommand` 已经废弃，W3C 编辑工作组的草案建议开发者改用 JavaScript 编辑器库，并声明这份规范不会再继续推进[^4]。接替它的方向分成两路，一路是用于拦截编辑的 Input Events Level 2，另一路是把编辑状态从 DOM 里解耦出来的 EditContext API[^5]。但 EditContext 目前只有 Chromium 实现，Firefox 和 Safari 还没跟上，所以现代编辑器仍然要自己搭一套命令层，坐在 `beforeinput` 之上。

把这些坑放在一起看，能得出一条主线。浏览器给的编辑面不可靠，数据源就不能是 DOM 本身。所以现代编辑器都做了同一个决定：数据与视图分离。DOM 只是投影，真正的文档存在你自己的数据结构里。

第一段是输入面，它接收用户输入，并承担 IME、粘贴、拖拽这些浏览器的原生行为。第二段是事务引擎，它把输入事件翻译成针对一个带类型约束的 schema 的原子操作。第三段是文档模型，一份不可变的数据结构，是整个编辑器的唯一真相。第四段是协调器，它把模型状态投影到 DOM，再把 DOM 里的选区映射回模型坐标。第五段是协作层，它把本地事务和远端事务做合并。

这套架构里值得注意的一点是：历史记录和实时协作都不是独立开辟的代码路径，而是挂在这条事务流上的插件。因为每一次编辑都会产生一个事务，事务又天然可序列化、可撤销、可重放，所以撤销、重做、多人同步，都从同一个原语里长出来。这正是把数据模型设计成不可变状态的好处。

## 五、富文本的三种数据模型

五段流水线里，决定其余的是第三段，也就是数据模型。现代编辑器大致有三种形状，其余都是它们的变体。

第一种是线性操作日志，代表是 Quill 的 Delta。它把文档描述成对空文档施加一系列 `insert`、`retain`、`delete` 操作的结果。同一份数据结构既描述文档，也描述修改，所以它天然适合 Operational Transform。看一段 Delta 长什么样：

```js
// 一份文档
const doc = {
  ops: [
    { insert: "Hello " },
    { insert: "World", attributes: { bold: true } },
    { insert: "\n" },
  ],
};

// 一次修改：在第 6 个字符后插入 "Beautiful "
const edit = {
  ops: [
    { retain: 6 },
    { insert: "Beautiful " },
  ],
};
```

线性模型的好处是简单，一份 JSON 就能表达全部内容和修改，跨平台序列化没有歧义，OT 下的操作组合也很干净。坏处是它处理非线性结构很吃力，嵌套表格、多栏、任意深度的块嵌套，都要靠开发者不断修正浏览器产生的结构才能维持住。

第二种是树加扁平标记，代表是 ProseMirror。它的文档是一棵块级节点的树，但每个文本块内部的连续文本是一段扁平的序列，加粗斜体这些格式作为 Mark 标记贴在文本上，而不是像 DOM 那样嵌套出 `<strong><em>` 这样的结构。

```ts
// ProseMirror 的 schema：声明有哪些节点、哪些标记、能怎么嵌套
const schema = new Schema({
  nodes: {
    doc: { content: "block+" },
    paragraph: { content: "inline*", group: "block" },
    text: { group: "inline" },
  },
  marks: {
    bold: {},
  },
});
```

“加粗加斜体的文字”在 ProseMirror 里是一段带 `[bold, italic]` 两个标记的文本，不会再套成 `<strong><em>` 那样的一棵树。这个选择让很多东西变简单：切换格式不会重组树，重叠区间可以表达，文档里的每个位置都是一个整数偏移量，位置映射也便宜。而位置映射，正是协作模块 `prosemirror-collab` 的基石。

第三种是 DOM 形状的树，代表是 Lexical 和现代的 Slate。它的文档就是一棵长得像它渲染出的 HTML 的树，段落、标题、表格都是节点，加粗是文本节点上的一个格式标志，链接是一个包含文本的内联节点。

这里有两个地方要单独讲清楚。

第一个是 IME 组合输入的特殊规则。`beforeinput` 事件的规范里有一条明确的规定：`inputType` 为 `insertCompositionText` 的事件不可取消[^6]。你在输入法组合期间试图 `preventDefault` 它会静默失败，还会破坏组合框。正确的做法是让浏览器全程掌管组合生命周期，在 `compositionstart` 和 `compositionend` 之间把模型当作与 DOM 暂时脱节，只在 `compositionend` 的时候把最终文字写回模型。ProseMirror 把这段漂移写进了文档，Lexical 则把它隔离在协调器内部。

第二个是粘贴，它是整个编辑器最大的安全漏洞。剪贴板里来自恶意页面的 `text/html` 是不受限制的 HTML，`<script>`、`<iframe>`、`<img onerror=...>`、`javascript:` 协议的链接，全都在里面。直接 `innerHTML` 插进去，就成了一次存储型 XSS，其他打开这份文档的用户都会中招。所以粘贴要过一条净化管线：先在脱离文档的 `DOMParser` 里解析，这一步不会执行脚本，再剥离 Word 和 Google Docs 塞进去的私有标签，再过一遍 DOMPurify 这样的白名单净化器，最后流进编辑器自己的 schema 解析器，schema 不认识的节点一律丢弃，这一步是第二道防线[^7]。

## 七、协作：OT 与 CRDT 的分野

多人同时编辑同一份文档，是最考验数据模型的地方。两个人同时在同一个位置插入字符，结果必须一致，这件事要么靠服务器来定，要么靠某种确定的规则。于是有了两个流派。

Operational Transform 让每个客户端乐观地应用本地操作，服务器负责给操作排序，并广播一个变换，把每个操作改写成“仿佛在别人之后应用”的样子。它依赖一台中心服务器作为顺序的权威。ProseMirror 在这里做了一个化简：它不去枚举每一种操作对另一种操作的变换矩阵，而是通过 `StepMap` 来变换位置，用位置映射绕开了组合爆炸。

CRDT 则把足够的元数据塞进数据结构本身，让并发操作不需要协调者也能收敛。以 Yjs 为代表的实现给每个字符分配一个唯一的 `(clientID, clock)` 标识，删除用墓碑标记。这样两个客户端各插各的字符，合并时按 ID 排序就能得到一致结果，离线也能正常编辑。

两者的取舍很清楚。OT 换的是中心权威，好推理，服务器是唯一真相，坏处是服务器是硬依赖，长时间离线需要小心的 rebase 逻辑。CRDT 换的是离线正确，没有协调者，坏处是逐字符元数据的开销，一份几兆字节的文档能膨胀成几十兆字节的 CRDT 状态，墓碑还会越积越多。

一个容易被营销话术误导的地方是，真实系统基本是混合的。Figma 评估过 OT，判断它对设计对象来说是过度设计，于是做了一个中心化、借鉴 CRDT 思想的系统，既不是纯 OT 也不是纯 CRDT[^8]。Linear 的核心同步引擎是自研的，默认 last-write-wins，只在议题描述这类特定文本字段上用 CRDT[^9]。Google Docs 用 OT，一部分是历史原因，一部分是规模原因，在数亿用户量级下，CRDT 逐字符元数据的成本不可忽视[^10]。所以“XX 迁移到了 CRDT”这类说法，多数时候是把复杂的真实架构简化成了口号。

## 八、性能与大文档

当文档从几十段涨到几十万段，前面的架构又要加一层考虑。

最主要的手段是虚拟化，只渲染屏幕可见的块外加一小圈缓冲。最简单的做法用 `IntersectionObserver` 追踪哪些块的哨兵进入了视口，渲染 `[start - buffer, end + buffer]` 这个窗口。Slate 在 `slate-react` 里提供了实验性的分块 API，但分块只在一个节点的子节点全是块而非内联文本时有效，所以最好只用在编辑器根部。CSS 的 `content-visibility: auto` 能作为互补的一层，跳过离屏块的绘制。

内存预算也是大文档绕不开的账。文本密集的文档可以用 piece table 这种结构，把文档表示成对原始缓冲的若干片段的引用，插入删除只动片段不搬整个缓冲。计算缓存放在 `WeakMap` 里，由垃圾回收器自动清理。撤销历史用 LRU 逐出，代价是丢掉最老的撤销步。CRDT 的墓碑要周期性做垃圾回收，Yjs 文档里写了这套控制项，OT 系统则要自己实现等价清理。

走到这一步的极端，就是 Google Docs 的选择。它在 2021 年把文档渲染从 DOM 迁到了 Canvas，用 Canvas 自己画所有内容，DOM 只留一个隐藏的输入层负责接收文字和 IME[^11]。这么做的原因很直接：当文档规模大到 DOM 的布局开销成为瓶颈，当跨平台的一致性重要到不能容忍浏览器之间的渲染差异，就得放弃让浏览器帮你排版，把渲染整个拿回来自己做。代价也明摆着：光标、选区、无障碍，这些浏览器本来免费给的东西，全都要自己重写。所以大多数编辑器到不了也不需要到这一步，它们仍然建立在 `contentEditable` 之上，只是用一个协调器把它管住。

## 九、亲手写一个最小内核

看懂了原理，动手写一个就明白数据与视图分离到底意味着什么。下面是一个极简的内核，只用文字和加粗做例子，但核心思想是通用的：状态不可变，事务是纯函数，视图只是投影。

```ts
// 一个文本段：一段文字加上它的格式集合
type Mark = "bold";

interface Segment {
  text: string;
  marks: Mark[];
}

// 状态不可变：内容加上选区。选区用整数偏移量表示
interface State {
  segments: Segment[];
  sel: { from: number; to: number };
}

// 在选区内切换加粗。这是纯函数：输入旧状态，输出新状态，旧状态原封不动
function toggleBold(state: State): State {
  const { from, to } = state.sel;
  if (from === to) return state; // 光标没选中任何东西

  const out: Segment[] = [];
  let pos = 0;

  for (const seg of state.segments) {
    const end = pos + seg.text.length;
    if (end <= from || pos >= to) {
      // 整段都在选区外，原样保留
      out.push(seg);
    } else {
      // 把这一段切成选区前、选区内、选区后三截
      const left = from > pos ? seg.text.slice(0, from - pos) : "";
      const mid = seg.text.slice(
        Math.max(0, from - pos),
        Math.min(seg.text.length, to - pos)
      );
      const right = to < end ? seg.text.slice(to - pos) : "";

      const hasBold = seg.marks.includes("bold");
      const nextMarks = hasBold
        ? seg.marks.filter((m) => m !== "bold")
        : [...seg.marks, "bold"];

      if (left) out.push({ text: left, marks: seg.marks });
      if (mid) out.push({ text: mid, marks: nextMarks });
      if (right) out.push({ text: right, marks: seg.marks });
    }
    pos = end;
  }

  return { ...state, segments: out };
}

// 视图只是投影：把状态渲染进一个 contenteditable 容器
function render(root: HTMLElement, state: State): void {
  root.textContent = "";
  for (const seg of state.segments) {
    const span = document.createElement("span");
    span.textContent = seg.text;
    if (seg.marks.includes("bold")) {
      const strong = document.createElement("strong");
      strong.append(span);
      root.append(strong);
    } else {
      root.append(span);
    }
  }
  restoreCaret(root, state.sel.from); // 把光标放回去，这里只处理折叠光标
}
```

这段代码值得注意的，是它缺了什么。真实编辑器里，`render` 之后还必须做一件反向的事：监听 DOM 里的选区变化，把 `window.getSelection()` 拿到的 DOM 坐标翻译回模型里的整数偏移量，再更新 `state.sel`。这个从 DOM 到模型的回映，加上 `toggleBold` 这种从模型到新模型的纯变换，合起来就是整条流水线的缩影。你在这里看到的概念，schema 约束、事务原子性、不可变状态、协调器 diff，都是把这几十行代码往工程化方向放大的结果。

## 十、怎么选

写到这里，选型是一件可以按需决定的事。

如果只是评论框、聊天输入框，用 Quill 就好，接受浏览器的不一致，靠 Delta 和 OT 快速落地。如果要的是 CMS 或文档工具，需要强制编辑结构，就用 ProseMirror 或它上面的 Tiptap，schema 在第一次挡住一份非法文档的时候就已经值了。如果要的是像素级渲染、复杂内嵌、紧凑体积，用 Lexical，同时做好 IME 和无障碍的预算。如果要在 React 上做无 schema、插件优先的创作，现代 Slate 是那条路。

无论选哪个，都要面对前面那些问题。因为富文本的本质问题，从来不在于“哪个库好用”，而在于“一段文字之外的格式和结构，存在哪，谁说了算，多个人一起改的时候怎么不打架”。想清楚这三个问题，再回头看任何一个编辑器，都能一眼看到它的结构。
