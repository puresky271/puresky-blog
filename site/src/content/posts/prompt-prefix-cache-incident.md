10 月 29 号晚上，我在看一张消耗明细，上面有一行数字连着几天都是 0：缓存读取。

同一套装配代码，之前在 DeepSeek 上能稳定读到缓存。换到 Gemini 4 的一条中转线路之后，输入永远是完整的 prompt token 数，缓存读取是 0，缓存写入也是 0。

明细上就是三个数在反复出现：输入是多少，缓存读取是多少，缓存写入是多少。这件事持续的不是一轮两轮，是连续几天的每一条主回复。

一份主回复的 prompt 大概三万多个 token，每轮都按全价计费，这在账单上很显眼。

我列了六个嫌疑：模型不支持缓存，中转线路不支持，我没传显式的缓存字段，prompt 前缀每轮都在变，用量字段解析错了，上游缓存失效了。

下面是一个一个把它们杀掉的过程。最后活下来的那个，是我自己拼出来的 prompt。

## 先证明这条路本来能缓存

第一步不是改代码，是证明这条路能缓存。

我造了一份 8,041 token 的最小请求，一字不改连发三次：

| 第几次 | cached_tokens |
| --- | ---: |
| 第 1 次 | 0 |
| 第 2 次 | 5,987 |
| 第 3 次 | 5,987 |

能命中。这条线路和这个模型都支持缓存，而且不需要 Claude 那种 `cache_control` 标记。

顺带把机制说清楚，因为后面的每个数字都要靠它解释。

前缀缓存复用的是 KV 状态，不是回答。它记下的是“这段 token 算过一遍”的中间结果，下次请求开头逐字相同，这段就不用重算。所以它不是语义缓存，意思相近但字面不同不算命中。也不是响应缓存，模型照样重新生成，温度和采样参数照样起作用。它是按前缀匹配的：开头一变，变化点之后全部作废。

顺便说清隐式和显式的区别，因为后面会反复用到这个区分。显式缓存要我自己创建一份缓存对象，指定哪些内容进缓存，还要管它的生命周期。隐式缓存没有这套接口，平台自己决定缓存什么，我唯一能影响的是把 prompt 写成什么样。所以后面所有的功夫，都只能花在“让前缀值得被缓存”上。

这条线路用的是隐式缓存，有两个硬指标。可缓存输入的最低门槛是 4,096 token。多轮场景下还有一条规则：新请求比上一轮至少多出 2,050 token，才会缓存完整的上一轮请求，不够的话，上一轮末尾那 2,050 token 会被重新处理。

8,041 减去 2,050 再减去 4 个 token 的边界开销，正好是 5,987。第 2 次和第 3 次读到的就是这个数。

接下来把“长 prompt”“多 system message”“计量映射错了”三个嫌疑一起排掉：拿一份真实的 32,023 token 主回复 `messages` 原样连发两次。

| 第几次 | 输入 tokens | cached_tokens |
| --- | ---: | ---: |
| 第 1 次 | 32,023 | 0 |
| 第 2 次 | 32,023 | 29,974 |

结构和长度都没问题，计量映射也是对的。

这里还有个当时被我当巧合放过的信号：第二次命中的是 29,974，输入减命中是 2,049。这个数后来变成了整篇文章的钥匙，当时我只觉得它挺接近两千。

顺便记一下这个数在响应里叫什么，不同协议不一样：DeepSeek 常见 `prompt_cache_hit_tokens`，Gemini 原生常见 `cachedContentTokenCount`，OpenAI 兼容的响应里在 `usage.prompt_tokens_details.cached_tokens`。我用的是最后一种，所以一开始我甚至怀疑过是不是字段名对不上。

## 只改一个字，命中就归零

剩下的嫌疑里，最不像真的那个是“前缀不稳定”。32k 里每轮真正变化的可能只有几百字，凭直觉这不该让整份输入重算。

我做了个单变量实验：把上面那份真实 prompt 的首条 system 只改一个字，其余 32k 原样不动，再发一次。

```text
改动前，第二次请求：cached_tokens = 29974
改动后，这一次请求：cached_tokens = 0
```

29974 变 0。

也就是说在这条链路上，首条 system 在缓存眼里是一整块。它里面只要变一个字节，这一块的整段计算就都不能复用，哪怕后面还有两万多字逐字相同。

这就是为什么“在开头改短一点”没有用，“把内容挪到后面”才有用。缓存匹配的是连续前缀，不是“共同部分占多少”。

嫌疑从六个收敛到一个：我的首条 system 里混进了每轮都会变的东西。

## 把每轮会变的东西赶出首条 system

### 第一处：一张按场景生成的长度卡

首条 system 当时装的是稳定人格，外加一张场景长度卡。这张卡按当前用户说的话生成：闲聊给一个长度，请求协作给另一个，问日程又是另一个。

对缓存来说，这张卡就是那“一个字”。

第一阶段的修法很直接：首条 system 只留稳定人格和全局长度规则，场景化长度卡整块挪到 prompt 尾部的 `<turn-style-target>`。

这里有个坑值得说。我本来想顺手塞进已有的 execution hint，但那层会把内容压缩到 240 字，长度卡的语义直接被压没。为了不被压缩，只能给它新开一个平面。

改完做 A/B：同时改变场景卡和当前用户文本，32,391 个输入 token 里命中 30,338 个，约 93.7%。

### 第二处：七个我没想到的块

第一阶段上线之后，缓存读取不再是持续为 0，但还是会 miss。

我把 22:14 和 22:16 两份真实 prompt 摊开对齐，前 24,984 个字符一模一样，然后分叉了。第一轮触发了与“熬夜”“作息”有关的特殊规则，第二轮没有。

对齐不是靠肉眼。我把两份 dump 的 messages 按块切开，逐块配对，打印出第一处哈希不同的块。这比盯着两坨 JSON 看快得多，也不会有“看起来一样”这种错觉。

顺着这条线继续审，我把剩下的逐轮内容整批挪进 `<dynamic-persona-context>`：本轮队友补充档案，开发者动态印象与今日事实，新闻与角色观察，角色特殊场景规则，图片问答补充，情绪提示，贴纸与 UI 状态。

首条 system 里只留主角色 canon，稳定身份和输出契约。

挪的时候有一件事要反复确认：当前 user 必须在最后一条，执行包不能跑到历史摘要前面。缓存的收益是次要的，提示词的语义顺序一旦破坏，角色扮演的质量会立刻掉下来。每挪一次，我都重新确认这几个位置。

再验一次，两份连续的真实 prompt 首条 system 都是 24,927 字符，SHA 完全一致。特殊规则只出现在对应轮次的动态平面里，当前 user 和执行包的位置没动。第二次请求输入 37,195，命中 35,146，约 94.5%。

两次修复在代码上都不复杂。难的是接受一个说法：“稳定”不是一个形容词，是一个可以验证的性质。判断首条 system 稳不稳，别比字符长度，比 SHA。

> [!TIP]
> 比对长度是最不可靠的做法。长度相同但内容变了会骗过人，长度变了但只是末尾追加也会骗过人。

```python
import hashlib
import json

def first_system_sha(path):
    messages = json.load(open(path, encoding="utf-8"))
    head = messages[0]["content"]
    if not isinstance(head, str):
        head = "".join(part.get("text", "") for part in head)
    return hashlib.sha256(head.encode("utf-8")).hexdigest()[:12]
```

这个动作的前提是每一轮真实请求都落一份 dump。那是上一篇 [我给提示词做了版本控制](/posts/prompt-diff-gate/) 里定下来的规矩，这次正好是它变现的时候：没有那两份 messages，我只能看着两个 0 猜。

还有一个嫌疑排得更早：刚上线的引用对话功能。无引用和有引用做 A/B，两次生成的人格块完全相同，首条 system 完全相同，引用原文只进 `ON_DEMAND_EVIDENCE`，引用焦点只进最后一条 user 的执行包，第一处差异落在后续的对话弧和证据平面。它可以改变命中比例，但不会让缓存读取归零。

## 剩下的 0 不在我的代码里

修完之后的线上数字长这样：

| 输入 tokens | 命中 | 命中率 |
| ---: | ---: | ---: |
| 25,602 | 8,192 | 32.0% |
| 24,714 | 18,474 | 74.7% |
| 26,458 | 18,473 | 69.8% |

第一眼看，32.0% 那行像是还有问题。但接下来还有两件事。

一是半夜两次单轮为 0。23:34 一轮是 0，下一轮自己恢复。23:56 又一轮是 0，也是下一轮恢复。同时段中转还回过一次 503。我把这两组相邻轮次各自重建了真实 prompt，首条 system 逐字相同，第二条历史摘要也逐字相同，一直到当前状态帧那些更靠后的平面才开始变化。

二是同一条线路下，不同角色的命中率差得很远。立希的首条 system 有 30,041 字符，逐字一致，我拿两份几乎一样的真实 prompt 连发：输入 27,952 时第一次 0，输入 27,944 时第二次 8,192，约 29.3%。

这两组都不是“拼错了”。真正解释它们的是同一个比例：能复用的前缀占了输入的多大一块。

把四组“好”的数据摆在一起，我才发现它们不是“还差一点”，是“正好到顶”：

| 场景 | 输入 | 命中 | 输入减命中 |
| --- | ---: | ---: | ---: |
| 最小探针第二次 | 8,041 | 5,987 | 2,054 |
| 真实长 prompt 第二次 | 32,023 | 29,974 | 2,049 |
| 场景长度卡移出后 | 32,391 | 30,338 | 2,053 |
| 两层都修完 | 37,195 | 35,146 | 2,049 |

四个缺口全停在两千上下，两千正是那条“新增不足 2,050 token 就重算尾部”的规则。

所以 93.7% 和 94.5% 不是还没调好，是这条线路上的上限。剩下那 6% 不是我的前缀有 bug，是每轮末尾必须新算的那一段。这也顺带解释了 32.0% 那一行：输入越短，固定的两千块占比越大，命中率自然越低。

至于 8,192 这个数两次出现，我到现在也没解释清楚。它看着很整，像一块 8K，但另外两组命中 18,474 和 18,473 只差 1 个 token，输入却差了 1,744，又不支持“整块”这个解释。我把它记成悬案，没有编机制。

这也解释了为什么换线路之后感觉明显变差：DeepSeek 的缓存单元更粗，保留窗口是小时到天级，旧结构下更容易命中。这不代表它更稳，两边文档都写着 best-effort，只是它对我当时那个结构更宽容。

到这里，能算到我头上的只有两件事：首条 system 里混了动态内容，以及我原来用字符长度判断它稳不稳。剩下的 miss 属于隐式缓存的 best-effort，文档写得很清楚，它不保证命中，行为受分片和路由影响。

## 复盘：缓存为 0 时按什么顺序查

这套顺序值得写下来，因为第一步就不是改代码。

1. 先证明这条路本来能缓存。造一份过了门槛的最小请求，连发三次。第二次还是 0，问题在平台或者用量解析，不在 prompt。
2. 再比 SHA，不比长度。拿相邻两轮的真实 messages，先比首条 system 的哈希，再比历史摘要和工具定义，找到第一处差异，看它落不落在稳定前缀里。
3. 稳定内容靠前，会变的内容靠后，并且给会变的内容一个明确的落点。这次真正的产物不是“挪走了一段”，是两个尾部平面：一个装本轮的风格目标，一个装本轮的人格补充。
4. 单轮为 0 又自己恢复，先别动 prompt。记录时间和模型，还有这一轮的输入量与缓存 token，归到上游。也别为了一次 miss 自动重试，那是拿钱去买一个不确定。
5. 要可预期的成本就别用隐式缓存。它给不了保证，能选的是换一条支持显式缓存的线路，或者接受命中率的波动。

这段经历也回答了一个常见问题：命中率还能不能再调高。在隐式缓存下，能调的只有前缀结构，剩下的是每轮必然新增的输入。把稳定部分做到极致之后，比例就由“每轮新增多少”决定，而这个量由业务本身决定，不由 prompt 决定。

另一头是别把东西挪错。能挪的只有“这一轮才知道的事实和状态”，而身份和 canon，还有输出契约，这些必须留在首部，挪到后面等于每轮都重新教她是谁。

顺带说一条我没做到的：这两次修复都靠事后对 dump，而不是靠一个能提前报警的指标。缓存命中率掉下来的时候，我是从账单上看见的。如果重来一次，我会先给这个比例加一条按角色分组的日线，而不是等数字变成 0 才去查。

最后说回那行一直是 0 的明细。它教我的不是“prompt 要写稳定”，而是：写“稳定”这两个字的时候，手里得有一个能证明它的东西。字符长度不算证明，哈希相等才算。
